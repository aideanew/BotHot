# 02 需求复核与辩证分析（V0.23.0）

## 1. 复述

BotHot 是 Aidean 主平台的独立机器人子系统：多渠道推送、热点日报、知识库 + RAG 问答、
公众号入库、整号订阅、SSO、管理后台。功能面八条需求里六条判「已实现」、两条判「部分」
（F-003 引擎骨架位、F-005/F-008 真后端读数），判词层面的三处过期已在 V0.22.0 排进 62。

本版复核的是**另一层**：判词之下，还有没有"契约/需求要求了、代码里确实没有"的东西。
答案是**有，但只剩三类，且都在 UI 与契约面上，不在业务逻辑里**：

1. **八态契约的 5 条要求没落地**（U1～U5）。这是本项目自己的 `ux_states` 冻结稿写的，
   不是外部最佳实践——它要求"演示态必须显式声明""0.0 显示待评分""降级不得显示成无通知"，
   而代码里这五处要么静默、要么文案合并、要么无分支。
2. **identity / chat 两域的形状仍是手写**（U6）。D-V21-01 定的是"一份形状、三处受约束"，
   六个域 + engine + shapes 都接上了，这两域还是 `.gitkeep`。
3. **八态契约的唯一源在历史版本目录里**（U7）。P-80 从 V0.12.0 挂到今天没人认领，
   而 STEP-60 的判据正是"八态枚举读契约"——不先解决，60 会把跨版本依赖固化进 e2e。

**这不是"又发现一堆没做的功能"。** 业务逻辑面（推送六渠道、聚簇评分、Manifest Diff、SSE、
引擎可插拔位、SSO、管理端读写）经本轮现读是完整的：`grep -rn "TODO\|FIXME\|未实现" apps/api/app`
除 `engine_port.py` 的显式骨架位外零命中。缺口集中在**"说好的界面行为"与"说好的单一形状源"**。

## 4. 5W1H

- **What**：真正未实现的只剩 6 条（U1～U6），全部落在"界面行为"与"形状单一源"两处；
  另有 1 条未归位（U7）、2 条显式排除（U8）。
- **Why（根因，不是现象）**：这三类缺口同源——**契约写得比实现细，而契约不在活体链上**。
  `ux_states` 冻结稿在 V0.12.0 写完就被版本迁移丢下（P-80），于是它的 5 条要求在
  "没人读得到"的状态下自然腐化；identity/chat 因为"没有对应的 SQLAlchemy 实体"
  被生成器跳过（`gen_contracts.py:40-48`），前端只能手写（`types.ts:19`）。
  **不是执行者偷懒，是判据没有执行者。**
- **Where/When**：`apps/web/components/{NotificationBell.tsx,chat/useSseAsk.ts}`、
  `apps/web/app/hot/page.tsx`、`packages/contracts/**`、`apps/api/app/contracts/ux.py`（新增）、
  `apps/api/tests/test_contract_jsonschema.py`、`apps/web/lib/api/types.ts`。
  64 先于 65（65 的测试要读 64 产出的枚举），64 先于 66（同改 `src/index.ts`），
  60 等 64+65，62 等 60，63 最后。
- **Who**：64/65 规划方亲做（核心 + UI）；66 执行助手；60/62/63 执行助手；
  判定由独立复查（只看 diff + 运行结果，只出 PASS/FAIL/UNKNOWN）。
- **How**：64 走"枚举进 Python 契约 → 生成器出 schema/TS → 一条相等断言"；
  65 走"先写红用例 → 改渲染 → 用例转绿"；66 走"实体内省 + 响应形状两路，前端 types 改别名"。
- **What if**：
  ① 加 ux 域撞既有域稿判据 ⇒ 走方案 B（常量模块 + 相等断言），不动生成器；
  ② 通知演示态在 mock 构建里拿不到 `isMockMode()` ⇒ 改由 `NEXT_PUBLIC_API_MOCK` 构建期内联常量判定（`http.ts` 已有同源机制）；
  ③ 热点页拿不到"最近更新时间"（后端不返回）⇒ M4 降级为只区分两态、时间字段进 backlog，**不伪造数据**；
  ④ 聊天 30002/50002 在前端拿不到 code（SSE error 帧无 code）⇒ 按 `ask.ts:159` 的 `evt.code ?? 50002` 兜底，仍可分流；
  ⑤ identity 的 `MeData` 改成别名后 tsc 报字段缺失 ⇒ 说明手写类型与后端投影本就不一致，**这是本卡要暴露的东西**，按后端 `get_me` 的三条分支字典（`apps/api/app/services/auth/service.py:239-250 / 273-278 / 286-293`）为准改前端，不反向改后端。

## 5. 钢人论证（关键判断逐个正反打）

### 5.1 "U1～U5 算未实现的需求"是否成立？

- **支持（最强）**：① 契约原文是命令式（"必须显式显示""禁止静默装作正常""不得显示为「无通知」"），
  不是建议式；② 契约文件在仓库里、被 e2e spec 引用（`r19-chat-stream.spec.ts:24`）、
  被 STEP-19 当判据用过（`REQ-F-005-rag-chat.md:34`）；③ 代码里对应位置确实是静默/合并/无分支（U1～U5 二级证据）。
- **反对（最强）**：① 该契约是 V0.12.0 的**冻结稿**，冻结稿的效力是"当时的判据"，不是"永久需求"；
  ② 它不在活体契约链上（U7），严格说它现在是"历史设计文档"，拿它当需求可能越权；
  ③ 项目已发 v1.1.4，若这五条算 MUST，前四个版本都漏了，说明当时也没人当它是 MUST。
- **裁决**：**部分成立，按"契约已声明但未兑现"处理，不按"新增需求"处理。** 三条限定：
  （a）只做契约**明写**的五条，不扩写（例如不因为"降级"就去补全站降级）；
  （b）不升格成 REQ-F-005/F-001 的 MUST，而是**在 STEP-64 把它变成活体契约后**才具备强制力——
  这正是 64 先做的理由；
  （c）62 的判词纠真里**不写**"F-001 已实现"这种升格话，只写"八态契约的 5 条已兑现"。
- **仍未排除的反对**：若产品方认为这五条本就不是需求，则 65 变成"自愿改进"。此点在 05 §2 登记为待裁决，
  但**不阻塞**：五条改动都是小改，且都朝"更诚实"方向（不静默、不冒充 0 分），即使不算需求也不产生负价值。

### 5.2 "identity/chat 该做成契约域"是否成立？

- **支持**：① `index.ts:17` 自己写着"待后端对应模型纳入生成器后接线"，是承诺不是猜测；
  ② 前端 `MeData` 手写 14 行字段，与后端 `_project_me` 的投影面是两个真源（P-122 的同类）；
  ③ D-V21-01 已定"一份形状、三处受约束"，两域缺席使这条裁决只兑现了 8/10。
- **反对**：① chat 域**没有 SQLAlchemy 实体**（`product-requirements.md:40` 的数据模型列是「—」），
  按 `DOMAIN_ENTITIES` 的机制无法内省，硬做会变成"手写一个 Pydantic 模型再生成回 TS"，绕一圈没有收益；
  ② identity 的 `MeView`/`MeWallet` 已在 `shapes` 域里（`types.ts:47` 已在用），
  再做 `identity/dto.ts` 会与 `shapes` 域**同名不同体**风险（生成器 `gen_contracts.py:258-262` 的冲突守卫会拦）。
- **裁决**：**identity 做，chat 只做"响应形状"不做"实体镜像"。** 具体：
  （a）identity：`User` 实体进 `DOMAIN_ENTITIES`，产出 `identity/dto.ts` 承载**持久层列形状**；
  与 `shapes.MeView` 的分工写进 `index.ts` 注释（一个管库、一个管线上），**不合并**；
  （b）chat：只把 `ChatCitation` / `ChatAnswer` 两个**线上形状**从 `types.ts` 挪到 `shapes` 域
  （它本来就是线上形状，归 `shapes` 才符合 STEP-47 定的分工），**不新建 chat/dto.ts**。
  ⇒ 这条裁决直接缩小了 66 的范围，也消除了"同名不同体"风险。
- **仍未排除**：`shapes` 域越加越大（已 222 行），未来要拆；本版不拆，登记 05 §2。

### 5.3 "U7 必须先做"是否成立？

- **支持**：① 60 的判据原文要"八态枚举改为读 `ux_states.schema.json`"，若读冻结稿，
  e2e 就依赖 `docs/任务规划V0.12.0/`——一个**历史版本目录**，任何一次文档整理都会打断它；
  ② P-80 自 V0.12.0 挂到现在，是本仓最长寿的未闭合项之一；③ `test_contract_jsonschema.py:45`
  已把该路径硬编码，等于契约锚被钉在历史版本。
- **反对**：① 60 完全可以继续硬编码数组（现状），八态枚举一共 8 个值，两年不变的概率很高，
  为它开一卡是过度工程；② 加域要动 `DOMAINS` 与既有判据，风险 > 收益（K5/K6）。
- **裁决**：**做，但按最小面做**——只迁 `State` 与 `StateRendering` 两个 def，
  `x-core-views` 不迁；且**允许方案 B 退路**（只加常量模块 + 一条相等断言，不动生成器）。
  S64.0 探针先跑，用读数选路，不用偏好选路。
- **仍未排除**：方案 B 下"唯一源"仍在冻结稿（只是被断言钉住），严格说 P-80 只算"显式声明取代关系"那一半闭合。
  ⇒ 05 §2 把"P-80 是否算闭合"的判定权留给复查者，卡面写"部分闭合"而非"闭合"。
