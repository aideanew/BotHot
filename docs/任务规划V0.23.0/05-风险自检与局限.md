## 3. 本规划的局限（必须一起读）

- **L1 只读了一份契约的叙述面。** 我逐条核了 `ux_states` 的六视图 × states，但**没有**对
  `identity.schema.json` 的 `x-idor-checklist`、`resources.schema.json` 的 `x-api-surface`、
  `errors.global.schema.json` 的 `x-table` 做同样的逐条核对。这些 `x-*` 扩展键里可能还有
  "声明了但没实现"的条目。⇒ 本版的"未实现清单"是**下界，不是全集**。
- **L2 未实现判定依赖"代码里找得到/找不到"这种检索式证据。** 它证明"字符串不存在"很硬
  （`grep` 零命中），但证明"行为不存在"较弱（可能用别的文案实现了同一行为）。
  所以每条都配了"通路是否存在"的第二级证据（例如 U2 证明帧解析存在、只缺文案），
  但**仍可能有我没想到的实现方式**。
- **L3 @ci 读数全缺。** 本机无 gh（`gh --version` 非零），D-V6-02 要求 CI 只能由 gh 或
  CI 产物认定 ⇒ 本文件**任何**关于 CI 的陈述都只能记 `采信[REMOTE]` 或"未读"。59 的余项因此仍是余项。
- **L4 本机不能跑 e2e-real。** 无 Redis、无 docker ⇒ 60 的判据只能在 @ci 取，本机无法预演。
- **L5 工期估算无历史基线支撑。** 「≈0.5 / 1 / 0.4 人日」是按改动面与既有同类卡（61 的 ≈0.3）估的，
  不是实测；本仓没有"卡的实际耗时"记录，故这些数字**不应当作承诺**。
- **L6 我没有验证 `ux.py` 的 Pydantic 模型能否生成出与冻结稿 `definitions.State` **键形完全一致**的产物**
  （冻结稿用 `definitions`，产物用 `$defs`）。这条正是 S64.0 要跑的东西；若跑出来不一致，
  方案 A 就要退 B——**这不是我漏了，是我把它设计成了必须用读数回答的问题**。

## 5. 自检结论

**通过，但带三条限定**（不满足"全部 ✅"就不许说全绿）：

1. §4.2 的"六份契约齐全"按**本仓现状**判定为 ⚠️ 部分——本版不新建契约包，只归位与补齐两份。
   若把指令的 §4.1 理解为"每版都必须重新产出六份"，则本版不满足；我按"本仓已有六份活体源"理解。
2. §4.3 的"第一刀是步行骨架"不适用（本仓已过该阶段），已改为"第一刀解锁依赖最多"。
3. §3 的 L1 表明本版"未实现清单"是下界。**任何人不得把本清单当作"全部未实现项"的证明。**
