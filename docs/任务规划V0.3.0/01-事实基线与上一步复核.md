### 3.1 被推翻的结论（苏格拉底式追问记录）

**结论**：「`test_event_delivery_failure_no_reclaim` 失败是因为 9999 端口被回 2xx 的服务占用；改指 `127.0.0.1:1` 即根治。」

1. 凭什么？——STEP-00 依据是代码阅读（`webhook.py:39-46`）与 `http.server 9999` 实验。
2. 证据是否来自最新代码？——是，但**没有在改后实跑连库用例**（S0.1.3 交给了 CI）。
3. 相反证据？——本次实跑改后仍失败；DBG 打印 `error_message='webhook 返回 HTTP 404'`，拒连不可能产生 HTTP 状态码。
4. 表面 vs 根因？——表面是「目标端口有人应答」；根因是「httpx 默认读取环境代理，测试出站不受控」。
5. 前提？——STEP-00 的结论只在「无代理环境」成立；CI runner 无代理所以 CI 绿，开发机（Dockerfile 注释记载宿主有 `127.0.0.1:10809` 代理）与本沙箱都会失败。
6. 结论仍有效吗？——「去掉端口空闲假设」方向正确但不充分。
7. 需要额外验证？——已做：清代理后 11/11 通过（§D）。

**钢人论证**
- 支持「改测试即可」：生产 webhook 走环境代理可能正是期望（企业出口代理），不应为测试改生产行为。
- 反对：测试出站受环境影响 = 测试不确定；且生产 webhook 是否应走代理、`127.0.0.1`/内网目标是否应绕代理，属行为决策。
- 判定：本轮只在**测试侧**消除环境依赖（autouse 夹具清除代理变量 / 注入 MockTransport），生产 `trust_env` 是否保留列为 NON_BLOCKING 未知 U-08，不在本轮改。
