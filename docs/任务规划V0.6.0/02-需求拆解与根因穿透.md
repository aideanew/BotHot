### 2.3 静默性（为什么 P0 长期没人发现）

- 告警只有三类：心跳缺失、Job 积压、推送连败（alerting.py:71/:81/:87）；指标六族无采集维度（metrics.py:55-80）。
- `_map_row → None` 不计数、不打日志；整页丢弃对外表现为“这一轮没有新文章”，与正常空轮询不可区分。
- 因此 STEP-05 的价值不是“多一个面板”，而是让 P0-3 这一类缺陷**下次在一天内被告警发现**。

## 4. 关键取舍（辩证）

| 议题 | 方案 A | 方案 B | 选择与理由 |
|---|---|---|---|
| 键格式（D-V2-01） | `b:{biz}:{mid}:{idx}` / `s:{token}` / `h:{sha256[:32]}` | 无前缀 `{biz}_{mid}_{idx}` / `{token}` / `{hash}` | **A**：前缀让三种来源永不碰撞、可被正则校验（契约 `ArticleKey.pattern`），存量裸 token 与新键可区分，回填可幂等判断“已迁/未迁”。代价：外部若有人按裸 token 查询需适配——仓内只有 kb/batch_ingest 两处消费方，可控 |
| 存量资产 | 迁移内回填 | 迁移只做 DDL，回填走脚本 + 人批 | **B**：迁移不依赖应用代码；生产规模未知（U-02/03）需先只读审计 |
| 清单对齐 | 改 manifest.external_id 为规范键 | 新增 `article_key` 列，保留渠道 id | **新增列**：渠道 id 仍是上游翻页/去重依据，不能丢 |
| 证明脚本 | 继续维护 | 判据迁 pytest，脚本归档 | **迁 pytest**：唯一能进 CI、能被变异反证、换机可跑的载体；禁 `git rm` 约束下以 README 标注归档 |
| 复审轮次 | 不设上限 | ≤2 轮熔断 | **≤2 轮**：S2.1.3 第 3–10 轮未改变任何业务结论（被证对象 3 行未变）；第 3 轮起应转为新卡或升档 |
| 性能优化 | 预先加索引/批量 upsert | 先测基线（STEP-11）再定 | **先测**：禁止无基线优化；但 STEP-04 的新索引 `ix_manifest_source_article_key` 属于正确性配套，随迁移一起加 |
| 扩展性 | 每个渠道各自适配 | 统一 `WorkListRow` 行契约 + 渠道注册表 `ChannelSpec` | **统一契约**：新增渠道 = 实现一个返回 `WorkListRow` 的 provider + 注册一条 spec + 参数化契约测试自动覆盖（STEP-03/08） |
