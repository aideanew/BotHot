## 5. 入库切分（第 1 批已入库 / 第 2 批随 STEP-00C 修复同批）

本目录以**第 1 批**入库：除 `evidence/65f508b/STEP-00C_simulated_65f508b.patch` 之外全部进仓。
该 patch 此刻**仍在工作树里、没进仓库**（也没写进 `.gitignore`，所以 `git status` 会一直列出它）。

- 判据工具随件入库，读数可复跑，不必信本节抄的数字：
  `python docs/任务规划V0.5.0/evidence/65f508b/secret_shape_scan.py docs/任务规划V0.5.0`
  ——本机没有 gitleaks 二进制，这个召回器把 `.gitleaks.toml` 规则 1（`scheme://<账号>:<口令>@<主机>`
  邻接形）与占位口令 allowlist 的正则**原样复刻**，只报 `文件:行号 + 形状片段`，不报正文；rc=1 表示有 HIGH。
- 决策时点（2026-10-13）实测：本目录的 HIGH **全部**落在该 patch 上（diff 的删增两侧都带
  `scheme://<账号>:<口令>@<主机>` 这段邻接形，账号与口令都是一字母的测试桩，但形状就是门禁要拦的形状），
  本目录其余文件 HIGH=0；`00-README.md:51` 那条 `postgresql+psycopg://postgres@…` 没有口令段，天然不匹配。
  本节**刻意不把那条串原样抄进来**：抄进来就等于让一次文档提交自己给 Security 门禁新增一条检出——
  上一版就栽过这个（见 `gitleaks_65f508b.txt` [A] 与 V0.4.0 的第 2 批切分）。要形状去扫描器输出里看。
- **这台仪器的校准件是 V0.4.0**：同一条命令跑 `docs/任务规划V0.4.0`，HIGH 恰为该批已知的
  两件（`evidence/b45777a/STEP-00C_proposed.patch` 4 处 + `evidence_check_b45777a.txt:121` 1 处），
  与 05 §3 记录的、当时用**真实** gitleaks 8.21.2 实测出的切分理由逐条对齐；
  `x:nosuch@`、`bothot:bothot_ci@` 这些占位段一律走 allowlist 放行，没有多报。
- 为什么不让它进来：`gitleaks_65f508b.txt` [A] 段已实测 Security 门禁正被 `x:y@` 这一形红着
