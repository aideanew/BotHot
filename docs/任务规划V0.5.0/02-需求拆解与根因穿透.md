## 2. 核心功能：四个 P0 的调用链穿透（65f508b）

### 2.1 入库主链（单篇）

```
POST /kb/ingest  或  job_worker._drain_items (job_worker.py:324)
  └─ make_default_ingest._ingest (job_worker.py:128)
       └─ KnowledgeBaseService.ingest_url (kb.py:200) → _ingest_url_inner (kb.py:211)
            ├─ _short_link_key / _lookup_short_link (kb.py:228-230)      短链 → 已映射长链键
            ├─ article_key = _article_key(norm_url) (kb.py:235)            ★P0-1 长链恒为 "s"
            ├─ _find_source_by_anchor(article_key, url) (kb.py:237→336)
            │     ├─ for anchor in (biz, article_key): scalar_one_or_none (kb.py:343-352)
            │     └─ Source.url.like(f"%{article_key}%") scalar_one_or_none (kb.py:354-361)  ★P0-1b 多源即 MultipleResultsFound
            ├─ asset_repo.get_by_source_external(source.id, article_key) (kb.py:241)  ★"s" 命中首篇资产 ⇒ hitCache 冒名
            ├─ get_by_url_fragment(source.id, article_key) (kb.py:245 → asset.py:36)  ★片段 "s" 几乎匹配任何 URL
            ├─ _resolve_with_retry → 抽取 → 质量门 (kb.py:265-271)
            ├─ _save_short_link(short_key, _article_key(article.url)) (kb.py:274-278)   ★映射目标也可能是 "s"

                                   唯一约束 uq_asset_source_external(source_id, external_id) (entities.py:144)
```

**根因**：键函数 `_article_key`（kb.py:554-557）用“去 query 取末段”定义文章身份。它对短链（`/s/{token}`）成立，对长链（`/s?__biz=…&mid=…&idx=…`）退化为常量 `"s"`。所有以 `article_key` 为锚的读（缓存命中、版本管理、源锚定、URL 片段兜底）与写（资产唯一约束、短链映射）全部继承这个退化。
**为何 S2.1.3 没有修好它**：S2.1.3 只修了 `_biz_from_url`（源锚的第一候选），没有触碰 `article_key`。P-3 读数 `fetch_count=1 B.hitCache=True` 在 65f508b 原样复现，证明修复面不覆盖缺陷面。
**修复点（最小充分）**：① `canonical_article_key(url)` 建立在 `parse_wechat_url`（article_identity.py:54）之上；② 6 个调用点改委托（kb.py:235/:276/:426/:432/:471 与 batch_ingest.py:44/:137）；③ 删除 LIKE 兜底；④ `get_by_url_fragment` 对短片段拒绝；⑤ 历史裸 token 键只读兼容。

**根因**：清单层与资产层各自定义“文章身份”，中间没有共享键也没有外键；清单状态机只有一个状态（DISCOVERED）。
**修复点**：清单行契约（`WorkListRow.id` 必填，无上游 id 时 = 规范键）；`article_manifests.article_key` 列 + `job_items.manifest_id`；Diff 改按 `article_key`；`DISCOVERED → ENQUEUED → INGESTED/FAILED` 状态机与 stale 回退。

### 2.3 静默性（为什么 P0 长期没人发现）

- 告警只有三类：心跳缺失、Job 积压、推送连败（alerting.py:71/:81/:87）；指标六族无采集维度（metrics.py:55-80）。
- `_map_row → None` 不计数、不打日志；整页丢弃对外表现为“这一轮没有新文章”，与正常空轮询不可区分。
- 因此 STEP-05 的价值不是“多一个面板”，而是让 P0-3 这一类缺陷**下次在一天内被告警发现**。

## 4. 关键取舍（辩证）

| 议题 | 方案 A | 方案 B | 选择与理由 |
|---|---|---|---|
| 键格式（D-V2-01） | `b:{biz}:{mid}:{idx}` / `s:{token}` / `h:{sha256[:32]}` | 无前缀 `{biz}_{mid}_{idx}` / `{token}` / `{hash}` | **A**：前缀让三种来源永不碰撞、可被正则校验（契约 `ArticleKey.pattern`），存量裸 token 与新键可区分，回填可幂等判断“已迁/未迁”。代价：外部若有人按裸 token 查询需适配——仓内只有 kb/batch_ingest 两处消费方，可控 |
| 存量资产 | 迁移内回填 | 迁移只做 DDL，回填走脚本 + 人批 | **B**：迁移不依赖应用代码；生产规模未知（U-02/03）需先只读审计 |
| 清单对齐 | 改 manifest.external_id 为规范键 | 新增 `article_key` 列，保留渠道 id | **新增列**：渠道 id 仍是上游翻页/去重依据，不能丢 |
| 证明脚本 | 继续维护 | 判据迁 pytest，脚本归档 | **迁 pytest**：唯一能进 CI、能被变异反证、换机可跑的载体；禁 `git rm` 约束下以 README 标注归档 |
| 复审轮次 | 不设上限 | ≤2 轮熔断 | **≤2 轮**：S2.1.3 第 3–10 轮未改变任何业务结论（被证对象 3 行未变）；第 3 轮起应转为新卡或升档 |
| 性能优化 | 预先加索引/批量 upsert | 先测基线（STEP-11）再定 | **先测**：禁止无基线优化；但 STEP-04 的新索引 `ix_manifest_source_article_key` 属于正确性配套，随迁移一起加 |
| 扩展性 | 每个渠道各自适配 | 统一 `WorkListRow` 行契约 + 渠道注册表 `ChannelSpec` | **统一契约**：新增渠道 = 实现一个返回 `WorkListRow` 的 provider + 注册一条 spec + 参数化契约测试自动覆盖（STEP-03/08） |
