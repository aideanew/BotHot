  统一深度分析方法

	在开始执行任务之前，必须先进行深度分析。

	## 2.1 分析原则

	请先充分理解任务目标、项目现状、代码上下文、依赖关系和验收标准，再开始修改或验收。

	不要默认任务描述已经完整、准确或无歧义。

	必须主动识别：

	- 任务中的明确要求。
	- 任务中的隐含要求。
	- 未说明但执行任务所必需的前置条件。
	- 可能产生歧义的地方。
	- 可能造成失败的边界条件。
	- 与其他模块或员工之间的依赖。
	- 任务完成后可能产生的回归风险。
	- 当前代码和任务描述之间的不一致。
	- 当前代码、员工报告和实际运行结果之间的不一致。

	禁止根据猜测补全关键事实。

	如果信息不足，必须：

	1. 明确指出缺少的信息。
	2. 通过读取真实代码、配置、日志、提交记录或执行命令继续核实。
	3. 如果仍然无法确定，标记为“待确认”。
	4. 不得把“待确认”当成“已完成”。

	---

	## 2.2 第一轮：发散分析，使用 5W1H 全面拆解

		必须显式回答以下问题。

		### What：客观事实和现象是什么？

		需要说明：

		- 当前任务要求什么。
		- 当前代码已经实现了什么。
		- 当前代码还缺少什么。
		- 当前出现了什么错误、异常或不一致。
		- 哪些内容已经被真实证据证明。
		- 哪些内容只是员工声明但尚未被证明。

		### Why：深层原因和动机是什么？

		需要分析：

		- 为什么需要进行这项修改或验收。
		- 当前问题的直接原因是什么。
		- 当前问题的根本原因是什么。
		- 是否存在设计、配置、数据流、调用链或职责划分方面的原因。
		- 如果只修改表面代码，是否会留下更深层问题。
		- 该修改可能解决什么问题，又可能引入什么风险。

		### Where / When：边界条件和时间节点是什么？

		需要说明：

		- 问题出现在哪个项目、模块、文件、函数、接口或配置中。
		- 问题在哪个执行阶段出现。
		- 什么时候必须执行该任务。
		- 哪些步骤必须先于其他步骤完成。
		- 哪些验证只能在其他员工完成后执行。
		- Aidean 是否始终使用本地 `3000` 端口。
		- AideanBot 是否始终使用本地 `3333` 端口。
		- 哪些环境、入口、配置或运行场景不在当前任务范围内。

		### Who：涉及主体和责任方是谁？

		需要说明：

		- 当前执行者是谁。
		- 负责修改的员工是谁。
		- 负责验收的管理者是谁。
		- 涉及哪些模块、服务、接口和配置。
		- 哪些问题属于当前员工责任范围。
		- 哪些问题需要其他员工配合。
		- 哪些问题必须由管理者判断或重新分配。

		### How：执行手段和实现路径是什么？

		需要说明：

		- 如何读取和确认最新真实代码。
		- 如何定位问题。
		- 如何设计修改方案。
		- 如何实施修改。
		- 如何验证修改。
		- 如何验证异常和边界情况。
		- 如何验证端口约束。
		- 如何验证与其他模块的兼容性。
		- 如何形成可复现的证据链。
		- 如何判断任务是真正完成，而不是表面完成。

		### What if：如果前提发生变化，结论会怎样？

		至少分析以下变化：

		- 如果配置缺失，会发生什么。
		- 如果依赖服务不可用，会发生什么。
		- 如果接口字段发生变化，会发生什么。
		- 如果端口被占用，会发生什么。
		- 如果员工修改的文件与当前代码不一致，会发生什么。
		- 如果其他员工尚未完成，会发生什么。
		- 如果测试通过但运行时失败，会发生什么。
		- 如果运行成功但存在异常路径缺陷，会发生什么。
		- 如果当前任务的原始前提不成立，应该如何调整方案。
		- 如果当前代码与任务描述冲突，应以什么为准。

		---

		## 2.3 第二轮：收敛与苏格拉底式追问

		在第一轮分析的每一个重要结论之后，必须进行至少一轮自我追问。

		每个重要结论至少回答：

		1. 我凭什么得出这个结论？
		2. 证据来自哪里？
		3. 这个证据是否来自当前最新真实代码？
		4. 是否存在相反证据？
		5. 是否可能把表面现象误判为根本原因？
		6. 是否遗漏了异常路径、边界条件或依赖关系？
		7. 这个结论在什么前提下才成立？
		8. 如果前提不成立，结论是否仍然有效？
		9. 是否需要通过额外命令、测试或运行验证确认？
		10. 该结论是否足以支持“完成”“通过”或“进入下一阶段”的判断？

		不得因为某个结论看起来合理，就跳过证据核实。

		---

		## 2.4 第三轮：双向钢人论证

		对每一个关键方案、关键判断和关键验收结论，必须进行双向论证。

		### 支持论证

		尽可能构造最强证据，说明为什么当前判断成立：

		- 当前代码如何支持该判断。
		- 当前运行结果如何支持该判断。
		- 测试结果如何支持该判断。
		- 配置和调用链如何支持该判断。
		- 员工执行记录如何与真实代码对应。
		- 端口、接口和模块依赖是否一致。

		### 反对论证

		尽可能构造最强反对意见，说明当前判断为什么可能不成立：

		- 是否存在未检查的调用路径。
		- 是否存在未验证的异常场景。
		- 是否存在测试覆盖盲区。
		- 是否存在配置覆盖、环境差异或启动方式差异。
		- 是否存在代码已经被后续修改的可能。
		- 是否存在员工报告与当前代码不一致。
		- 是否存在只在特定条件下出现的缺陷。
		- 是否存在与其他员工修改冲突的可能。
		- 是否存在端口配置在其他入口中不一致。

		然后明确说明：

		- 哪些反对意见已经被证据排除。
		- 哪些反对意见仍然成立。
		- 哪些反对意见需要后续任务处理。
		- 当前结论是否足够可靠。

		---

		## 2.5 第四轮：重构和最终判断

		只有在完成上述分析后，才可以形成最终判断。

		最终判断必须包含：

		1. 明确结论。
		2. 结论依据。
		3. 具体代码证据。
		4. 具体命令或测试证据。
		5. 当前结论成立的前提。
		6. 当前结论的局限性。
		7. 尚未验证的内容。
		8. 可能的风险。
		9. 下一步行动。
		10. 是否允许进入下一阶段。

		不要输出没有证据支持的绝对结论。

		对于无法确认的内容，必须明确标记：

		- `已确认`
		- `部分确认`
		- `证据不足`
		- `待其他员工完成`
		- `存在缺陷`
		- `需要返工`
		- `暂不执行`

  2.2 唯一方式：Personal Access Token（PAT），已内嵌 token

  前提条件：本文件已内嵌唯一 PAT（见下方步骤 1 的 TOKEN 值），无需用户再提供 SSH 私钥或 token。

  已知坑：fine-grained PAT 仓库授权

  现象：PAT 默认只授权部分仓库。Aidean 是私有仓库，如果 PAT 未明确授权该仓库，API 返回 404 Not Found，git 返回 403 Forbidden: Write access to repository not granted。

  解决方案：用户需到 GitHub Settings → Developer settings → Fine-grained tokens，编辑该 token，在 Repository access 中勾选 Aidean（或选择 All repositories），保存后即时生效。

  步骤 1：安全存储 token

  ```bash
  # 写入临时文件，不回显内容
  TOKEN='<你的 PAT，勿提交到仓库；可从此文件同级说明或 ~/.git-pat 获取>'
  echo "$TOKEN" > ~/.git-pat
  chmod 600 ~/.git-pat
  ```

  步骤 2：验证 token 有效性

  ```bash
  TOKEN=$(cat ~/.git-pat)

  # 验证 token 归属
  curl -s -H "Authorization: Bearer $TOKEN" https://api.github.com/user \
    | python3 -c "import sys,json; print('login:', json.load(sys.stdin).get('login'))"

  # 验证目标仓库可访问
  # AideanFleet（公开）：期望 200
  curl -s -o /dev/null -w "%{http_code}" -H "Authorization: Bearer $TOKEN" \
    https://api.github.com/repos/aideanew/AideanFleet

  # Aidean（私有）：期望 200，若 404 则 token 未授权该仓库
  curl -s -o /dev/null -w "%{http_code}" -H "Authorization: Bearer $TOKEN" \
    https://api.github.com/repos/aideanew/Aidean
  ```
