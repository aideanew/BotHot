## 2. 辩证统一：四对矛盾
1. **「已实现」与「已完成」**：R0/16 代码落了，但门禁红、真库没跑。统一点：完成 = 实现 + 当前基线读数。故 V0.8.0 新增 STEP-RV 专做验收，而不是把两卡划掉。
2. **「测试严」与「测试真」**：`test_url_fragment_query_is_source_scoped_like` 的意图（钉住按源过滤、单行、通配）是对的，写法使它对正确实现恒红。严格如果不可满足就等于噪声。修法是让断言可满足（`literal_binds`），不是删断言、更不是改产品代码去迎合。
3. **「证据多」与「证据可信」**：evidence 脚本从 8,383 涨到 9,519 行，gitleaks 命中也随之增加——证据件本身成了安全债。统一点：判据进 pytest（00T），证据件只留结果，且入库前过 gitleaks（G-PLAN）。
4. **「规划方亲做 UI」与「本轮只出规划」**：用户要求核心/UI 由规划方完成；本轮任务是规划。统一点：本版把 UI 卡写到可直接开工的粒度，执行归属标「规划方」，启动条件仅剩 D-V3-00 一个签字。

## 3. 根因链（当前基线）
- **RC-1 CI 红** ← 测试记录器渲染方式与断言口径不一致（F-04）← 该测试在第十四–十六轮复审中多次改写，但提交前未全量实跑 ← 本机无 PG 时 421 条 skip，执行者习惯于「看 passed」。
- **RC-2 Security 红** ← gitleaks 无 allowlist（F-11）← 历史证据件与规划文档中出现 DSN/密钥形字面量（F-10）← 规划流程无入库前扫描门。
- **RC-3 管理端「有 API 无前端」**（F-15）← 前端没有统一契约层，页面各自手写 fetch ← UI 卡长期排在 M4/M5。
- **RC-4 引擎能力面空洞**（F-14）← ADR-0004 设计了可插拔端口但只实接一个引擎 ← 需求 REQ-F-003 未裁决范围（D-V3-03）。
- **RC-5 性能 SLA 无基线** ← 无测量卡执行。

## 4. 全方位设计要点
| 维度 | 设计 | 落卡 |
|---|---|---|
| 前端 | 统一 `lib/api/admin/*` 契约客户端（由 contracts 生成类型），页面只消费 hook；管理端 4 屏：推送、运维存活、发现渠道、引擎密钥（+告警状态条） | 15、14b |
| 后端 | 分页统一为 V0.7.0 冻结的目标壳（`items/total/page/page_size`），offset 端点加兼容层不破旧客户端 | 14a |

| 交互 | 每屏四态（加载/空/错误/成功）遵 `ux_states.schema.json`；危险操作统一 `ConfirmModal` | 14b |

| 配置 | 告警/限流默认姿态已落，补 `/ready` 契约测试与文档 | RV、16 |
| 知识库 | 资产身份键（source_id, external_id）唯一；URL LIKE 仅作长度≥8 的兼容兜底 | 02、10 |
| 响应 | 统一 envelope 与错误码（`api.envelope`、`errors.global`） | 01、14a |
| 存储/资源 | 证据件瘦身、`.coverage/.venv` 等不入库；gitleaks 零新增 | 00S、00T、00G |
