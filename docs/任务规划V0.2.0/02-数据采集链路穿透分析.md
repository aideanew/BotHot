# 02 数据采集链路穿透分析

> 阅读约定：`文件:行` 以 `61739f0` 为准；每条缺陷给出**符号锚 + 复算命令 + 探针/测试实证**三件套。
> 结论分级：**实证**（本轮跑出来的）／**代码推断**（读代码可确定，未运行）／**待活体**（依赖外部系统）。

## 2.1 全链路执行逻辑（自顶向下）

```
[入口 A] 单篇入库 POST /spaces/{id}/docs ─────────────┐
[入口 B] 批量入库 batch_ingest → Job(batch) ───────────┤
[入口 C] 订阅 POST /subscriptions → Job(sync_account) ─┤
[入口 D] IncrementalScheduler.run_once（常驻）          │
   │ claim_due(FOR UPDATE SKIP LOCKED)                  │
   │ make_default_sync_runner → resolve_default_channel │  ← 全局唯一默认渠道
   │   ManifestSyncService.sync_source(source_id, Source.external_id=biz)
   │     provider.query_work_list(biz, page) → rows     │  ← 标识体系在此错位（D-05）
   │     _map_row(row) → ArticleManifest(DISCOVERED)     │  ← 行契约在此断裂（D-03/D-04）
   │   SourceSubscriptionService.run_incremental_sync   │
   │     _compute_new_manifests（DISCOVERED − READY 资产 − 在途）← 键失配（D-02）
   │     _create_sync_job → JobItem(external_id=workUuid, url)
   ▼                                                    ▼
JobWorker._drain_items → make_default_ingest → KnowledgeBaseService.ingest_url(space, url)
   normalize_article_url（ALLOWED_HOSTS={"mp.weixin.qq.com"}）← RSS 外链在此被拒（D-07）
   _article_key(url)  ← 长链坍缩为 "s"（D-01）
   _find_source_by_anchor(_biz_from_url, article_key) ← 读 "biz" 不读 "__biz"；LIKE '%s%'（D-01b）
   先查后抓：get_by_source_external / get_by_url_fragment → 命中 READY 即复用（冒名顶替）
   未命中 → _resolve_with_retry → WechatArticleFetcher.fetch（免费直抓）
            （ArticleDetailFallbackCoordinator 本应在此兜底——零调用方，D-08）
   ExtractorService → normalize → score_quality → _persist_document
     _ensure_source(biz) → upsert_content(source_id, external_id=_article_key(url)) → Document INDEXED
     on_article_indexed → FeedItem + new_article 事件（推送/热点下游）
```

## 2.2 缺陷证据链

### D-01【P0｜实证】长链 `article_key` 坍缩为 `"s"`，同号后续文章被首篇缓存冒名顶替

- **符号锚**：`services/kb.py::_article_key`（`:554`）`re.sub(r"[?&#].*$", "", url).rstrip("/").rsplit("/", 1)[-1]`
- **执行逻辑**：长链 `https://mp.weixin.qq.com/s?__biz=X&mid=M&idx=I&sn=S` 去掉 query 后为 `…/s`，末段恒为 `"s"`。
  同一公众号所有长链文章的资产键都是 `(source_id, "s")`，而唯一约束 `uq_asset_source_external`（`models/entities.py:144`）让它们只能存一行。
- **后果路径**：第 2 篇进入 `ingest_url` → 先查后抓 `get_by_source_external(source.id, "s")`（`kb.py:241`）命中第 1 篇 READY 资产 → `hitCache=True` 直接返回第 1 篇的 doc，**第 2 篇永远不会被抓取**。
- **复算**：`.venv/bin/python -c "from app.services.kb import _article_key as k; print(k('https://mp.weixin.qq.com/s?__biz=X&mid=1&idx=1&sn=a'))"` → `s`
- **探针 P-3 实证**：`PROBE fetch_count= 1 A.hitCache= False B.hitCache= True same_doc= True`（`evidence/probe_longlink_collision.py`）
- **为何测试没抓到**：`tests/test_p0_asset_cache.py:26` 的 `URL_A` 用的是 `/s/p0-cache-001?biz=…` 短链形态 + 非真实参数名 `biz`；全库无一条用两篇不同长链做入库的测试（`grep -rn "mid=.*idx=.*sn=" tests/` 仅 `test_resolver.py` 命中且不走 `ingest_url`）。
- **波及**：`ShortLinkMap.article_key`（`kb.py:276` `final_key = _article_key(article.url)`）——若短链直抓跳转到长链（U-03），映射也会写成 `"s"`。

### D-01b【P0｜实证】库内 ≥2 个 source 时，长链入库直接崩溃（MultipleResultsFound）

- **符号锚**：`services/kb.py::_biz_from_url`（`:587`）读 `qs.get("biz")`，微信长链参数名是 `__biz` ⇒ 恒为空串；
  `services/kb.py::_find_source_by_anchor`（`:336`）兜底 `Source.url.like(f"%{article_key}%")` 在 `article_key="s"` 时等价于"URL 含字母 s"，配合 `scalar_one_or_none()`。
- **执行逻辑**：biz 锚为空 → 以 `"s"` 精确查 source 不中 → LIKE `'%s%'` 命中所有 `https://…` 源 → 多行 → 抛 `MultipleResultsFound` → 入库 500。
  单 source 时不崩但会把文章错挂到那唯一的 source 上（D-01 的冒名路径正是经由这里）。
- **探针 P-4 实证**：`PROBE2 EXC MultipleResultsFound Multiple rows were found when one or none was required`（`evidence/probe_multisource_crash.py`）
- **影响面**：所有长链来源——JustOneAPI `ContentUrl`、TikHub `content_url`、Wellbyte `ContentUrl`、用户手贴长链；RedFox 取决于 U-01。

### D-02【P0｜实证】Manifest 键与 Asset 键失配 ⇒ 已入库篇被反复重新入列

- **符号锚**：`ArticleManifest.external_id = workUuid`（`models/entities.py:108` 注释、`manifest.py::_map_row`）；`ContentAsset.external_id = _article_key(url)`（`kb.py:432`）；
  Diff：`subscription.py::_compute_new_manifests`（`:796`）`ArticleManifest.external_id.not_in(select(ContentAsset.external_id)…)`。
- **执行逻辑**：两侧键空间不同（32 位 hex vs URL 末段），"− 已 READY 资产"永远减不掉任何行；只剩"− 在途 Job"一项生效。
  于是 Job 一旦进入终态（SUCCEEDED/PARTIAL/FAILED），下一轮该订阅的**全部历史 DISCOVERED 清单**重新入列；且 `new_count>0` 使 `consecutive_empty_syncs` 归零，空轮询退避（`scheduler.py::backoff_multiplier`）永不生效。
- **代价**：每订阅每轮新建一个 Job + N 个 JobItem（N=该号历史总篇数，随时间单调增长）；worker 每篇走一次 `ingest_url`（命中缓存时 0 微信请求，但仍有 DB 往返与 KB `_reuse_cached_asset`）；`ArticleManifest.status` 全库无任何代码把它从 `DISCOVERED` 推进（`grep -rn "MANIFEST_STATUS\|manifest.status" app/` 仅定义处）。
- **探针 P-2 实证**：`manifest.external_id= aaaa…e8da5e62 asset.external_id= RealTokene8da5e62 / 已 READY 入库后 Diff 仍判为新增篇数 = 1`（`evidence/probe_reenqueue_loop.py`）
- **为何测试没抓到**：`tests/test_scheduler.py::_seed_manifests`（`:188`）把 `external_id=ext` 且 `url=f"https://mp.weixin.qq.com/s/{ext}"`，使 `_article_key(url) == external_id` **恰好相等**；`:530` 处再直接用 `external_id=ext` 造 READY 资产——测试按"两键相同"的假设构造数据，等于把缺陷写进了夹具。
- **违反需求**：REQ-F-006 验收"增量同步只拉新文章，水位正确推进"。

### D-03【P0｜实证】4 家付费源的清单行没有 id ⇒ 发现产出恒为 0

- **符号锚**：`manifest.py::_ID_KEYS = ("workUuid","work_uuid","uuid","id","articleId","article_id")`（`:51`）；
  `dajiala.py` 行 = `{url,title,digest,publish_time}`（`:111-119`），`justoneapi.py:135-143`、`tikhub.py:140-148`、`wellbyte.py:155-162` 同形——**都不含上述任何 id 键**。
- **执行逻辑**：`_map_row` 取不到 `external_id` → 返回 None → `report.skipped += 1`；整页全 skip 时 `saw_existing=False`、`len(rows)<20` → 循环结束，日志 `new=0 … skip=N`，**无告警**。
- **探针 P-1 实证**：`dajiala -> None`、`justoneapi -> None`、`redfox -> {...}`（`evidence/probe_row_mapping.py`）
- **矛盾的文档陈述**：`providers/article_sources/base.py:56` 注释"行字段经 manifest._map_row 的别名消化"；AGENTS.md "文章来源：4 平台已接入"；registry 各渠道 `implemented=True`。
- **触发条件**：`DISCOVERY_DEFAULT_CHANNEL` 设为非 redfox，或 redfox 无 key 而其他渠道有 key（`registry.py::resolve_default_channel` 回落注册序）。见 U-05。

### D-04【P1｜实证】RSS 2.0 `pubDate`（RFC 822）解析恒为 None

- **符号锚**：`rss.py::_extract_rss_item` 原样透传 `"publishTime": pub_date`（`:221`）；`manifest.py::_parse_time` 只用 `datetime.fromisoformat`（`:114`）。
- **实证**：`datetime.fromisoformat('Mon, 12 Oct 2026 07:00:00 +0000')` → `Invalid isoformat string`；探针 P-1：`rss -> publish_time: None`，Atom（ISO 8601）正常。
- **测试缺口**：`tests/test_rss_provider.py::test_parse_rss2_pubdate` 只断言原始字符串被保留，未断言经 `_map_row` 后的时间。
- **下游影响**：清单排序（`order_by(created_at)` 不受影响），但任何依赖 `publish_time` 的展示/热点时间衰减拿不到发布时间。

### D-05【P1｜代码推断】标识体系错位：全局单一渠道 × `Source.external_id` 只存 biz

- **符号锚**：`scheduler.py::make_sync_runner` 传 `src.external_id`（`:138-140`）；`Source.external_id` 注释"公众号 biz"（`entities.py:62`）；
  各 provider 期待：RedFox=biz、Dajiala/JustOneAPI/TikHub=ghid（`dajiala.py:85`、`justoneapi.py:92`、`tikhub.py:93`）、Wellbyte=文章 URL（`wellbyte.py:108`）、RSS=feed URL/别名（`rss.py:85-97`）。
- **执行逻辑**：渠道是**进程级**选择（`make_default_sync_runner` 在调度器启动时装配一次），所有订阅共用；把 biz 传给要 ghid 的上游 = 参数错误；传给 RSS 时 `_resolve_feed_url` 不认识就"当作 URL 直接用"（`rss.py:97`），httpx 报错后**静默返回空**（`rss.py:115-117`）。
- **数据模型缺口**：全库无 `ghid` 字段（`grep -rn ghid app/models` 为空），无 biz→ghid 映射；Wellbyte 文档称"传文章 URL 即免费返回 gh_"（registry `verified_scope`），是唯一零成本映射路径，但未被利用。
- **结论**：即便修好 D-03，非 RedFox 渠道也无法对现有订阅工作，必须引入"按源标识 + 按能力路由"。

### D-06【P1｜代码推断】分页语义不一致，回填能力被静默截断

- Dajiala `post_condition` 只返回最新 4 条、`page>1` 返回空（`dajiala.py:86-92`）；JustOneAPI 用 Offset 游标但 `page>1` 直接返回空（`justoneapi.py:99-102`，注释"需上页 Offset，无法预构"）；RSS `page>1` 返回空。
- `ManifestSyncService` 以 RedFox 的 `PAGE_SIZE`（20）判"末页"（`manifest.py::_upstream_page_size`）。对 JustOneAPI（10 条/页）首页即被判末页 → 首次订阅只回填 10 篇。
- **结论**：`WorkListProvider` 协议 `(biz, page)` 形状无法表达游标分页；需要协议升级为"游标 + 每源页大小"。

### D-07【P1｜代码推断】RSS 渠道只能发现、不能入库（非微信外链）

- `source_resolver.py::ALLOWED_HOSTS = {"mp.weixin.qq.com"}`（`:24`）；`normalize_article_url` 对其他域名抛 `MalformedUrlError`（`:61-62`）。
- `JobWorker._is_permanent_error` 不含 `MalformedUrlError`（`job_worker.py:100-107` 只列 `SourceUrlUnrecognizedError | ExtractQualityLowError`）⇒ 外链会被**重试到上限**再失败，白耗退避时间。已核：`MalformedUrlError(AppError)`（`core/errors.py:89`）与 `SourceUrlUnrecognizedError(AppError)`（`:124`）是兄弟类、无继承关系；`kb.py::_resolve_with_retry` 只对后两者直接上抛（`:328-329`），其余 `except Exception` 一律重试（`:330`）⇒ 单篇内重试 + worker 层重试双重放大。
- 文档 `docs/RSS订阅渠道.md` 预置的新闻/科技源（新华网、阮一峰、V2EX…）全部是外链 ⇒ 按文档配置后入库 100% 失败。
- `Source.type` 仅 `wechat_oa`（`entities.py:56` 注释），RSS feed 无法成为订阅对象。

### D-08【P1｜实证】详情兜底协调器生产零调用方

- `services/article_detail_fallback.py::ArticleDetailFallbackCoordinator` 覆盖率 **0%**；`grep -rn "article_detail_fallback\|ArticleDetailFallbackCoordinator" app/ | grep -v article_detail_fallback.py` 只命中 `core/config.py:110` 的开关定义。
- 与 AGENTS.md "详情兜底协调器按成本排序" 的现状陈述矛盾（文档写成已生效）。
- 接入点应在 `kb.py::_resolve_with_retry` 失败分支与 `ExtractQualityLowError` 分支，且须排除图集（`source_resolver.py::is_gallery_type`）。

### D-09【P1｜代码推断】付费调用无预算护栏

- `grep -rln "budget\|quota\|cost_limit" app/` 为空。调度器并发 4、每订阅每轮至少 1 次付费调用；D-02 的重复入列不额外触发付费发现，但 STEP-06 接入付费兜底后，若无日预算，一次上游故障（直抓全失败）会把每篇都推到付费详情。

### D-10【P2｜代码推断】清单写入 N+1

- `ManifestSyncService._upsert` 每行一次 `SELECT` + 一次 `SAVEPOINT flush`（`manifest.py:251-266`），20 行/页 ⇒ ≥40 次往返。可改 `INSERT … ON CONFLICT (source_id, external_id) DO UPDATE … RETURNING (xmax = 0)` 一次完成并区分新增/更新。

### D-11【P2｜代码推断】`Job.idempotency_key LIKE 'sync_account:{sub}%'` 的索引可用性

- `jobs.idempotency_key` 有唯一索引（`entities.py:202`），但 PG 默认排序规则下 btree 不服务 `LIKE 'prefix%'`（需 `text_pattern_ops` 或 `C` collation）。`_compute_new_manifests` 每轮都执行该子查询 ⇒ 随 Job 表增长（D-02 会放大）退化为顺扫。需 `EXPLAIN` 证实（STEP-08.2）。

### D-12【P2｜实证】测试环境两处脆弱点

- `tests/conftest.py:36` 默认 DSN 指向 `localhost:5433/bothot`（生产形态库，含口令字面量），仅告警不拒绝 ⇒ 未设 `AIDEANBOT_TEST_PG_DSN` 时测试会写生产形态库（文件内 D23 注释已承认风险）。
- `test_w3_push_scheduler.py::test_event_delivery_failure_no_reclaim` 依赖 `localhost:9999` 空闲（见 01 §1.2.1）。

### D-13【P2｜代码推断】发现渠道失败无降级链

- `resolve_default_channel` 只选一个渠道；该渠道抛 `DiscoveryFailedError`（如 RedFox 3201 积分不足）时，`scheduler._process_one` 回滚并按基准间隔推进水位（`:530-537`），**不会尝试其他已配置渠道**。

### D-14【P2｜实证】`/admin/discovery/channels` 无前端消费方

- 后端 `api/v1/admin.py:467`；`grep -rln "discovery" apps/web --include=*.ts*` 为空。运营无法在后台看到"为什么没在发现"。

### D-15【P2｜代码推断】TikHub 发现端点疑似已下线

- 见 01 §1.4 U-04。代码 `tikhub.py:114` 调 `…/web/fetch_account_articles`，registry 自述 web/* 已 404。

### D-16【P1｜实证，承 V0.1.0 G-21】定时 web 通知全部广播

- 采集 → `on_article_indexed` → `new_article` 事件 → `PushTaskScheduler` → web provider：调度侧 `PushMessage` 不设 `external_user_id`，`persist_web_notification` 恒 `is_broadcast=True`（`push_scheduler.py:277-291` 的判定逻辑本身正确，问题在上游构造）。采集产生的通知会被所有登录用户看到。

## 2.3 缺陷之间的耦合（修复顺序的依据）

```
D-01 (article_key) ──┬─► D-01b（同根：长链键为 "s" 才触发 LIKE '%s%'）
                     └─► D-02（Diff 若改用 article_key 对齐，必须先让 article_key 正确）
D-03 (行无 id) ──────► 修法依赖 D-01：缺 id 时以 canonical article_key 充当 external_id
D-05 (标识体系) ─────► 依赖 D-03（行可用）+ 数据模型变更（source_identifiers）
D-06 (分页) ─────────► 与 D-05 同改 WorkListProvider 协议，合并为一次协议升级
D-07 (RSS 入库) ─────► 依赖 D-05（Source.type=rss）+ 产品裁决 C-03
D-08/D-09 (兜底+预算) ► 依赖 D-01（兜底结果按正确键落库）
```

**唯一合理的起点是 D-01**：它是 D-01b/D-02/D-03 修法的共同前提，且影响用户手贴长链这条最短路径。
