## 3.3 关键决策的辩证分析

### C-01 canonical article key 用什么？（STEP-01）

- **方案 A：`{biz}:{mid}:{idx}`（长链）/ `s:{token}`（短链）**
  - 正：微信文章的天然主键就是 (biz, mid, idx)；与 URL 形态（`sn`、`chksm`、`scene` 等追踪参数）解耦；同一篇的长链变体全部收敛。
  - 反：短链 `/s/<token>` 与同篇长链是两个不同键，仍需 `ShortLinkMap` 桥接（现有机制，可复用）；`mid/idx` 缺失的畸形长链需降级。
- **方案 B：直接用 `sn`**
  - 正：单字段、无需 biz。
  - 反：`sn` 是签名，不同分享场景下是否稳定**无仓库内证据**；违反"禁止猜测"。
- **方案 C：完整规范化 URL 的 sha256**
  - 正：形态无关、实现最简。
  - 反：`sn/chksm/scene` 变化即换键 ⇒ 同篇多资产，重新引入重复。
- **裁定建议**：A，降级顺序 `__biz+mid+idx` → `/s/<token>` → `sha256(规范化URL)`，并把前缀（`b:`/`s:`/`h:`）写进键，保证三类键空间不相交。**需人批准（D-V2-01）**，因为它改变 `content_assets.external_id` 的语义并触发存量回填。

### C-02 Manifest 与 Asset 如何对齐？（STEP-02）

- **方案 A：Diff 改按 canonical article_key 对齐**（manifest 新增 `article_key` 列，写入时由 URL 计算）
  - 正：消除键空间错位的根因；与 Asset 同函数同口径。
  - 反：需迁移 + 回填；URL 缺失的清单行（`url=""`）无法算键。
- **方案 B：清单状态机**（ingest 成功后把 manifest 推进 `INGESTED`，Diff 只取 `DISCOVERED`）
  - 正：Diff 查询变成纯索引过滤，最快；状态可观测。
  - 反：需要 worker → manifest 的回写链路（JobItem 要能回指 manifest）；若回写失败会漏推进，仍需 A 作为兜底。
- **钢人论证"只做 B"**：B 更简单、性能更好。反驳：B 依赖 worker 正确回写，而回写本身可能因 D-01 写错键；A 是数据层不变量，B 是性能优化，二者不互斥。
- **裁定建议**：A + B 同做，A 为正确性、B 为性能；JobItem 增加 `manifest_id` 外键用于回写。

### C-03 RSS 外链要不要入库？（STEP-05）

- **正（入库）**：`docs/RSS订阅渠道.md` 已对外宣称新闻/科技源可用；热点聚簇需要多来源；`ExtractorService` 是通用 HTML 清洗器，理论可复用。
- **反（不入库）**：产品定位是"公众号"知识库（REQ-F-004 标题即"公众号链接入库"）；外链意味着 SSRF 面扩大（`ALLOWED_HOSTS` 是当前唯一的出站白名单）、版权与 robots 合规、通用正文抽取质量未经验证；工作量远大于其他 STEP。
- **折中**：V0.2.0 只做"RSS 作为**公众号镜像源**"（RSSHub/WeRSS/feeddd 这类输出 `mp.weixin.qq.com` 链接的 feed），外链在发现层即过滤并计数，不进入入库链；外链入库作为独立需求立项。
- **需人裁决（D-V2-03）**：是否接受折中；若要外链入库，需单独的 ADR（出站白名单策略 + 通用抽取器 + 合规）。

### C-04 渠道选择：全局默认 vs 按源路由？（STEP-04）

- **全局默认（现状）**：简单、可预测、成本可控。但与"各渠道标识体系不同"冲突（D-05），实际只有 RedFox 能工作。
- **按源路由**：每个 Source 记录自己拥有的标识（biz/ghid/sample_url/feed_url），按"渠道能力 ∩ 源已有标识 ∩ 启用白名单"排序选渠道，失败降级到下一个（解 D-13）。
  - 反：复杂度上升；多渠道意味着多计费口径，需要预算护栏（STEP-06）先就位才能放开降级。
- **裁定建议**：按源路由，但**降级默认关闭**（`discovery_fallback_enabled=False`），待 STEP-06 预算上线后再开。

### C-05 是否在 V0.2.0 内完成 V0.1.0 的 17 张阻塞卡？

- **正**：规划连续性；契约单一源（D-09）是长期价值。
- **反**：17 张卡全部卡在人工裁决上，裁决不来编码无法开始；且其中多数（错误码生成、响应 DTO）与采集正确性无关。
- **裁定**：V0.2.0 不承接这 17 张卡的实施，只在 STEP-10 列出"裁决即可开工"的清单；**例外**：TASK-001（安全）与 G-21（数据可见性）作为前置。

### C-06 存量数据：回填还是重抓？（STEP-01/02）

- 回填（按 `content_assets.url` 重算 canonical key）：零上游成本，但被 D-01 冒名的那些"本应存在的文章"在库里**根本没有行**，回填补不回来。
- 重抓：能补回丢失文章，但需要知道丢了哪些——只有 `article_manifests`（RedFox 路径）和 `job_items.url` 留有 URL 线索。
- **裁定**：先回填（修正已存在行的键），再用 `job_items`/`article_manifests` 中 URL 与资产 URL 的差集生成"补抓清单"，由运营决定是否重抓（免费直抓，非付费）。
