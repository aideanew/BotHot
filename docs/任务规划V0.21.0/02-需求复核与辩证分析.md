## 1. 复述

## 3. 分级
- **MUST**：M1 mock 表每条样例的形状由契约生成类型约束，写错一个字段 tsc 红（P-82/S37.4）。M2 后端真端点吐出的 `data` 与同一契约逐键一致（多键/缺键/类型错均红）。M3 不降任何覆盖率阈值、不动已有 tag。
- **SHOULD**：S1 SQL 参数化与 Cookie SameSite 各有一条断言。S2 门面版本声明与实值不一致即红。S3 需求表判词与证据同步。
- **COULD**：C1 后端逐路由加 `response_model`（让 OpenAPI 也带形状）——本版不做，见 §5 反证。
- **MUST NOT**：不实接四家引擎（D-V3-03）；不为 mock 档造 admin 会话（D-V21-06）；不改端口（D-V21-05）；STEP-41 未经用户同意不跑。

## 4. 5W1H（聚焦 P-82）
- **What**：前端 24 条 mock 样例与 `lib/api/*` 类型是手写的；后端吐什么没有任何机器在比。已抓到一处实锤漂移（P-119）。
- **Why**：契约链只覆盖到"持久层列"和"请求体"，"响应体"这一段一直空着；根因是路由返回裸 dict，OpenAPI 推不出形状。只改前端（`satisfies` 前端自己的类型）= 自己证明自己，治标。
- **Where/When**：后端 `app/contracts/<域>.py`；生成器 `scripts/gen_contracts.py`；前端 `lib/api/mock-routes.ts`、`lib/api/<域>.ts`。必须先有契约（46/47），再让前端 satisfies（48/52）。
- **Who**：契约语义是规划方（opus）；前端 satisfies 与类型对齐是执行助手（sonnet）。
- **How**：Pydantic 契约模型（唯一源，ADR-0008）→ JSON Schema（已有逐字节幂等门）→ **TS（本版新增派生，同一 --check 门）**；后端用 schema 校真端点 data；前端 `satisfies` 生成类型。
- **What if**：① 后端改了序列化没改契约 ⇒ 反向核用例红。② 改了契约没重生成 ⇒ gen --check 红。③ 前端样例不对 ⇒ tsc 红。④ 生成器遇到不认识的 schema 形状 ⇒ 立刻报错，不降级成 `unknown`（降级会让 satisfies 失牙）。⑤ 连库用例在 Windows skip ⇒ 已同步抬 `SKIP_BASELINE_WIN` 683→685。

## 5. 钢人论证：为什么不选"每个路由加 response_model"
- **支持它**：OpenAPI 自带形状，FastAPI 还会在运行时按模型过滤字段，一处声明两处受益。
- **反对它（采纳）**：① 24+ 路由的返回路径要改成返回模型对象，`JSONResponse(content=...)` 的写法会绕过 response_model，改动面覆盖几乎所有 API 文件，回归面大；② 运行时过滤会**静默丢掉**多出来的键，反而把"后端多吐了一个键"这种漂移藏起来，与本版要的"多一个键也红"相反；③ 现有 `app/contracts/` + schema 门 + 契约比对测试是成熟链路，增量最小。
- **结论**：契约模型 + 测试反向核；`response_model` 记为 COULD，不排期。

## 6. 钢人论证：P-119 改前端还是改契约
- 前端把 `decryptFailed`/`activeSource` 写成可选的理由是"旧后端不返回"。现读后端 `_engine_status` 恒返回这两个键（`test_p4_engines.py` 端点用例断言 `decryptFailed is False`、`activeSource is None`），且 v1.0.0 之后没有不带它们的后端版本在支持范围内。
- **结论（D-V21-02）**：以契约为准，前端类型改为别名契约类型、样例补齐两键。保留"可选"= 让 satisfies 对这两个键失牙。
