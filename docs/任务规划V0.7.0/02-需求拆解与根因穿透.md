# 02 需求拆解与根因穿透（main@13acacc）

## 1. 一句话复述项目要解决的问题
BotHot 是一个「公众号内容 → 采集/清单/入库 → 热点聚簇评分 → RAG 问答 → 多渠道推送 + 站内通知」的内容机器人平台；身份全部挂在主平台 SSO（`users.sub`），队列在 PostgreSQL，前端 Next.js 15 经同源 rewrites 打后端。用户此刻要的是：**把「还没实现的需求」查清楚，并给出一套能被 N 个互不通信的执行者并行领取的规划**。

## 5. 四条根因链（穿透到底层与关联板块）

### 5.1 短链回归链（M-1 为什么坏、为什么没被拦住）
```
078dc30 删 Source.url.like 兜底（kb.py:363 → return None）
   ↓ 该兜底实际服务两种场景，提交只论证了长链
   ├─ 长链 键="s" → LIKE 命中多行 → MultipleResultsFound（P-4）：删对了 ✅
   └─ 无参短链：首抓时 _ensure_source 用「页面 biz」建源（kb.py:471 external_id = biz or _article_key(url)）
                二次入库：短链 URL 解不出 biz（article_identity.py:77 只读 query 的 __biz/biz）⇒ 锚①空
                          article_key=token，对不上以 biz 为键的源 ⇒ 锚②空 ⇒ 锚③已删 ⇒ source=None
                → kb.py:240 整块缓存逻辑跳过 → 重抓（fetch_count=2）→ :301 assert 2==1
                附带：kb.py:281-288 stale 版本管理同样失效（它也依赖 source）
   ↓ 为什么三道防线都没响
   ├─ 执行机无依赖：连库用例在无 PG 时是 **skip 不是 fail**（conftest.py:106-107,125-126）⇒ 本机永远看不到
   ├─ 证明台（假会话 + AST）只证「代码向 DB 发了哪些查询」，证不了「删掉一条查询后别的路径还通不通」；
   │  且 REAL_DB_TARGETS（replay_s213.py:458-466）7 个靶里根本没有 test_be02_engine_routing.py
   └─ CI：backend job 红在 `ruff`（ci.yml:67 在 pytest 之前），pytest 已连续 22 次没执行
```
**根因不是「改得不好」**：078dc30 有先红用例、有边界测试、有 WARNING 留痕、P-4 判断正确。根因是**「没跑就合」+「替代证据的判据对象与风险不同域」**。故 R0 卡的修复方向（精确等值反查，不复活 LIKE）保留，但必须补 F-74 的两句假 docstring（否则下一个人还会被它骗），并把 F-75 的恒红判据换成 AF-S6 的 AST 判据。

### 5.2 未实现需求的遮蔽链（R-2 为什么上一轮没查到）
```
V0.6.0 全文只出现 REQ-F-004(3) / REQ-NF-001(1)
   ↓ 因为它的入口是「四个 P0 探针」，不是「需求清单」
   ↓ 需求清单里 9 条既无状态字段、backlog 也无对应条目（F-005/F-007 在 backlog 里 0 条）
   ↓ 需求目录 features/ non-functional/ constraints/ 只有 .gitkeep（coverage §1）
      ⇒ 任何按目录检索需求的动作都会返回空，于是「需求基线」在实践上退化成「探针清单」
结果：引擎域 16 处 NotImplementedError（F-78）、管理端 6 组端点无 UI（F-79）、
      四条性能 SLA 无度量锚（coverage §3）全部落在规划盲区。
```
**辩证结论**：V0.6.0 的深度是以**宽度**为代价换来的。它抓到的 P0 是真的（F-72 复现证明），但「12 条需求只覆盖 2 条」也是真的。V0.7.0 不再重复其深度，而是补宽度，并把深度作为已验证的前提继承。

## 6. 双向钢人论证（对本版关键判断）

### B-1 判断：「V0.7.0 应该转向补宽度，而不是继续深挖采集域」
- **支持**：F-77（2/12 覆盖）、F-78（16 处骨架）、F-79（0 消费面）、F-83（告警前提缺失）全部为实测；采集域四个 P0 中 3 个的修复路径已由 V0.6.0 写死到卡级，继续写只会产生 docs 增量。
- **最强反方**：采集域的 M0 回归还红着、CI 已 22 连红，此时铺开新战场会让两条线都烂尾；且「9 条无 STEP」里有多条其实是「已实现但未纳管」（F-002/F-005/F-007），补宽度可能只是在给已完成的东西补文档，边际价值低于修回归。
- **裁定**：两条都对，取合取——**M0（R0+00C+00G）仍是第一刀且不变**；补宽度部分**不与 M0 并行写代码**，而是先只做「验证 + 纳管」类卡（STEP-19/17），把真开发类（STEP-13 引擎实接、STEP-14 管理 UI）排在 M1 之后并标 BLOCKING。反方第二点被证据部分接受：故本版把 F-002/F-005/F-007 的需求条目处理定为「验证与纳管」而非「实现」。

### B-2 判断：「冻结并压缩证明脚本是正确方向」
- **支持**：F-65/F-67 分母为 0 而分子 +521；真实判据不进 CI 就不能防回归（§5.3）。
- **最强反方**：证明台是本项目唯一能抓「变异级缺陷」的手段，a576bc2 那一轮加靶确实发现了 3 个 MAJOR（交付门自己没靶就是真缺陷）；冻结行数会压制这种发现能力，可能把另一类缺陷换成可见的。
- **裁定**：反方**成立且不被排除**。因此本版不做「下线证明台」，而做「同一判据在 pytest 里存在一份 + CI 跑它」的**双轨迁移**（STEP-00T），冻结的是「只增证明脚本而不增 pytest 用例」这一单边行为；例外通道写死为「迁移与 gitleaks 修复」。此局限如实记入 05 §3。

### B-3 判断：「引擎域 16 处 NotImplementedError 判为未实现需求，而非技术债」
- **支持**：REQ-F-003 需求文本要求可插拔引擎；`engines.py:121-122` 只是拒绝切换，用户仍拿不到多引擎能力。
- **最强反方**：护栏诚实、无虚假宣传、无用户可感故障；实接 4 家外部引擎依赖密钥与预算（U 项未知），本轮硬排可能是空转。
- **裁定**：判为「需求未实现」属实，但**排期上降级**：D-V3-03 默认「本轮不实接」，STEP-13 只做「能力面可见化 + 需求文本与实现对齐 + 实接的前置契约」，把真实接交人裁决。

## 7. 隐含要求与前置条件（需求文档里没有、执行必需）
1. 执行者必须能**跑**连库套件；否则 M-1 类验收在本机不可判（F-88：无 PG 时 skip 不是 fail）→ 转 STEP-R0 R0.4.2 的 👤 前置。
2. `check_docs_consistency.py` 已在 CI 阻断（F-85）：它校验 backlog 路径存在 + 声称行号 ≤ 文件实际行数 ⇒ **规划/文档里的行号写错会直接把 CI 弄红**。本版所有行号均来自本轮实读，且 04 立规则「行号只作提示、判据必须给命令」。
3. 迁移必须**串行**：单头 `ab1005w5b`（实测 18 个版本文件、无人引用为 down_revision）。新迁移号顺序在 03 §7 冻结。
4. 前端任何「真实后端」验证都要显式关 mock（`NEXT_PUBLIC_API_MOCK=false`），否则默认演示态会静默不连 SSE（F-81/coverage §4）。
5. `gen_contracts --check` 是阻断步 ⇒ 改实体模型的提交**必须同提交**重生成 `packages/contracts/src/**`，否则 CI 红（V0.6.0 03 §3 已列，本版沿用）。
