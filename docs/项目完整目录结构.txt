# 第一部分：核心设计原则

## 1. 规范目标

### 1.1 本规范解决的问题

```text
AI CLI 只生成"可运行项目"，不生成"可持续演进的工程"。
两者的本质差距是：

可运行项目              可持续演进工程
─────────────────────────────────────────
能 npm run dev         有业务边界
没有职责边界           有职责边界
没有依赖方向           有依赖方向
没有模块归属           有模块归属
没有生命周期分类        有生命周期分类
没有 AI 修改约束        有 AI 修改约束
没有自动边界守卫        有自动边界守卫
```

### 1.2 本规范不负责定义

```text
具体编程语言语法
具体框架 API 使用方式
业务需求内容
团队协作流程（见 PROJECT-DOCUMENTATION-SPEC.md）
```

### 1.3 本规范与其他规范的关系

```text
PROJECT-DOCUMENTATION-SPEC.md
        │
        └── 项目的"知识、需求、计划、任务、证据"如何组织

PROJECT-STRUCTURE-SPEC.md（本文件）
        │
        └── 项目的"源码、模块、配置、测试、脚本、资产、生成物"如何组织

AGENTS.md
        │
        └── AI Agent 读取哪些规范、如何执行、修改前检查什么

ARCHITECTURE-GUARD（自动化守卫）
        │
        └── 将规范从"建议"变为"强制约束"的机器可验证机制
```

## 2. 第一原则：文件生命周期分类

### 2.1 五种文件类型（所有文件必须属于其中一类）

```text
┌──────────────────────┬────────────────────────────────────────┬──────────────┐
│ 类型                  │ 含义                                    │ 进入 Git？   │
├──────────────────────┼────────────────────────────────────────┼──────────────┤
│ Source               │ 源码、配置源码、迁移、测试源码            │ ✅ 必须      │
│ Specification        │ 文档、架构、需求、ADR、规范              │ ✅ 必须      │
│ Reproducible Input   │ fixtures、seed、schema、template        │ ✅ 通常      │
│ Generated Artifact   │ dist、build、coverage、logs、缓存       │ ❌ 默认不进  │
│ Local / Temporary    │ 调试日志、截图、临时脚本、AI 会话产物    │ ❌ 绝不进    │
└──────────────────────┴────────────────────────────────────────┴──────────────┘
```

### 2.2 文件创建前的归属判断流程

```text
准备创建一个新文件
        │
        ▼
它属于哪种生命周期类型？
        │
   ┌────┴──────────────────────────────────────────┐
   ▼           ▼            ▼           ▼           ▼
 Source   Specification  Reproducible Generated   Temporary
   │           │           Input         │           │
   ▼           ▼             │           ▼           ▼
按模块     docs/ 对应      按需归入    加入      .local/
归属规则   子目录          对应目录   .gitignore  或删除
   │
   ▼
它属于哪个业务域？
        │
   ┌────┴──────────┬──────────┬─────────┐
   ▼               ▼          ▼         ▼
 user/          order/    payment/  notification/
   │
   ▼
它在业务域内属于哪一层？
        │
   ┌────┴───────────────────┬──────────┐
   ▼          ▼             ▼          ▼
domain/  application/  interfaces/  infrastructure/

无法回答归属 → 不创建，先明确归属
```

## 3. 第二原则：依赖方向（单向，不可逆）

### 3.1 后端依赖方向

```text
interfaces/（HTTP、CLI、Event）
        │
        ▼
application/（用例编排）
        │
        ▼
domain/（业务规则，最纯净）

infrastructure/（技术实现）
        │
        ▼
domain / application contracts（只依赖接口，不依赖实现）
```

**绝对禁止的依赖方向：**

```text
❌ domain → database
❌ domain → HTTP framework
❌ domain → Redis
❌ domain → 第三方 SDK
❌ interfaces/controller → repository（跳过 application 层）
❌ interfaces/controller → ORM model（直接操作数据）
```

### 3.2 前端依赖方向

```text
pages/（路由组合层）
        │
        ▼
features/<domain>/（业务功能域）
        │
   ┌────┴─────────────────┐
   ▼                      ▼
components/ui/          services/
（纯 UI，无业务）        （API 客户端）
        │
        ▼
      lib/utils/
（纯工具函数，无业务无副作用）
```

**绝对禁止的依赖方向：**

```text
❌ features/order/ → features/payment/internal/（跨域访问内部文件）
❌ components/ui/ → features/（UI 组件依赖业务逻辑）
❌ utils/ → features/（工具函数不能依赖业务域）
❌ pages/ → infrastructure/（页面不直接访问数据层）
```

### 3.3 模块间通信规则

```text
✅ 允许的模块间通信
─────────────────────────────────────
模块 A → 模块 B 的公开 Application API
模块 A → Domain Event → 模块 B（事件驱动）
模块 A → 共享 contracts（跨端契约）

❌ 禁止的模块间通信
─────────────────────────────────────
order → payment/infrastructure/internal-repo.ts
user → order/domain/private-model.ts
任何模块 → 另一个模块的 internal/ 路径
```

## 4. 第三原则：按业务边界，而非技术类型组织

```text
❌ 按技术类型（错误）        ✅ 按业务边界（正确）
────────────────────────    ────────────────────────
src/                        src/modules/
├── controllers/            ├── identity/
├── services/               │   ├── domain/
├── repositories/           │   ├── application/
├── models/                 │   ├── interfaces/
└── utils/                  │   └── infrastructure/
                            ├── order/
                            └── payment/

问题：修改"订单"功能         好处：修改"订单"功能
需要同时修改 5 个目录         只需要进入 order/ 模块
```

```text
pyproject.toml              Python 根配置（如使用）
turbo.json                  构建工具配置（如使用）
```

### 5.2 禁止出现于根目录的文件类型

```text
❌ 根目录禁止清单（永久禁止）
──────────────────────────────────────────────────────────
*.png / *.jpg / *.gif        截图/图片    → docs/evidence/ 或 .local/screenshots/
*.log / *.txt（日志）        日志文件    → .local/logs/ 或 logs/（gitignore）
test_*.py / test*.js         临时测试    → tests/ 对应目录 或 删除
*.bak / *.backup             备份副本    → 永远不应存在，用 Git 替代
*.tmp / *.temp               临时文件    → .local/
config*.old / config*.new   配置副本    → 永远不应存在，用 Git 替代
*_v2.* / *_final.* / *_copy.*  版本副本  → 永远不应存在，用 Git branch/tag
debug*.js / debug*.py        调试脚本    → .local/scratch/ 或删除
0922测试.py / 副本_xxx.py   随意命名    → 永远不允许
server.log / error.log       日志文件    → .local/logs/
backup/ / old/ / temp/ / tmp/  临时目录  → .local/
```

### 5.3 根目录新增顶层目录审批规则

新增任何顶层目录，必须依次回答以下全部问题：

```text
1. 它属于哪种生命周期类型（Source/Spec/Input/Generated/Temporary）？
2. 为什么现有顶层目录无法容纳？
3. 它是否属于某个已有应用（→ 应进入 apps/<app>/）？
4. 它是否属于某个已有业务模块（→ 应进入对应模块）？
5. 它是否是生成物（→ 加入 .gitignore，进入 .local/）？
6. 它是否是临时状态（→ 进入 .local/）？
7. 它是否需要 Git 跟踪？
8. 它是否具有独立的、稳定的、长期的生命周期？

无法回答全部 8 个问题 → 不允许新建
```

# 第六部分：共享层与契约层规范

## 12. packages/ 规范（跨应用真正复用）

### 12.1 创建 package 的判断标准

```text
创建 packages/<name>/ 的必要条件（必须同时满足）：
──────────────────────────────────────────────────
1. 已有至少两个独立应用/模块真正使用这些代码
2. 共享语义已经稳定（不会因单个需求频繁变更）
3. 不属于某一个具体业务（不是 user 域的私有代码）
4. 具有独立的版本生命周期
5. 具有稳定的对外 API（index.ts 导出边界）

不满足以上任意一条 → 不创建，保留在模块内部
```

### 12.2 packages/ 完整结构

```text
packages/
│
├── contracts/                          # ★ 前后端共享契约（最重要的 package）
│   ├── src/
│   │   ├── identity/
│   │   │   ├── register.contract.ts    # 注册接口契约
│   │   │   ├── login.contract.ts
│   │   │   └── index.ts
│   │   ├── order/
│   │   │   ├── create-order.contract.ts
│   │   │   └── index.ts
│   │   ├── common/
│   │   │   ├── pagination.types.ts     # 通用分页类型
│   │   │   ├── response.types.ts       # 通用响应格式
│   │   │   └── error.types.ts          # 错误契约
│   │   └── index.ts
│   └── package.json
│
├── ui/                                 # 共享 Design System（可选）
│   ├── src/
│   │   ├── components/                 # 跨应用共享的基础组件
│   │   ├── tokens/                     # Design Tokens（颜色/间距/字体）
│   │   ├── patterns/                   # 复合 UI 模式
│   │   └── primitives/                 # 最小 UI 原语
│   └── package.json
│
└── config/                             # 共享工具配置基础（可选）
    ├── eslint-base.js
    ├── tsconfig-base.json
    └── package.json
```

### 12.3 contracts/ 的价值

```text
没有 contracts/：
    Web 猜接口格式
    API 猜前端期望
    两端各自维护类型，各自腐化

有 contracts/：
    Web  ─────────────→ contracts/ ←───────── API
    共同依赖同一份类型定义
    接口变更时，TypeScript 编译时即可发现两端不一致
```

# 第八部分：自动化边界守卫（Architecture Guard）

**这是将规范从"建议"变为"强制约束"的关键机制。**

没有工具约束时，架构意图随着成员离开而消失。有了边界约束，这些决策被编码进 lint 配置，超越任何单个贡献者而长期存在。

## 15. 第一层守卫：ESLint 模块边界规则

通过 `@nx/enforce-module-boundaries` ESLint 规则，可以为仓库中不同项目之间的资源访问定义严格规则，强制执行严格边界有助于防止计划外的跨域依赖。

```javascript
// eslint.config.js 或 .eslintrc.js
{
  rules: {
    '@nx/enforce-module-boundaries': [
      'error',
      {
        // 禁止传递依赖
        banTransitiveDependencies: true,
        depConstraints: [
          // ── 按层级约束依赖方向 ──
          {
            sourceTag: 'layer:domain',
            onlyDependOnLibsWithTags: ['layer:domain', 'layer:shared']
          },
          {
            sourceTag: 'layer:application',
            onlyDependOnLibsWithTags: ['layer:domain', 'layer:application', 'layer:shared']
          },
          {
            sourceTag: 'layer:interfaces',
            onlyDependOnLibsWithTags: ['layer:application', 'layer:domain', 'layer:shared']
          },
          {
            sourceTag: 'layer:infrastructure',
            onlyDependOnLibsWithTags: ['layer:domain', 'layer:shared']
          },
          // ── 按业务域约束跨域访问 ──
          {
            sourceTag: 'scope:order',
            onlyDependOnLibsWithTags: ['scope:order', 'scope:shared', 'scope:contracts']
          },
          {
            sourceTag: 'scope:payment',
            onlyDependOnLibsWithTags: ['scope:payment', 'scope:shared', 'scope:contracts']
          },
          // ── 按前端组件类型约束 ──
          {
            sourceTag: 'type:ui',
            onlyDependOnLibsWithTags: ['type:ui', 'type:util']
            // UI 组件不能依赖业务 feature
          },
          {
            sourceTag: 'type:util',
            onlyDependOnLibsWithTags: ['type:util']
            // 工具函数不能依赖任何业务代码
          }
        ]
      }
    ]
  }
}
```

模块边界落地并在 CI 中运行后，收益会随时间复利增长。架构变得自文档化——新工程师加入团队后，通过阅读 ESLint 配置，可以在五分钟内理解整个领域结构和依赖规则。这些规则讲述的故事与架构图相同，因为它们本身就是用代码表达的架构图。

## 16. 第二层守卫：依赖图分析（dependency-cruiser）

```javascript
// .dependency-cruiser.js
module.exports = {
  forbidden: [
    // 规则 1：domain 层不得依赖 infrastructure
    {
      name: 'no-domain-to-infrastructure',
      severity: 'error',
      from: { path: '/domain/' },
      to: { path: '/infrastructure/' }
    },
    // 规则 2：禁止循环依赖
    {
      name: 'no-circular',
      severity: 'error',
      from: {},
      to: { circular: true }
    },
    // 规则 3：禁止孤儿模块
    {
      name: 'no-orphans',
      severity: 'warn',
      from: { orphan: true, pathNot: ['\\.d\\.ts$', '(^|/)AGENTS\\.md$'] },
      to: {}
    },
    // 规则 4：禁止跨业务域直接访问 internal 文件
    {
      name: 'no-cross-domain-internal',
      severity: 'error',
      from: { path: '/modules/order/' },
      to: { path: '/modules/payment/(?!index\\.)' }
    }
  ]
};
```

## 17. 第三层守卫：根目录污染检查（Makefile）

```makefile
# ============================================================
# Architecture Guard：根目录污染检查
# ============================================================

check-root-pollution:
	@echo "[ Guard ] 检查根目录非法文件..."
	@ILLEGAL=$$(find . -maxdepth 1 \
	    \( -name "*.png" -o -name "*.jpg" -o -name "*.log" \
	    -o -name "*.bak" -o -name "*.tmp" -o -name "debug*" \
	    -o -name "test2*" -o -name "*_final*" -o -name "*_old*" \
	    -o -name "*_copy*" -o -name "*_v2*" \) \
	    ! -name ".gitignore" 2>/dev/null); \
	if [ -n "$$ILLEGAL" ]; then \
	    echo "❌ 根目录发现非法文件："; \
	    echo "$$ILLEGAL"; \
	    exit 1; \
	else \
	    echo "✅ 根目录检查通过"; \
	fi

check-forbidden-filenames:
	@echo "[ Guard ] 检查禁止命名的文件..."
	@FORBIDDEN=$$(find . -not -path "./.git/*" -not -path "./.local/*" \
	    \( -name "*_final*" -o -name "*_old*" -o -name "*_new*" \
	    -o -name "*_copy*" -o -name "*_v2*" -o -name "*.bak" \
	    -o -name "*副本*" -o -name "debug-*" \) 2>/dev/null); \
	if [ -n "$$FORBIDDEN" ]; then \
	    echo "❌ 发现禁止命名的文件："; \
	    echo "$$FORBIDDEN"; \
	    exit 1; \
	else \
	    echo "✅ 文件命名检查通过"; \
	fi

check-generated-in-git:
	@echo "[ Guard ] 检查生成物是否意外进入 Git..."
	@GENERATED=$$(git ls-files | grep -E \
	    "(dist/|build/|\.pyc|coverage/|\.log)" 2>/dev/null); \
	if [ -n "$$GENERATED" ]; then \
	    echo "❌ 生成物意外进入 Git："; \
	    echo "$$GENERATED"; \
	    exit 1; \
	else \
	    echo "✅ 生成物检查通过"; \
	fi

check-module-boundaries:
	@echo "[ Guard ] 检查模块依赖边界..."
	npx depcruise src --config .dependency-cruiser.js
	@echo "✅ 模块边界检查通过"

# 完整守卫（CI 中执行）
guard: check-root-pollution check-forbidden-filenames check-generated-in-git check-module-boundaries
	@echo "✅ 所有架构守卫检查通过"

# CI 完整流水线
ci: lint test guard build
```

# 第九部分：AGENTS.md 规范

## 19. AGENTS.md 的定位与作用

AGENTS.md 是一种简单的开放格式，用于指导编码 Agent。把它看作面向 Agent 的 README。

AGENTS.md 填补了 README 的空白。它是一个位于仓库根目录的 Markdown 文件，包含编码 Agent 有效工作所需的上下文：带有精确标志的构建命令、测试流程、与默认值不同的代码风格规则、架构约束以及 Agent 不应触碰的文件边界。

AGENTS.md 规范要求：实现 Agent Rules 的 Agent 必须检查项目根目录中是否存在 AGENTS.md 文件。如果存在，其内容应被纳入 Agent 的上下文范围。文件必须被解析为自然语言指令，并用于向 AI 编码 Agent 提供指导。

## 22. 模块拆分判断规则

```text
出现以下情况之一，评估是否需要拆分模块：
──────────────────────────────────────────────────────────
1. 一个模块存在多个明显不同的业务能力（高于3个）
2. 不同部分有不同的变化原因（SRP 违反）
3. 不同部分有完全不同的外部依赖
4. 不同部分有不同的团队归属
5. 不同部分有不同的部署生命周期

不满足以上任何一条 → 不拆分
拆分依据：业务内聚性与变化边界，而非"文件数量"
```

```makefile
migrate:

	@echo "✅ 全部架构守卫检查通过"

check-root-pollution:
	@ILLEGAL=$$(find . -maxdepth 1 \
	    \( -name "*.png" -o -name "*.log" -o -name "*.bak" \
	    -o -name "*.tmp" -o -name "debug*" -o -name "*_final*" \
	    -o -name "*_old*" -o -name "*_copy*" \) 2>/dev/null); \

ci: lint test guard build

clean:

	find . -type d -name .pytest_cache -exec rm -rf {} + 2>/dev/null || true
	find . -name "*.pyc" -delete 2>/dev/null || true
	rm -rf apps/web/dist apps/api/dist .local/runtime/
	@echo "✅ 清理完成"
```

## 25. 核心规则浓缩（50条 → 10条）

```text
1.  按运行边界分应用（apps/），按业务边界分模块，按职责分层，
    按复用关系抽共享（packages/），按生命周期隔离临时状态（.local/）。

2.  根目录是声明区，不是工作区。白名单制，非白名单文件立即清除。

3.  所有临时文件（截图、日志、调试脚本、备份）进入 .local/（完整 gitignore）。

4.  配置历史用 Git 管理，永远不允许 *.bak / *_final / *_old / *_copy 存在。

5.  依赖方向单向不可逆：interfaces → application → domain ← infrastructure。
    domain 不得依赖任何框架、数据库、第三方 SDK。

6.  模块间只通过公开 API（index.ts）或 Domain Event 通信，
    不得直接访问另一个模块的 internal 文件。

7.  shared/ 和 utils/ 不是垃圾桶。进入共享层必须满足：
    已有至少两个真实消费者 + 语义稳定 + 无业务特定含义。

8.  架构边界必须自动化守卫（ESLint 规则 + dependency-cruiser + CI 检查），
    不能只靠开发者记忆和代码审查。

9.  AGENTS.md 是 AI 的规范入口，与 README.md 平级但目的不同。
    AI 执行任务前必须加载规范，完成任务后必须运行守卫检查。

10. 结构不以"目录数量多"或"看起来企业级"为目标，
    而以"一个文件有且只有一个显而易见的正确位置"为目标。
```

## 26. 一句话原则

> **按运行边界分应用，按业务边界分模块，按职责边界分层，按复用关系抽共享，按生命周期隔离生成物与临时状态，用自动化守卫将文档规则变为机器约束——最终形成一个能约束人、也能约束 AI 的工程边界系统。**
