# 02 需求复核与辩证分析

## 1. 复述

AideanBotHot 是一个「公众号文章 → 知识库 → 对话问答」的产品：用户把文章收进空间，机器人基于空间内文章回答，并给出引用来源。管理端能看运维读数、配引擎密钥、触发推送。本版只碰其中一条主路径：**`/chat` 的流式问答在「未登录 / 加载中 / 成功 / 中断 / 降级」五种情形下的界面行为，以及这些行为的可执行验收。**

用户、管理端、系统边界：

- 用户：已登录的普通用户（`is_admin=false` 也要能用 `/chat`）。
- 管理端：`/admin`、`/admin/ops`，要求 `is_admin`。
- 系统边界：`/chat` 的检索与生成都不在本进程——检索委派 LangBot（`chat.py:344`），生成委派 OpenAI 兼容上游（`chat.py:242`）。本产品负责编排、收窄、渲染与降级。

## 6. 双向钢人论证

### 6.1 「`/chat` 该按 5 态验收」

**支持**：① 契约逐视图只列 5 个（`x-core-views` 现读）；② `initial` 在 `/chat` 无专属 DOM 出口，只有 `app/chat/loading.tsx` 的骨架 div，无可读文字；③ `forbidden` 无供给——越权空间返 404+30004（`chat.py:431-434`），唯一的 403+10004 是「引擎不可用」（`chat.py:438-439`），与「无权限」不是一回事。

**反对（最强）**：`definitions.State` 的 `note` 白纸黑字写「8 态而非 5 态」，`x-universal-rules[4]` 还要求「一次交齐 8 态」——照这个读，5 态验收就是降标准。

**结论**：反对意见的效力被自身文本抵消——`note` 与 `universal-rules[4]` 若成立，则 `NotificationBell` 的 `offstate` 与 6 个视图的 5–7 键同时违规，即契约在描述一个**不存在**的世界。按「具体优于抽象」，取逐视图键集。这不是降标准，是把标准从「不可判」改成「可判」——`r19` ④ 之所以退化成自指断言，正是因为原标准不可判。

### 6.2 「`stop` 按钮归 UI 卡，不改 `middleware`」

**支持**：`useSseAsk.ts:61` 已有 `streamAbortRef`，`:66`/`:180` 已在卸载与切空间时 abort ⇒ 中断能力**已在**，缺的只是一个用户可达的入口。加 `stop()` 是暴露既有能力，不是新建能力。

**反对（最强）**：`reset()` 已经 abort 了，为什么不能直接拿它当「停止」？——因为 `:179-184` 同时 `setMessages([])` 与 `setInput("")`，等于清空会话。用 `reset` 当停止，会把「停止」变成「清空」，与契约 error 态「保留已渲染内容」直接冲突。

**结论**：必须新增 `stop()`（只 abort + 把当前气泡标为已停止，不动 `messages` 其它项）。反对意见成立且已被吸收。

### 6.3 「假 LangBot 是唯一可行解」

**支持**：`langbot_base_url` 是 setting（`config.py:63`，无 `env_prefix`）⇒ 一个环境变量指走；`retrieve` 只依赖两个端点（`client.py:52-68` auth、`:198-211` retrieve）；响应形状有代码内注释（`:207`）与测试镜像（`test_chat_sse.py` 的 `_results()`）两处锚。

**反对（最强）**：假服务测的是自己的桩，不是真 LangBot——保真度不可证。

**结论**：反对成立但无法消解（真 LangBot 需要 docker compose + 公开可抓取文章 URL，CI 里都没有）。缓解：形状必须逐字复用 `_results()`，不得自创；这条风险随 STEP-60 进证据，不写成「已验证」。

### 6.4 「契约由规划方给逐字新文本、执行侧只做替换」

**支持**：D-V21-20 的例外是规划方；语义判断（哪些字该改、改成什么）不可逆性最高，属 opus；字节替换属 sonnet。

**反对（最强）**：既然规划方有落笔权，为什么不直接改文件？——因为用户 2026-10-28 的指令 §11 把可写路径限定为规划产物，冻结稿不在其中。让执行侧按逐字文本替换，既守住写权限，又保证语义由规划方定。

**结论**：反对不成立（写权限边界是硬约束）。方案成立。
