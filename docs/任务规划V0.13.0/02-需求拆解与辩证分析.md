# 02 需求拆解与辩证分析（main@314d7f2）

## 1. 复述与拆解

**核心问题（一段话）**：BotHot 是挂在主平台 SSO 下的"公众号内容采集 → 知识库 → 热点/日报 → 多渠道推送"系统。它要让运营者把公众号文章（单篇链接或整号订阅）可靠地、不重复地、可增量地收进分空间的知识库，基于知识库做 RAG 问答与热点聚簇，再按 Cron/事件/手动把结果推到飞书、钉钉、企微、Webhook、站内通知；管理端负责渠道、任务、引擎、空间与运维观测。

- **用户**：登录用户（role=user，默认）——用自己的空间、文档、订阅、问答、站内通知。
- **管理端**：operator（运营：渠道、推送任务、全局源）与 admin（管理：跨用户操作、引擎密钥、运维四屏）。
- **系统边界**：身份由主平台 OIDC 提供（本服务只存 `users.sub` 与角色）；知识引擎是可插拔外部服务（LangBot/aidean/redfox/builtin）；付费采集源（TikHub/JustOneAPI/Dajiala/WellByte）是外部 HTTP；推送目标是外部 webhook。端口 3200（前端）/3300（后端）在用户指定段 3200-3300 内（`docker/compose.yml:245,423`）。

**本次需求的关键词**：未实现需求、统一规划体系、核心功能、完成测试、契约先行、可并行、证据链。

## 5. 隐含要求与前置条件
- 隐含：**加密落库的密钥不能经任何读接口以明文回到非管理者**（REQ-NF-002 的应有之义）。
- 隐含：路由声明顺序是行为的一部分——静态段必须先于同层动态段（22 的守卫把它变成机检）。
- 隐含：健康接口是 compose healthcheck 依赖（`system.py:3`），它挂住 = 容器编排判不出状态。
- 前置：`@linux` 验收机需要 PG16（本版已在 5547 起，见 `07` §环境）与 `PUSH_SECRET_MASTER_KEY`（测试用随机值，不落盘）。
- 边界：Windows 回环不回 RST（执行方读数）——任何"连本地拒绝端口很快失败"的测试假设在 Windows 上都不成立。
- 依赖：22 与 23 同改 `bots.py` ⇒ 串行；21 依赖 22 的规则；15b 依赖 22（否则翻到真实后端立即报错）。

## 7. 苏格拉底追问（第二轮收敛，只列关键结论）
1. **"F-06 是越权"凭什么？** 证据来自 314d7f2 真库探针 + 代码现读，最新。反证"单租户都是运营"被写接口的分级门否定。前提：identity 契约的角色分级是有效设计——它是冻结契约，成立。⇒ 足以支持"P0、进入执行"。
2. **"CI-Windows 就是 H2"凭什么？** 只有相容证据（只卡 `/health`、portal 停在 select、Windows 不 RST），没有 Windows 直接读数 ⇒ **不足以判"已确认"**，只足以判"值得先修"——因为修法（加上界）对 H2 是根治、对 H3 无害。
3. **"/bots/tasks 恒 404"会不会是探针用 dependency_overrides 造成的假象？** 路由匹配发生在依赖解析之前，与 override 无关；且 `route_shadow_bots_tasks.txt` 是纯路由表计算，不经请求。⇒ 已排除。
4. **"前导零是缺陷"会不会是过度设计？** 键函数宣称的不变量是"同文同键"；违反不变量就是缺陷，与上游是否常见无关；修法 2 行、可逆。⇒ 成立，但排 S2.4 小任务而非 P0。
