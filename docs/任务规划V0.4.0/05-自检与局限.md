### 2.1 落库切分（本轮实测决定，不是偏好）

原先整包一起「等 D-12 再入库」是**估的**：以为只有模拟修复 patch 带假 DSN。本轮把判定交给代码——
`evidence/b45777a/precommit_gitleaks_scan.py` 用 `tomllib` 现读 `.gitleaks.toml` 的同一条规则与两类白名单，
按「即将入库的文件」逐行扫本包，读数在 `precommit_gitleaks_scan.txt`（三跑：整包 **5 条 rc=1** →
第 1 批（其余全部文件）**0 条 rc=0** → 自扫读数文件 **0 条 rc=0**；文件数以读数为准，本行不替它担保）。
点名的不是预想的一件而是三件：

| 批 | 内容 | 依据 |
|---|---|---|
| 第 1 批（现在入） | 本包除下列两件外的全部文件 | 跑 2 rc=0：提交它不会给 Security 添任何新指纹 |
| 第 2 批（S0C.2.1 之后入） | `evidence/b45777a/STEP-00C_proposed.patch`（4 条）、`evidence/b45777a/evidence_check_b45777a.txt`（1 条，第 121 行 NR-7 读数） | 跑 1 点名；两者入库即成为**新提交里的新指纹**，要先在源码侧把假 DSN 口令改成 `nosuch` 再重采/重生成 |

三条读表须知：
1. **`-` 行一样会被扫到**。补丁正文整份都是「新增文件的内容」，历史模式按新增行扫 ⇒ 引用旧代码的
   `-\ \`postgresql+psycopg://x…\` 那几行同样算新指纹。这一条推翻了上一轮「只有正行有风险」的猜测。
2. **模拟修复并未丢**：patch 里 `apps/api/tests/*` 那三个 hunk 已按块切出为
   `STEP-00C_ruff_tests.patch`（ruff 三处段序 + 一处 E501 折行，不含任何 DSN），
   `git apply --stat` 与合并版逐文件相同、`git apply --check` rc=0 ⇒ 可先入库并供 S0C.1 直接用；
   合并版留在工作树未入库，S0C.2.1/S0C.2.2 完成后由重采的读数取代。
3. **读数文件自己也带回了那 5 条**——第一版逐字打印命中片段，`precommit_gitleaks_scan.txt` 自己变成新的
   指纹源（「报告漏洞的信本身是漏洞」）。故片段一律经 `mask()` 掩码，并加跑 3 自扫读数要求 rc=0 作为反证通道。

## 3. 前提与局限
1. **本包混用了两台机器**，读数不能混着读：b45777a 的两次全量、探针、覆盖率、gitleaks、evidence-check 产在
   aarch64 Linux 沙箱（`/workspace/work/BotHot`，有 uv + 依赖 + PG）；本轮的 E501 宽度对照、g24↔ruff I001 互斥、
   patch 切分与 `git apply --check`、落库前置扫描、EVD-V2-02 的 A–N 驱动留档产在 win32 执行机
   （Python 3.11.9，只有 stdlib 与 pytest 9.1.1 壳）。两台的判据是同一份代码，但**覆盖面不同**，
   分工表见 00-README §7；分辨两份读数的来源也有免费线索：沙箱件里的路径是 `docs/...`、`tests/...`，
   win32 件里是 `tests\...`（反斜杠）。
   本轮把「win32 到底缺什么」量出来了（`evidence/win32_pytest_collect_20261013.txt`）：
   `python -m pytest tests --collect-only -q` 0.73 秒死在 `tests/conftest.py:33` 的
   `ModuleNotFoundError: No module named 'sqlalchemy'`，rc=4，连 `collected` 行都没有。
   win32 现象里**本轮实测到的只有 cp936 一类**（`out_s213.txt:84-85` 的编码自证与 K.1/K.4 的裸跑）；
   **环境变量大小写折叠与回环 DROP 本轮未复测**，仍沿用 V0.3.0 的记录。
2. **CI 的「步骤名与结论」本轮已实测，「日志正文」仍未读**（需登录）。本轮经 10808 代理取匿名 REST
   `/repos/aideanew/BotHot/actions/runs?per_page=60` 与 `/actions/runs/{id}/jobs`，量到：连红 13 次
   （`5c8552b`→`d80eeaf`），`d80eeaf` 那次只有 `backend` job 的 `Lint (ruff)` 步 failure、其后 7 步 skipped，
   另四个 job 全 success（01 F-29）。**没量到的仍是那 7 步的内容**：它们在 `5c8552b..dcb1ffb` 之间是否曾红过，
   从步骤状态看不出来（skipped 不区分「因为 ruff 失败而跳过」与「自己失败」）⇒ 结论仍来自同版本工具本地复现
   + 模拟修复反证，S0C.4.1 的口子照留。匿名 API 有速率限制（本轮复测时 `remaining 0/60`，
   重置前的读数无法二次核对），所以这类读数一次成型就要落盘。
3. `.gitleaksignore` 指纹含行号，基于 `main@b45777a` 的历史；若在 STEP-00C 前又有新提交带入假 DSN，需重跑 gitleaks 重新取指纹。
4. 前端未复跑（本区间零改动）。
5. 生产数据规模仍未知（U-02/U-03）。
6. 估时是相对估计，不是承诺。
