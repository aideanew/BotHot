## 4. 辩证
**为什么 P-114 要修，而不是接受"锁环境不可达"**
- 支持不修：CI 与镜像都按依赖声明安装，今天确实没有 rich。
- 反对：可达性取决于"依赖树里碰巧没有 rich"，任何一个新依赖（命令行工具类库常带 rich）都会悄悄打开它，且没有门会响；开发机日志也会被拷贝、截图、贴进工单。修复只需给渲染器显式传一个参数，成本极低。⇒ 修。

**为什么 JSON 用 `format_exc_info` 而不是结构化 `dict_tracebacks`**
- `dict_tracebacks` 输出结构化栈，便于检索，但它的变换器支持局部变量展示，口径要额外钉死；`format_exc_info` 只产出纯文本栈，天然不含局部变量，且渲染后照样经过 STEP-40 的 URL 遮蔽。⇒ 选纯文本，代价是栈在 JSON 里是一个长字符串字段 `exception`。

**反证（修了以后可能出什么问题）**
- 生产日志变长（每条异常多一段栈）：异常本就少，可接受。
- 有用例按 JSON 字段断言 `exc_info`：现读 `tests/` 只有 `test_log_redaction.py` 涉及，已核。
- 修改的是规划方 STEP-40 的同一文件 ⇒ 同样需要独立复查（并入 STEP-44 的 S44.1）。

**P-116 为什么不降阈值或靠重跑**
- 支持降阈值：只差 1 行。反对：D-V18-07 禁降；重跑会把看墙钟的确定性缺陷藏起来，下一个凌晨照红。⇒ 补冻结时钟用例，读数与时刻无关。
- 为什么规划方亲做：main 红会让执行助手每张卡的「同一 head 三绿」判据永远达不到，阻塞全队列。
