## 1. 本版立场（为什么不再是"再加几张卡"）

V0.8.0 的大纲已经很整齐（27 卡 / 187 任务 / 28 人日），但**它没有推进**：7 个提交里 `apps/api/app` 零改动（F-02），
唯一完成的门禁项（恒红断言）是并发会话顺手做的，而同期证据脚本涨了 ~890 行、复审到第十八轮。
⇒ 三个版本的同一批卡都在"未开始"，原因不在任务不清，而在**两个前提从来没被固定住**：

1. **签字缺失**：`decision-log.md` 不存在，累计裁决 3 个版本 0 已签（F-11）。BLOCKING 项（D-V3-00/01/03/06、D-V2-01…）全部悬空 ⇒ 01/02/04/13/14/15 无法开工。
2. **验收环境缺失**：真库 pytest 连续两版标 BLOCKING（V0.8.0 §4 记本机 PG 实例被并发会话清掉，F-15）；本轮 `node_modules` 又实测不存在（F-10，而 V0.8.0 F-08 说存在）。

所以 V0.9.0 的 M0 第一件事不是改代码，而是**把前提变成可交付物**：00G（裁决登记，不需人即可做的部分）+ **00E（验收环境供给与固定）** + **00P（敏感形机械门）**。其余卡不动，避免制造第四份平行大纲。

### 2.1 计数的可复算性（本版定的硬规则）
V0.8.0 的 187 是程序化求和得来的，本版沿用该纪律，并加两条：**任何"合计"必须由脚本现算，禁止手填**；**求和口径必须落在唯一真有该字段的地方**。

```bash
# 真源＝本文件 §2 表的「三级任务」与「人日」两列（继承卡内不带计数字段，别去卡里找）
python - << 'PY'
import pathlib, re
t = pathlib.Path('docs/任务规划V0.9.0/04-剩余可执行大纲体系.md').read_text(encoding='utf-8')
n=tot=0; days=0.0
for line in t.splitlines():
    if not line.startswith('| '): continue
    c=[x.strip() for x in line.strip('|').split('|')]
    if len(c)<9 or c[0] in ('STEP','---') or c[0].startswith('**合计'): continue
    a=re.match(r'(\d+)', c[5].replace('*','')); b=re.match(r'(\d+(?:\.\d+)?)', c[6].replace('*',''))
    if a and b: n+=1; tot+=int(a.group(1)); days+=float(b.group(1))
print('STEP 行:', n, '| 三级任务合计:', tot, '| 人日合计:', round(days,2))
PY
# 期望：STEP 行 29 ｜ 三级任务合计 198 ｜ 人日合计 29.0
```

> **本版在此踩过的坑（记下来防再犯）**：初版把复算命令写成"逐卡 grep `剩余原子任务`"，实测只返回 12——
> 因为 V0.8.0 的 27 张继承卡**根本没有那个字段**，计数只存在于 04 的总表列里；只有本版新写的 00E/00P 两张卡带字段。
> 判据指向不存在的数据源，比没有判据更糟：它会给出一个看似精确的错误数。
> 同理，本版正文合计曾手填 199，脚本复算为 **198**（漏扣 00C 已完成的那一格），已改。
> **该脚本的形状依赖性（独立验证者实测，勿当通用工具用）**：它按"第 6 列=任务数、第 7 列=人日"解析本表；
> 拿它去跑 V0.8.0 的 04（12 列布局）会返回 **0/0/0**——不是 V0.8.0 没有数，是列位不同。
> 因此这条命令只对**本版表**有效；跨版对照须各自按其表头列位重写解析，别复用。
> 扣减项由执行者按其卡内勾选态现算；本版不重抄 V0.8.0 的卡内明细——那只会制造第四份真相源。

## 3. 00G 的关键改法：把"登记"与"签字"拆开

三个版本 0 签的根因不是没人肯签，是 V0.6.0 起的默认机制被写成**一个动作**：`新建 decision-log.md 并登记 20 项`。
登记需要人（怕被理解为规划方自证通过），于是整张卡停摆。
⇒ 本版 00G 拆两格：
- **S0G.1.1 登记（执行者可做，不需授权）**：建 `decision-log.md`，每项写「默认值 / 登记时间 / 生效时间 = 登记+24h / 签字栏留空 / 推翻入口」。留空签字栏是**事实陈述**，不是代签。
- **S0G.1.2 签署（👤）**：人只勾 4 个 BLOCKING（D-V3-00/01/03/06），其余按机制默认生效。
这样"没人签字"时，仍能确定性地知道哪些项将在何时生效，而不是整条链停摆。

## 4. STEP-00P 与 F-09 的正确解读（不要过度声称）

本轮我清掉了 `V0.7.0/06` 里自己写进去的凭据形（占位 DSN + 扫描正则本身），并验证扫描器对 V0.7.0 / V0.9.0 **HIGH 0**、对被排除 patch 仍 HIGH 5。
**但这不等于 Security 转绿**：gitleaks 扫的是历史提交，`f70d52f` 那次引入的指纹永远留在历史里，只能靠 `.gitleaksignore` 逐指纹豁免（S0C.2.2 / 00S），而本机没有 gitleaks 二进制 ⇒ **指纹值仍 NOT_MEASURED，禁止猜**。
00P 因此只干两件事：
- **S00P.1** `evidence-check` 增机械门：对**待入库路径**跑 `secret_shape_scan.py`，HIGH>0 即红，且缺 gitleaks 时打印 `SKIP(tool missing)` 并以非 0 区分（沿用 00C S0C.4.1 的口径）。
- **S00P.2** 立规：文档里的"扫描判据"必须指向脚本，**不得内联正则或样例串**——本仓已经自伤两次（V0.7.0/06 抄 DSN、抄正则），这不是假想风险。

## 5. 指标的口径修正：从"设基线"改成"耦合门"

V0.7.0 设 B-8「证明脚本只降不升」，V0.8.0 沿用；两版连续被破（8,383 → 9,519 → **10,406**，F-07）。
一个被破两次还没换机制的指标，说明指标本身无效。本版改为：

| 旧指标（废） | 新门（耦合） | 判据 |
|---|---|---|
| 证明脚本行数 ≤ 某基线 | **同一 PR 内 `evidence/*.py` 净增行数 > 0 时，`apps/api/tests/**` 必须净增 ≥1 条用例；否则 evidence-check 红** | 脚本数差值现算，红档可复现；配一发"只加脚本不加用例"的变异反证 |

理由：行数本身不是价值，"只长证据不长假设"才是问题。耦合门让两者必须一起动，比任何冻结数字都难被绕过。
