### F-4 `backend` 的红是**确定性文档缺陷**，不是 flaky（**推翻规划方的判断**）

规划方的只读报告把它记成「非确定性失败、失败用例名 UNKNOWN」。实测推翻：

| 项 | 读数 |
|---|---|
| 失败用例（CI + CI-Windows 同名） | `tests/test_collection_contract.py::test_decision_log_tables_are_well_formed` |
| 两个 run | `40673181463`（`5002410`，backend）、`40673181460`（CI-Windows） |
| 可复现性 | 本机复跑同一用例 → 红；blame 定位到 `7c15264`（规划方追加 D-V24-01～12） |
| 根因 | `docs/03_solution/decisions/decision-log.md:183` 是 `eba3b20` 留下的**表格终止空行**；规划方把 12 行裁决**接在该空行之后** ⇒ 表格被劈成两张，后 12 行落在无表头的第二张表里 |
| 修法 | 删掉那一个空行（2 文件 +1/−1） |
| 落地 | `df210b3`，已登 P-159 |

**为什么这个订正重要**：按「flaky」处理会走 rerun，rerun 之后仍红（因为字节没变），
然后被判成「CI 环境抖动」放过——**STEP-75 的原始卡面（rerun 一次即收工）恰好会落进这个坑**。
STEP-75 因此改成「先读失败用例原文名，再判是否 flaky」，rerun 不是第一步而是兜底。
