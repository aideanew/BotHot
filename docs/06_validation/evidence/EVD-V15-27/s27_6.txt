S27.6 —— 启动期 schema 探测的上界（D-V12-07）

一、改了什么
`apps/api/tests/test_startup_probe_timeout.py` 的 `_CHILD` 在 `import app.main` **之前**
把 `asyncio.run` 换成计时包装（进入起表、返回/抛出停表），子进程自报
`SCHEMA_PROBE_SECONDS <秒>|none`。判据：3.0s ≤ 探测段 < 7.0s（`LIMIT_SECONDS` 8.0 → 7.0）；
`PROBE_SECONDS`（整段 import 墙钟）只报不判。`apps/api/app/**` 一个字未动（卡面禁止）。

二、本机实测（绿态）
$ cd apps/api && python -m pytest tests/test_startup_probe_timeout.py -q -rs
1 passed in 8.37s
子进程自报形如 `SCHEMA_PROBE_SECONDS 3.01`（非 none）⇒ 计时包装真的包住了探测那一段，
而不是把整段 import 墙钟当判据——后者受解释器启动/磁盘影响，会把超时上界随机器漂移。

三、两条反证（把判据的牙拔掉，必须立刻红）
1. 变异：把 `app/main.py` 的两级超时调成 `/20`、`/30.0`（EVD 记录后逐字节还原）
   原文：`s27_6_mutation.txt`
   E   AssertionError: 探测段耗时 20.02s 超过 7.0s 上界 —— 黑洞地址下还这么久说明两级超时
       （connect_timeout=3 / wait_for=5）都没生效。整段 import 22.09s、父进程墙钟 22.78s
       （均含解释器启动，不计入判据）
   assert 20.02 < 7.0
2. 去掉计时包装（改成 `asyncio.run` 原样调用）
   原文：`s27_6_no_wrapper.txt`
   E   assert 'none' != 'none'
        +  where 'none' = ...match='SCHEMA_PROBE_SECONDS none'...
   ⇒ 有自报行但值是 none：探测本身没跑到 ⇒ 不能让"看起来有读数"冒充通过。

四、并发复跑（P-38 原失败条件）
3 个 pytest 并发跑本用例 ×3 轮，全部 rc=0，未复现 P-38 的墙钟假红。
结论：21:24 前后本机独占跑 8.37s；上界 7.0s 留了约 2 倍余量给并发扰动。

五、读数边界
本机无 PostgreSQL（沙箱禁止 initdb/postgres），连库用例全部 skip；本条判据不连库
（它连的是黑洞地址），因此读数与有没有库无关。
