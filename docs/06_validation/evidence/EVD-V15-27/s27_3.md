# S27.3 / S27.V15.1 敏感形门源码模式（D-V12-05 / D-V12-19 / D-V12-21）

## 1. 为什么要有第二口径

P-40 记录的 14 份自有源码文件长期被本门挡住：命中全是**表达式**——键名紧接赋值号、
右值是解密函数调用；对象键名后接冒号、右值是表单属性；键名等于配置对象属性。
门没有豁免通道（S00P 明确「本门不自建 allowlist」），于是任何触碰这些文件的提交都被
永久挡住。S27.V15.1 要的是**有语义的线**，不是"源码文件跳过"。

判据（写进 `docs/04_engineering/conventions.md` §9.2，源码面与文档面口径不同）：

| 情形 | 判定 |
|---|---|
| 键名落在字符串/注释里（含跨行三引号、反引号） | 照报——那段文本本身就是字面量 |
| 键名在代码位，右值无引号且非纯数字 | 不报（表达式） |
| 右值里出现**值位**的值类字面量（≥8 字符、非占位、非全大写环境变量名） | 报 |
| 右值整体就是一个字面量 | 报（不看长度） |
| 字面量处在**键位**（`[` 之后、`.get(`/`.pop(`/`.setdefault(` 首实参） | 不算值，不据此报 |

## 5. 实现过程中自查出的一处自伤（本轮内修掉，未入下一轮）

首版把**键位**里的字面量当成值类字面量，于是 `providers/aidean/client.py`（0 → 3 命中）
与 `api/v1/auth.py`（0 → 1）这两份**改前能过门**的文件被新口径判红——"放宽表达式"的同一批
改动，又把两处表达式换成另一种误报关回门里。形态是"键名 = 对象[同名键]"与
"键名 = str(表单.get(同名键, 空串))"。

修法：`_literal_is_key()` 判定字面量是否处在键位（`[` 之后，或 `.get(`/`.pop(`/`.setdefault(`/
`.getlist(`/`.getall(` 的第一个实参）；键位不参与"值类"判定，**第二个实参（兜底值）照旧按值判**。
成对用例：`test_source_mode_treats_a_keyed_lookup_as_a_reference_not_a_value`（不报）与
`test_source_mode_still_reports_a_hardcoded_fallback_after_a_keyed_lookup`（照报）。

同一次自查还发现**门咬死自己**：`guards.py` 的注释里内联了那两处完整形状，自扫 2 条 HIGH
（S00P.2.1 的第二次复发）。改法同既有纪律：只描述形状（「键名=对象[同名键]」），不写完整文本。
回归守卫 `test_source_mode_never_drops_a_line_carrying_a_value_literal` 的辅助判据同步改为
"**值位**值类字面量"，并在测试侧**独立复写**键位判定——不调实现里的私有函数，否则等于用实现
证明实现。

如尖括号/`xxxx`/`REDACTED`）不在本卡「允许修改」范围内（本卡只允许 3 个测试文件）。
**按规则登记为新 P 项（建议 P-42）**，不在本卡内顺手改。
