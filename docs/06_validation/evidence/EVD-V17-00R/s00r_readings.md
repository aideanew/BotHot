## 1. S0R.1 归类：`IntegrityError` / `DataError`

卡面要"抽取全部 IntegrityError/DataError 行 → 按用例名对齐 → 判定预期/缺陷 → 缺陷项开新卡"。
这一串是在**没有失败用例的全量**上做的，所以判据不能是"日志里搜不到"一句话，得说清三件事：

1. **空集是被证明的**：`failures=0 errors=0`（junit 总账）+ `2061 passed`。`-q` 模式下无失败就不打印
   traceback，所以日志 67 行里没有六族关键字**是结果**；判据实体是 junit 的 `failures/errors` 两格。
2. **`DataError` 在本仓 0 命中**（`git grep -n 'DataError' -- apps/api` ⇒ 空）。卡面把两族并列写了几版，
   但第二族从来没有用例面。这条要说死，否则下一轮又 grep 一遍再记成"新发现"。
3. **`IntegrityError` 的 31 行按层归类**：生产侧 19 行、测试侧 12 行（行数是这条命令的输出，不是"站点数"——
   里面含 import 与注释行）。测试侧全部是断言预期；生产侧分两套判别式，
   逐条对照后**没有一条是掩盖性的**（非目标冲突一律 `raise` 上抛）。
   两套判别式的名字、局限与"没有门钉住新代码必须选哪一种"这条观察，固化在
   `docs/04_engineering/db_noise.md` §4。

## 2. S0R.2 skip 固化

产出面是 **`docs/04_engineering/db_noise.md`**（活文档，工程规范树内），不是本证据目录——
理由见 §4 的路径越界声明。本卡要的三件都在那里：族表、逐条清单、与两个基线的对照。

**一条值得单独记的纠正**：本文第一版的 Windows 列抄的是 `EVD-V13-00H` §7.3 在 `441` 基线时代的那组数
（`PG-DSN-未设置 332`）。本批直接读 run 39536915781 的门输出后是 **469**，
`PG-不可达` 仍是 104。两个数之间没有任何"解释"可言——基线从 441 抬到 578，构成必然重算。
这就是为什么族表下面必须写"判据来源是门自己打的行"，而不是"某次执行方的分布统计"。

另一个形态差异也照实记下来，不要抹平：`LangBot-不可达` 在 ubuntu 是 2 条、在 Windows 是 1 条。
门禁的归档是**按表序首命中**，同一批 skip 在不同平台可能落进不同族，
所以"族构成"不可跨平台外推，也不可拿本机分布去推 CI。

## 4. 路径越界声明（本卡唯一一个"不能照卡面执行"的点）
