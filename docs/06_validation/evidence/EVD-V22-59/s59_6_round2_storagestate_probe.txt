== P-147 那条红的机制探针：`test.use({storageState: undefined})` 到底清不清得掉 project 默认会话 ==
== 判据不是配置回显，也不是 Playwright 的日志，而是**测试服务器实际收到的 Cookie 头** ==
== 探针落在仓外（%USERPROFILE%/AppData/Local/Temp/s59/spw/），三个文件：playwright.config.ts / probe.spec.ts / server.mjs ==
== 用的是本仓 apps/web/node_modules 里那份 @playwright/test（^1.63.0）与本机已装的 chromium； ==
== 与 BotHot 的产品代码、后端、Redis 都无关，所以它能在没有 docker/PG 的本机跑出来 ==

配置要点（就是 `playwright.config.ts` 里 real project 那个形状）：
  projects: [{ name: "probe", use: { storageState: "state.json" } }]
  state.json 里一条 cookie：probe_session=admin-token（domain 127.0.0.1）
  server.mjs 把 req.headers.cookie 原样包进 COOKIE::<...>::END 吐回去

三条用例与读数（原文）：

  Running 3 tests using 1 worker
  PROBE_B_COOKIE=[probe_session=admin-token]
  PROBE_C_COOKIE=[]
    3 passed (4.7s)

逐条含义：
  A「不覆盖」是正对照，它用 expect(header).toContain("probe_session=admin-token") 断言并通过
    （`3 passed` 里含它）⇒ 证明"服务器能看见 cookie"这条观测通道本身是活的，B/C 的空与非空才不是假读数。
  B `test.use({storageState: undefined})` —— **admin.spec.ts 当时用的就是这个写法** ——
    服务器仍收到 `probe_session=admin-token` ⇒ **没有清掉**。
  C `test.use({storageState: {cookies: [], origins: []}})` —— 文档化的清空写法 ——
    服务器收到空 Cookie 头 ⇒ **清掉了**。

结论：P-147 里那两条机制候选，①成立、②排除。这条不是推定，是上面 4 行读数。

  ❌ 本脚本起过的 backend 还占着端口 3300（没清干净，不静默放过）

== 本机证不了的那一半，写清楚而不是不说 ==
本机跑不了 stop 路径的真读数：git-bash 的 `kill` 按 MSYS pid 发信号，Windows 侧监听进程根本不死，
`stopped … pid=` 这句在这台机上会谎报（我第一次试的时候 3300 上留下两个孤儿监听者，
得用 `netstat -ano` 拿到 Windows pid 再 `taskkill //PID <n> //F` 才清掉，复 check 已空闲）。
⇒ stop 那条改动的**真实读数只能在 @ci（ubuntu runner，SIGTERM 直达）取**：
   期望看到 `端口 3300 在第 N 次轮询…后才空闲——SIGTERM 的释放延迟，不是泄漏`，
   或干脆不出现这行（第一次轮询就空闲）；两种都算过，出现"等满 6s"才算真泄漏。
① 那条同理：本机没有 docker/PG/Redis ⇒ 真后端档跑不起来，只能由 @ci 的 `e2e-real` job 证。
