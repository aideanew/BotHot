### 1.2 两份参考均未发现的新问题（本轮新增）

1. **CI 测试门禁虚设**：测试基座是真实 Postgres（`conftest.py:36` 默认 DSN 指向 5433），PG 不可达 3 秒内 skip（`conftest.py:98-99`），而 **`.github/workflows/ci.yml` backend job 无 postgres service** → CI 里所有连库测试静默 skip，“全量测试通过”是假象。
2. **事件触发的进程拓扑矛盾**：ingest 发生在 **worker 进程**（`compose.yml:296-328`，`python -m app.services.job_worker`），而 push_scheduler 跑在 **backend 进程** lifespan（`main.py:247`）。参考分析2 的 T3.1.1“进程内 asyncio 发布订阅”**根本跨不过进程边界**，方案不可行，须改 outbox 表。
3. **PushTask 无 PUT 端点**：`bots.py` 只有 create/list/delete/run——任务**无法编辑、无法暂停/恢复**。参考分析2 的 T1.1.2“在任务编辑端点重算 next_run_at”前提不存在，得先建端点。
4. **创建 cron 任务不校验 cron_expr**：`bots.py:349-367` 对 `trigger_type=cron` 不校验表达式可解析性，可创建出 cron_expr 为空的“静默死亡任务”。
5. **站内通知“已通”是半程虚报**：`web.py` 投递侧真实（Redis pub/sub），但前端 grep `WebSocket|bothot:notifications` **零命中**——无订阅侧，所有站内通知发进无人接收的频道。
6. **celery[redis] 依赖僵尸**：`pyproject.toml:12` 锁着 `celery[redis]>=5.4.0`，全仓零接线（job 队列是自研 PG 队列），与约束#4“不引入 Redis 队列”直接冲突。
7. **前端 API 层已齐、只缺 UI**：`lib/api/bots.ts:162-197` 的 `createPushTask/listPushTasks/deletePushTask/runPushTaskNow` 与 `hot.ts:89` 的 `triggerCluster` 均已实现（`page.tsx:23` 的 `listPushTasks` 是死导入）——前端工作量远小于参考分析1的估计。
8. **ContentAsset 无 embedding 列、无 source_name 冗余**（`entities.py:118-143`）：向量聚簇需 Alembic 加列；而 TF-IDF 文本聚簇所需字段（title/category/published_at）齐全，零 schema 变更。`embedding.py` 生产零调用方（仅测试引用）。
9. **时间源不一致小刺**：`bots.py:478` 用 `func.now()`（DB 时钟），调度器用 `datetime.now(UTC)`（应用时钟）。

## 二、辩证收敛：六个关键决策的两向钢人

**D1 先迁移 vs 先填功能 → 先填功能，迁移延后，但契约先行。**
主张先迁移者说 apps/ 骨架越晚越难迁；钢人后否决——当前所有功能缺口（AES、cron、聚簇）都要在 backend/ 代码上验证，先迁等于在空壳上重写未稳定逻辑，双倍返工。但采纳参考分析2的折中：**先冻结 packages/contracts 契约**（成本一天以内），把迁移摩擦降到最低。裁决：功能先行（M1/M2），契约冻结随行（M5.2），目录迁移压轴（M5.3+）。

**D2 聚簇选型：LLM+向量 vs TF-IDF → 初版 TF-IDF，LLM 只做标题摘要。**
主张向量方案者说精度高；钢人后发现隐藏成本被两份参考都低估：嵌入方案需要给 ContentAsset 加向量列（Alembic 变更）+ 打通生产零调用的 embedding.py + 灌全量历史向量，而 TF-IDF 所需字段全部现成、日增文章量级（百~千）下 Python 内存计算毫秒级完成。LLM 在环只用于摘要（失败可降级），不进聚簇关键路径。裁决：TF-IDF + 余弦 + 阈值凝聚聚类；**同时在模型层预留升级路径**（嵌入列与 pgvector 列为独立后续任务，不阻塞 v0.5）。

**D3 事件触发的实现拓扑 → DB outbox 表 + push_scheduler 统一扫描，否决进程内 event_bus。**
理由见新问题#2：worker 进程里产生的 `article_indexed` 无法用进程内总线送到 backend 进程的调度器。outbox 方案（事件与业务同事务落库 → backend 每 60s tick 扫描执行）天然获得 at-least-once 语义、与 cron 扫描同构、复用同一套 `_execute_task`，且不违反约束#4（PG 而非 Redis）。代价是事件延迟下限 = 扫描间隔 60s，验收口径据实调整为 <90s。

**D4 渠道密钥主密钥：复用 ENGINE_KEY_MASTER_KEY vs 独立 PUSH_SECRET_MASTER_KEY → 独立。**
主张复用者说少一个配置项；钢人后否决——引擎 Key 与渠道 secret 是不同泄露域、不同轮换周期，复用会让一次轮换波及两域；且 `engine_keyring.py:67-89` 的纪律明文“绝不回落明文/静默分歧”，回落复用恰是静默耦合。裁决：新增独立 `PUSH_SECRET_MASTER_KEY`，fail-closed，生产断言（`main.py:256` 的 `assert_production_ready`）同步收紧；存量 base64 由 Alembic data migration 一次性重加密（compose 的 migrate 服务先于 backend 启动，时序成立）。

**D5 聚簇/日报的执行位置：新 loop vs 复用 Job 队列 → Job 队列。**
自研 PG Job 队列已有完整的认领（SKIP LOCKED）、重试、心跳、幂等基建（`job_worker.py:103-132`），把 `hot_cluster` 和 `daily_report` 做成 Job type 即可白拿全部可靠性语义；新开 loop 则要重造一遍。裁决：聚簇由订阅同步进程按日触发入队（或手动 API 入队），worker 执行；日报同理。

**D6 旧 push.py 分叉的处置：退役 vs 改造 → 改造收编，删除 push_port。**
`admin.py:515` 的管理端推送语义（校验+代投）与新包能力重合。把 `PushService` 的校验三段式（`_assert_channel/_assert_content/_assert_targets`）保留为共享校验模块，投递切换到 `providers/push.make_push_provider`（web 渠道语义兼容：都是 external_user_id → Redis），随后删除 `push_port.py` 并迁移 `test_r11_push.py`、`admin.py:64` 两处引用。裁决：收编，而非并存。

## 五、验收标准（量化）

1. cron 任务创建后 `next_run_at` 非空且被调度器拾取执行——全链路集成测试证明；任务可编辑/暂停/恢复。
2. 标准 5 段 cron 正确调度，存量三种简写格式行为不回归（兼容层测试）。
3. 存量密文迁移后 100% AES-256-GCM 可解，跨 channel AAD 拒解，`PUSH_SECRET_MASTER_KEY` 缺失时 fail-closed 拒启。
4. 事件触发推送端到端延迟 < 90s（受 60s 扫描间隔下限约束，据实修正参考分析1 的 <60s 口径）。
5. 聚簇人工抽检 10 条，准确率 > 70%；日报含 LLM 摘要且 LLM 故障时降级可读。
6. feed_items 三类条目均有真实生产者，`(item_type, ref_id)` 无重复。
7. CI 连库测试真实执行（skip 数回落基线），全量绿；compose 冒烟含“入库→聚簇→日报→推送”闭环。
8. web 渠道验收前置：前端订阅侧上线前，投递成功率验收口径为 5/6 渠道。
9. `push_port.py`、`celery[redis]` 删除，全仓 grep 清零；文档三方（roadmap/backlog/AGENTS）状态一致。

## 六、关键风险与缓解

| 风险 | 概率 | 缓解 |
|---|---|---|
| TF-IDF 聚簇精度不足（短标题/同义改写） | 中 | τ 阈值可配+人工抽检门禁；模型已预留嵌入列升级路径（独立后续任务） |
| outbox 消费与 cron 投递重复投递 | 低 | 消费标记与 SKIP LOCKED 同事务；集成测试覆盖 |
| 存量 base64 迁移丢数据 | 低 | data migration 先解后加密、失败即中止（fail-closed）；迁移前备份 |
| 领取后崩溃丢一轮推送 | 低 | cron at-most-once 语义在文档明示；重要场景可配 run-now 补偿 |
| 前端迁移破坏功能 | 中 | 迁移前 e2e 链路已补（4.3.1），每域迁移后全绿门禁 |
| 业务日界口径错误（UTC vs Asia/Shanghai） | 中 | **需产品拍板**：建议 topic_date/日报用 Asia/Shanghai 日界（`ZoneInfo`），文档明示口径；热榜 8 小时错位会直接打脸“今日热点” |

## 七、前提条件与局限性

- **前提**：本地/CI PG 可达（5433）；`PUSH_SECRET_MASTER_KEY` 与既有 `ENGINE_KEY_MASTER_KEY` 的密钥管理流程建立；LLM_API_BASE（SiliconFlow）可用是日报 LLM 摘要验收的前提（降级路径不受此限）；微信 ClawBot 渠道验收依赖其服务部署。
- **局限**：本方案的热度公式与状态阈值来自需求文档口径，实际分布需上线后校准；60s 扫描间隔是事件延迟的硬下限，若业务要求秒级需引入 LISTEN/NOTIFY（列为后续可选项，当前不建议）；嵌入向量聚簇、web 渠道订阅侧、pgvector 均为显式排除项而非遗漏，各自单独立项。

**一句话总览**：v0.4 的推送能力在代码层未达验收——cron 任务创建即死（1.1.2）与 AES 未接入（1.2）是两处硬阻塞；v0.5 的 Feed/日报被 backlog 虚标完成，本质是整条生产管道缺失（M2）；参考分析2 的事件方案存在跨进程拓扑错误，已用 outbox 方案修正（M3）；两份参考共同的盲点是 CI 无 PG 导致测试门禁虚设（4.1.1）——建议它作为第一个动工项。
