## 4. 辩证：P-113 为什么由规划方亲做、为什么要发 v1.1.1
- **支持亲做**：它跨"所有出站 provider + 所有日志出口"，修错位置（逐个调用点改）会漏；判断"在哪一层修"是架构决策，属规划方。
- **反对**：规划方本轮任务是规划，改代码违反"默认只读"。⇒ 处置：代码改动单独一个提交（`fix(STEP-40 …)`），与规划提交分开；先红读数、改后读数、全量回归都入证；独立复查交执行助手在 STEP-42 开工时做（只看 diff + 运行结果，输出 PASS/FAIL）。
- **为什么不只改 httpx 日志级别**：调成 WARNING 只堵住第 1 条路；`HTTPStatusError` 的文本自带完整 URL，provider 用 WARNING 打它（`justoneapi.py:206`），照样泄漏。⇒ 必须在**渲染后的整行文本**上遮蔽。
- **为什么 query 整段省略、不按参数名**：各家凭据参数名都不同（access_token / key / token / sign），白名单维护不起来，漏一个就白做；query 的诊断价值低。
- **代价（反证）**：日志里看不到 query 了，排查"带了什么参数"要靠调试级本地复现；路径里 ≥16 位的令牌形段（含 UUID）在**绝对 URL** 里被遮——出站 URL 的资源 id 也看不到。相对路径（入站）不遮段，资源 id 仍可审计。
- **为什么发 v1.1.1**：v1.1.0 已公开发布，任何按它部署并真实推送的环境都会把 webhook 凭据写进日志；补丁版是给部署方的明确信号。
- **残余风险**：把凭据写成裸字符串（不在 URL 里）打日志的路不归遮蔽管——这是调用点错误，由审查与 gitleaks 兜。
