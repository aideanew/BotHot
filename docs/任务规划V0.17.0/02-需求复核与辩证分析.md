# 02 需求复核与辩证分析（V0.17.0）

## 1. 复述
用户 2026-10-20 两条指示：
1. "完成所有核心任务后，更新到最新规划目录、推送同步，交给助手执行。我不懂开发，只要结果。"
2. "核心任务是指本项目的核心功能、架构、设计等必须 5 年以上架构师/开发者才能高效完成的部分；普通 2–3 年开发者能做的交给助手。不是让你完成大部分工作。"

## 2. 怎么判"核心"（D-V17-01 的判据）
| 判据 | 归规划方 | 归执行助手 |
|---|---|---|
| 改的是不是**契约、权限边界、跨域设计** | 是 | 否 |
| 做错了会不会**静默**造成安全或数据问题、且常规测试抓不到 | 会 | 不会 |
| 有没有**现成判据**可照做 | 没有，要先定判据 | 有 |
- **支持**：按这把尺子，21（越权矩阵 + 冻结权限三类）、01（契约语义真源换路）、13（引擎能力面契约）是规划方的；19（按卡面补测）、15/15b/14b（按已冻结契约写前端）、12（对账汇总）是执行助手的。
- **反对**：14b 有"UI 设计"字样，像是设计工作。**判**：四屏已存在，余下 3 项是在现有组件体系里加告警条与配置页，有现成样式与 `LoadingErrorShell`，不是新设计体系 ⇒ 执行助手。
- **反对**：审计日志（P-49）实现量小，为什么不直接交执行助手？**判**：实现交执行助手（31），但**记什么、不记什么、记在哪**是安全设计，做错会泄露凭据或漏记 ⇒ 规划方先冻结为 D-V17-02。

## 3. P-49 审计怎么落（D-V17-02 的支持/反对）
- 方案 A（选定）：零迁移的结构化审计日志，按路由前缀与方法自动覆盖。
  - 支持：不占迁移号，不进关键路径（28/08/09 迁移串行）；按前缀覆盖，新增写接口自动被记，漏记不会复发。
  - 反对：日志可被轮转丢失、不便查询。**缓解**：字段固定，可被日志平台检索；确有查询需求时，08/09 之后再立表（届时只是换载体，字段不变）。
- 方案 B：现在建 `audit_events` 表。否决：占迁移号、与 28/08/09 串行，拖慢关键路径；当前没有"按操作者查历史"的产品需求。
- 方案 C：在端点里逐个写日志。否决：新端点必然漏记。
- **MUST NOT**：记录请求体、响应体、查询串、请求头（推送渠道写操作的请求体里就有 webhook 与 app_secret）。
