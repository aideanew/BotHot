# 02 需求复核与辩证分析

## 1. 复述与拆解
**核心问题**：BotHot 是挂在 Aidean 主平台下面的公众号内容中台。它采集公众号文章，规范化入库，做热点聚簇和日报，提供 RAG 问答，并把内容按 Cron、事件或手动方式推送到飞书、钉钉、企微、Webhook 和站内通知（`docs/02_requirements/product-requirements.md` REQ-F-001～008）。
- **用户**：主平台 SSO 登录的普通用户（只读 Feed、问答、订阅、站内通知）。
- **管理端**：operator（运营：渠道、推送任务、热点、日报、采集作业）和 admin（全部 + 跨用户管理、引擎 key）（REQ-F-007/008，identity 契约 `x-rank`）。
- **系统边界**：前端 3200 / 后端 3300；主平台 3000 只作 OIDC IdP，不占用（REQ-C-002）。付费采集源（TikHub、WellByte、Dajiala、JustOneAPI）与 LangBot 属于外部依赖。
- **关键词**：规范键、清单状态机、多源降级、推送三触发、站内通知历史、角色阶梯、契约唯一源、真库验收、跨平台 CI。

## 5. 隐含要求与前置条件
- 推送任务能建出来，是 M-PUSH-HIST、STEP-21 IDOR 矩阵、15b e2e 的共同前提 ⇒ STEP-24 必须排第一。
- 前端 mock 默认开启时，UI 层的任何验收都不能证明后端可用 ⇒ 15b 之前的 UI 验收一律附真实后端截图或网络记录。
- 角色语义改动会扩大授权面 ⇒ 必须有逐端点矩阵和一轮安全复核（STEP-25 S25.1.2 + opus 券）。
- 新增连库用例会改变 CI-Windows 的 skip 基线 ⇒ 按 D-V10-11 程序重测（24/25/26 都会触发）。

## 6. 深度分析（5W1H → 追问 → 钢人 → 终判）

### 6.1 What
- 已证明：00H/22/23/20/02-S2.4 已交付，三条工作流绿；本机全量 1570 passed，唯一失败是环境泄漏（01 §3、§4）。
- 新缺陷：推送任务创建 500、operator 写 403、`/admin/push` 不写历史、两条裁决没有门、证据脚本红、前端 mock 默认开（01 §5）。
- 只是声称、没被证明的：执行方说「CI-Windows 卡死的根因是 PG 无连接超时」——本版只能证明「修了之后 Windows 绿了、黑洞下有界了」，单因归属仍是**部分确认**（Windows 原生环境不可在本机复现）。

### 6.2 Why
- 直接原因：`bots.py:325` 的兜底字面量；10 个调用点写了两个参数。
- 根本原因：(1) 推送写接口**零连库用例**，所以 CI 全绿和"能不能用"无关；(2) 前端默认 mock 让手工点验也看不到 500；(3) 契约写的是 max，docstring 写的是 min，作者按 docstring 写调用点——**同一语义存在两份文本**。
- 只改表面会怎样：只把 `"system"` 换成某个 admin 的 id ⇒ 500 消失，但归属仍可伪造；只把 max 改成 min ⇒ 契约被静默改写，以后谁写多参数谁就扩大授权。

### 6.3 Where / When
- 文件：`apps/api/app/api/v1/bots.py`、`hot.py`、`app/services/roles.py`、`services/push.py`、`apps/web/components/PushTasksTab.tsx`、`lib/api/bots.ts`、`lib/api/http.ts`。
- 时序：24 → 25 → {26, 21, 15b}；Guard 线与 API 线（10/05）跟 24/25 文件不相交，可以同时开工。
- 端口：BotHot 前端 3200、后端 3300；本版没有任何改动涉及端口（AGENTS.md 端口段）。旧模板里写的「AideanBot 3333」已经退役，`guard-ports` 会拦（06）。

### 6.4 Who
- 规划方自做：24、25（核心 + 安全）、15b、14b（UI）、21、19、13、15、01、12。
- 执行方：Guard（00H/00T/00R/00X/00P/00E/06/18）、API（04/10/05/11/14a/26/RV）、Data（07/08/09）、Doc（17）。
- 只有用户能定的：Q-1～Q-4。

### 6.5 How
先红（新用例在未改代码上红，原文入 EVD）→ 最小修复 → 真库全量 + `@ci` 三绿（核对 `head_sha`）→ 独立验证者只输出 PASS/FAIL/UNKNOWN → 同一判据连续 2 次 FAIL 就熔断（D-14，00T 增量把它变成机器门）。

### 6.6 What if
| 前提变化 | 结论如何变 |
|---|---|
| 主平台 SSO 首登不建本地 `users` 行 | STEP-24 拿不到 `users.id` ⇒ 停在阻塞条件，升级 fable 裁决列语义（不能兜底字面量） |
| 用户认为 operator 不应有推送写权 | D-V11-01 改为把 10 个调用点写成 `require_roles("admin")`；守卫与矩阵不变，只换期望列。代价：STEP-22 卡面「operator 得 200」要改窄 |
| PG 不可用 | 连库用例按 skip 门计 `pg_unreachable`；`/health` 有界返回 degraded（已证） |
| 接口字段变化（删除请求里的 `created_by`） | pydantic 默认忽略多余键 ⇒ 旧前端不会 422；契约 dto 的响应字段不变 |
| 端口被占用 | `guard-ports` 只校验配置；运行时占用不在本版范围 |
| 测试绿但运行时失败 | 正是 F-V14-01 的形态 ⇒ 每张卡都要附探针复跑 |
| 执行方改的文件与本卡面不一致 | 以 `git diff` 为准，越出允许面 ⇒ 独立验证判 FAIL |

### 6.7 苏格拉底追问（每条关键结论一轮）
1. 「推送任务功能不可用」凭什么？——真库探针两条路径都 500；有没有反证：有没有别的创建入口？`git grep -n "PushTask(" apps/api/app` 只在 `create_push_task` 中构造任务（调度器只读）。前提：生产库也有这个外键——模型声明了 FK，迁移由 alembic 生成；生产 DSN 没有，所以"生产上也 500"是**高度可信的推断，不是已确认**。
2. 「operator 应该有写权」凭什么？——调用点代码、D-V10-04、REQ-F-008。反证：有没有需求说"渠道写只给 admin"？`grep -n "admin-only\|仅 admin" docs/02_requirements` 未见推送域条目。结论在"业务确实要运营管推送"的前提下成立 ⇒ 登记为 N-2，What-if 给出反向方案。
3. 「1 failed 不是回归」凭什么？——同一用例清空环境后通过；CI 不设该变量且 CI 绿。局限：没有在 CI 上构造这个变量来复跑。

### 6.8 双向钢人
- **方案 24（服务端取 users.id）**
  - 支持：消除 500 和伪造两个问题；不迁移；前端改动小。
  - 反对：历史行如果有 `"system"`（例如在 SQLite 开发库里）会让列表显示异常 ⇒ S24.3.1 只读审计覆盖；如果业务想要"代某人建任务"，这个方案就不支持 ⇒ 需求里没有这个场景（`grep -n "代建\|代他人" docs/02_requirements` = 0）。
  - 结论：采纳；残余风险是生产存量未测（Q-2）。
- **方案 25（单参数化，不改 max）**
  - 支持：契约不变；守卫让同类错误不能再写出来；行为变化范围精确到 10 个端点。
  - 反对：operator 获得删除渠道的能力，误删风险上升 ⇒ 写操作都有 PushLog 和审计中间件？**证据不足**（本版没有核对推送域写操作是否进审计日志）⇒ 登记 R-V14-03，归 STEP-21。
  - 结论：采纳，附一轮安全复核。

### 6.9 终判
- **结论**：本版可以进入执行。P0 是 24 和 25（规划方自做），并行线是 Guard（00H 收尾 / 00R / 00T）和 API（04 / 10 / 05）。
- **依据**：01 §4–§5 的现跑读数、两份探针、CI 三绿、本机全量。
- **前提**：Q-1～Q-4 不影响 M0/M2 的推进；N-1、N-2 成立。
- **局限**：生产侧读数未测；Windows 单因归属只是部分确认；推送域写操作的审计覆盖证据不足。
- **是否允许进入下一阶段**：允许（M0-P0 开工）；M4 发布收口（STEP-12）要等 Q-2 和 Q-3。
