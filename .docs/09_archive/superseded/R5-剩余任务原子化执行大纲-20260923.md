#### R5.1.2 PKCE 机制裁定与文档

| 字段 | 内容 |
|---|---|
| **当前** | 纯 session cookie，无 id_token 验签；`service.py:5-6` docstring「替代本地验签」，完全信任 userinfo 端点 |
| **裁定** | **不引入 PKCE / OAuth2 客户端模式** |
| **理由** | ① AideanBot 是主平台内嵌应用（OIDC code flow 已完成认证），session cookie 是派生会话机制；② PKCE 适用于第三方授权码场景，在本平台内嵌场景无额外安全收益；③ 引入 PyJWT 依赖会改变后端供应链，且 session cookie 的 SameSite=Lax 已提供基础 CSRF 防护（`auth.py:78-87` HttpOnly + SameSite=Lax） |
| **回退路径** | 若管理者裁定引入，需新增 `PyJWT` 依赖 + 修改 `service.py` 兑换流程；回退成本 = 1 个 commit |
| **涉及文件** | `backend/app/services/auth/service.py` docstring 补充「为何不做 PKCE」说明（纯文档改动，1 行注释） |
| **验收判据** | L1：docstring 已更新，明确记录「不引入 PKCE」的决策 |
| **规模** | S |
| **依赖** | 无 |

## 四、管理者裁定建议（4 项，均附理由与回退路径）

### R5.A Sources 权限模型（R4.2.2 原定）

**裁定建议：不加 user_id，保留当前 admin-only 模型**

| 理由 | 说明 |
|---|---|
| ① sources 是共享资源 | `sources` 表无 user_id，设计目的是作为订阅引用对象（`subscriptions.py:4-6` docstring 明示「全用户共享源清单」） |
| ② 现有权限已收口 | PATCH /sources 和 DELETE /sources 均收口 admin（`subscriptions.py:92,113`），这是正确的系统级资源共享模型 |
| ③ 引入 user_id 的代价 | 需迁移所有现有 source 行的 user_id（回填），且会改变订阅引用的跨用户语义 |
| 回退路径 | 若未来需要私有 source，添加 `user_id nullable` 列，新 source 强制写 user_id，旧 source 保持 user_id=NULL（全局共享） |

### R5.B PKCE 引入（R4.3.2 原定）

**裁定建议：不引入 PKCE**（见 R5.1.2 完整理由）

### R5.C 用户删除空间（R4.7.3 原定）

**裁定建议：纳入**

| 理由 | 说明 |
|---|---|
| ① 后端已完整 | `spaces.py:173` DELETE /spaces/{id} 已具备，引擎先删 → 文档表 CASCADE，顺序正确 |
| ② 空间是用户资产 | 空间由用户创建，前端不暴露删除能力是功能缺失，不是安全考量 |
| ③ 无安全顾虑 | DELETE /spaces/{id} 已强制 `space.user_id == actor.id`（本人归属），不会跨用户误删 |

### R5.D 批量删除 sources（R4.8.4 原定）

**裁定建议：不纳入**

| 理由 | 说明 |
|---|---|
| ① 单条 DELETE 已具备正确保护 | `subscriptions.py:113-129`：零引用闸门（subscription/assets/manifests 三者皆空才允许删） |
| ② 批量操作无明确场景 | sources 是系统共享资源，批量删除的使用场景不明确 |
| ③ 复杂度不成比例 | 批量执行零引用闸门需在单个事务中逐条检查，实现复杂度高而收益低 |
| 替代方案 | 管理员可先查询 `GET /sources` 筛选目标，逐条调用 `DELETE /sources/{id}`；或在管理台增加「批量清理零引用 sources」的 UI（但后端仍是逐条） |
