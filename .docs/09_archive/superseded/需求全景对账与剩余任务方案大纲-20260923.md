代理在数据域报称「号主改文 → `mark_stale_docs` 把**另一用户空间**的 doc 标 FAILED/superseded」。本轮实读 `backend/app/repositories/asset.py:106-123`：

```
select(KnowledgeDocument).where(
    KnowledgeDocument.asset_id == asset_id,
    KnowledgeDocument.space_id == space_id,   # ← 有空间过滤
```

调用点 `backend/app/services/kb.py:240` 传的是 `space.id`（当前入库空间）。故 `mark_stale_docs` 是**空间内**语义，不跨用户标 FAILED。**真实缺陷更微妙**，见 §4.2 之 F-11：共享 asset 行被覆写后，其他空间的 doc **静默指向已变正文**，既不重入库也不标 stale —— 比「跨用户标 FAILED」更难发现，因为**不产生任何错误信号**。

### 2.1 拷问 1：「生产默认 MOCK 态」是真缺陷，还是文档化的合理默认？

- 支持「不是重复」：R3.2 是一个**动作**（跑一次 e2e）。但本轮查出的 SSO 相关缺口是**五个不同的子问题**：① userinfo 不校 `iss`/`aud`（`service.py:64-67` 只查 sub 非空）② `id_token` 不验签、无 PKCE（`client.py:37-48,83`）③ `oidc_client_secret` 默认 `"change-me"` 且**无启动期非默认值断言** ④ `session_cookie_secure` 默认 `False`（`config.py:38`）⑤ `session_store_backend` 默认 `memory`（`config.py:41`，重启全体掉线）。**其中 ②③④⑤ 四项 R3.2 完全没覆盖**——它们不是「跑一次 e2e」能解决的，是**信任模型与配置守卫**问题。

### 2.3 拷问 3：R2.1「scheduler/job_worker 进程化部署」已登记 —— 那我这轮关于 U7 的发现是空转吗？

**致命追问**：R2.1 原文「scheduler/job_worker 进程化部署（compose 增 worker 服务 + `main.py` 挂接）—— 核心3 的投放缺口，**最高优先级外部锁**」。**我已经知道这件事了。我的价值在哪？**

**双向钢人**
- 支持「空转」：R2.1 已登记且标为最高优先级，我重复。
- 支持「非空转」：**三处实质错误**：
  1. **标签错**：标为「外部锁」，但 compose 是仓库内文件、`main.py` 是仓库内文件、部署手册是仓库内文件 —— **零外部依赖**。这是一项**纯内部施工**。把一个成本最低、影响最大的项标成「外部锁」，等于**在排期语义上把它降级**——读者会以为它在等别人。

**幸存结论**：R2.1 **不重编号**，但在本轮**显式更正其失实锚**（标签 + 括号歧义），并新增其遗漏的第三条腿。这是 AideanBot 自身约定的「实测更正——更正失实锚而非静默删除结论」的正例。**U7 是本轮确认的最高优先级项，理由从「外部锁最高优先」变为「纯内部施工、零外部依赖、当前产品目标 3 与 U7 完全不可达」**。

### 2.4 拷问 4：「前后端交互是否经过测试」—— 有 playwright e2e 且 last-run 是 passed，答案该是"是"吗？

### 2.5 拷问 5：「14/50 后端端点无前端调用方」—— 其中约 5 个是裁定不建 UI，我把裁定不建的算成缺口了吗？

**双向钢人**
- 支持「越权」：裁定纪律是本项目的核心资产。把裁定不建的列成缺口，读者会以为可以翻案。

### 2.6 拷问 6：`DELETE /sources/{id}` 仅登录即可 —— 但 sources 按 biz 全局唯一是设计，删除全局源不是越权而是运维吗？

**致命追问**：A-2 裁定「admin 变体不增能力」的理由是**源是全局共享实体，不需要按用户分**。既然源本就全局，那**登录用户删除一个源，在数据模型上是合法操作**。我是不是把一个设计选择误报成越权？

**双向钢人**
- 支持「是设计选择」：`entities.py` 的 `sources` 表**没有 `user_id`**，`UniqueConstraint` 按 `biz`；`register_source` 收 `user_id` 但不落库（`subscription.py:80-102`），`list_sources` 忽略 `user_id` 返回全局全量（`:105-114`）。**整个表就是全局语义**。全局表 + 全局删，自洽。
- 支持「是越权」：自洽 ≠ 正当。**授权问题不在数据模型，在「谁有权做全局动作」**。当前 `DELETE /api/v1/sources/{id}`（`subscriptions.py:78`）的门禁是 `get_current_user_id`（仅登录），而同一文件里 `subscriptions` 的四个端点都是「登录 + 归属」。删除一个源会波及**所有依赖它的订阅**。A-2 裁定回答的是「admin 要不要额外的 source 端点」，**从未回答「普通用户要不要有全局删除权」** —— 这是两个不同问题。

**幸存结论**：**成立，且是本轮最高优先级的单点安全发现。** 定级 P0 的理由：它是**唯一一个"普通用户可单方面破坏其他用户数据"的现役路径**（`mark_stale_docs` 那类是静默不一致，这个是显式删除）。但**修复方式需管理者裁定**（提秩至 admin vs 移除端点 vs 加引用计数守卫），因为 A-2 的语义边界需要复核 —— 不越权替管理者做架构决定。

### 6.5 一处「险些误报」的取证纪律留档

本轮核验 R5.2.3 时，实测发现 `langbot/client.py:208` 注释写「实测 v4.10.9：`...similarity?`」，与 R5.2.3「把 `similarity` 改为 `score`」看似矛盾，**险些被登记为新缺陷**。

追查 M0 能力实证总报告 §四 B-T8：**「字段是 `score`/`distance`，原文写的 `similarity` 不存在」**。结论翻转：**注释本身是已被实测推翻的过期注释，R5.2.3 的修正是对的**。

真实的新发现是**反向的**：① `client.py:208` 过期注释 + `test_langbot.py:84`、`test_metadata_filter.py:59`、`test_p4_engines.py:79,97` 四处桩仍用 `similarity`，与修正后的 `test_chat_sse.py` 口径分裂（→ R6.6.4，P3）；② 更实质的——`chat.py:124-127` 仅在 reranker 有结果时重排，否则**保持 LangBot 原始顺序**，而该顺序基于 LangBot 未使用的 `score` 字段，**即无 reranker 时排序未定义**（→ R6.6.5，P2）。

**留档理由**：本轮全部结论都经过了"再查一层"，这一条记录了**再查一层会推翻我自己**的情形——取证纪律必须对取证者本人生效。

**不推翻 R5。** R6 复核批逐项复验了 R5 的 10+ 项可静态验证声明（admin.ts 6 导出 / `deleteSpace` / 5 页行数 / `_verify_userinfo_claims` 实装与调用 / compose 9 服务 / prebuild 守卫 / eslint 依赖与配置 / R5.3 sources 裁定 / 阻塞项登记表建立），**无一失实**（1 处文件名偏差：实为 `.eslintrc.js` 非 `eslint.config.mjs`，不影响功能）。R5 在其声明的 **L1 静态范围**内确实竣工。
