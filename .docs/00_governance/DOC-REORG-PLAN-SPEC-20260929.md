## §5 第二轮拷问记录（苏格拉底追问 + 双向钢人，仅录幸存裁定）

**Q1 为什么要动？不动行不行？**
反方（钢人）：文档都能找到，迁移有断链与并行会话风险，收益是"美观"。正方：42 个文件平铺、六类信息混放，新会话冷启动必须通读 178KB 索引才能定位；历史大纲与在役大纲同层混放，"哪些还有效"只能靠人脑记忆——这正是本规范 §2 要解决的 18 问。**裁定：动，但以"纯迁移+历史不回写"把破坏面压到最小。**

**Q2 目录名用规范英文、文件名要不要跟着英文化/编号化？**
追问：全量英文化能带来什么？破坏什么？——台账、记忆、历史文档中数百处中文路径引用全部失效（历史不回写=永久断链），收益仅为风格统一。**裁定：目录用规范名（00_governance 等），71 个既有文件名一律不改（规范 §32"ID 必须稳定"）；新文档起走规范 ID。**

**Q3 `.docs` 要不要改名 `docs`？**
**裁定：不改。** 台账/记忆/所有历史文档引用 `.docs/`；点前缀还避免被前端构建扫描。改名收益为零、断链为全域。

**Q4 要不要把存量文档回溯改造成 REQ-F-/TASK- 编号体系？**
**裁定：不回溯。** 项目自有 T/R/D/N 四套编号且互转表在维护，台账按追加唯一锚纪律运转；回溯重编号=系统级引用破坏。规范对**新增**需求/任务生效（inbox → REQ 编号），存量按"偏差登记"兼容。

**Q5 台账 569KB、索引 178KB 要不要趁势拆分？**
**裁定：本轮不拆。** 台账是并行会话追加唯一锚的锚定文件（实证：`.workbuddy/memory/2026-09-28.md` 未提交修改说明并行会话活着），拆分风险>收益；本轮只改其**追加新节**与索引路径列。台账超 1MB 时再立专项裁决（登记为观察项）。

**Q6 R8/R9 放 planning 还是 solutions？R5/R6/R7 为何归类不同？**
判据=信息类型而非编号字面：跨波次总纲（R6 编号权威、R7 全景矩阵、T 系主大纲、当前态）→ planning；单主题执行方案（R8=RedFox 对接、R9=SSO logout、5 份 SPEC）→ solutions。**裁定：按此归类，判据写入 project-map。**

**Q7 `01_product` 与 `07_release` 建不建？**
**裁定：均不建。** 产品目标已在 README+需求文档 §一（单源）；项目无发布事实。裁剪偏差登记于 project-map，附启用条件。

**Q8 html 重复件删还是归档？**
**裁定：先等价性验证（文本抽取对比 md），等价→删（md 为权威源，git 可溯）；不等价→随 md 一并归档。** 0 字节空文件直接删。

**Q9 `.workbuddy/`（127 个被追踪文件，含大量证据）要不要并入 `.docs/06_validation/evidence/`？**
**裁定：不动。** 它是执行体工具私有工作区，且有并行会话正在写入（未提交修改在案）；强行迁移会破坏其他执行体上下文。project-map 登记其为"证据存放地"，evidence 索引引用其路径即可。
