### D3.5：与积分无关的三处致死缺陷（R8 已修，v1.5 及以前完全未登记）

| 项 | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| **F1 契约错** | 客户端调的是优质库 `/story/api/gzhData/queryWorkList` + `{biz, page}` | 上游恒定 `code 500`，整条发现链从未成功过 | 改用广域库 `/story/api/gzh/data/queryWorkList` + `{bizInfo, offset, sortType}` |
| **F2 字段错** | `_URL_KEYS` 缺 `workUrl`（广域库**没有** `url` 键） | 入库 `url=""` → `job_worker.py` 抛 `ValueError("item.url 为空，无可采地址")`，**100% 硬失败** | `_URL_KEYS` 首位补 `workUrl`；历史空 `url` 行由下一轮同步原地补齐（`_apply_update` 差异更新），**无需数据迁移** |
| **F3 时区错** | `_parse_time` 把无时区串当 UTC（广域库 `publishTime` 是无时区北京时间串） | 全部文章时间**整体早 8 小时** | `UPSTREAM_TZ = ZoneInfo("Asia/Shanghai")`，无时区值按该时区解释 |

**为什么这三项之前 42 天无人发现**：`tests/test_redfox_client.py` 与 `tests/test_manifest_sync.py`
把**错误契约写进了断言**（`body == {"biz": ..., "page": ...}`、mock 行用 `"url"`），测试因此
自我认证为「通过」。这是与 D17/D20 同一根因的第三次出现：**测试断言的是实现者的猜想，
而非上游的真实契约**。R8 已用真实行形状（含 `workUrl`、无 `url`、`content=None`）重建断言。

## D25：调度器双重认领竞态（同一轮内同一订阅被同步两次，按次计费被重复扣费）

> **新增（v1.9，2026-09-28）**。在验证每日锚点特性时由全量 `pytest` 复现暴露，**本条直接触及「不要把余额给我花光」这条硬约束**。

| 字段 | 内容 |
|---|---|
| **现象** | `tests/test_manifest_sync.py::test_scheduler_error_advances_watermark_without_polluting_empty` 在全量运行时以 `assert 2 == 1` 失败，日志中 `scheduler 同步失败 subscription=t22-err` **出现两次**——即同一条订阅在同一轮内被 `_sync` 调用了两次。**单独运行稳定通过**，全量运行时以约 **4 成概率**复现（连续 5 次全量跑中 2 次失败） |
| **根因** | `_process_one()` 的**错误路径**做了两次分离的操作：<br>① `await session.rollback()` —— 回滚同步的失败写入，但**同时释放了 `claim_due` 的 `FOR UPDATE SKIP LOCKED` 行锁**；<br>② 再另起一个事务提交水位推进（`_advance_after_error`）。<br>两步之间存在一个窗口：该行 `next_run_at` **仍早于 now**（水位尚未落库），但行锁已释放 → `run_once` 的 `asyncio.gather` 派发的其余 `scheduler_concurrency-1` 个并行认领者（默认配置 `scheduler_concurrency=4`）能认领到**同一条**订阅，把 `_sync` 又跑一遍 |
| **危害（直接对应预算约束）** | 发现阶段的 RedFox 清单调用**按次计费**。重复认领 = 同一轮内对同一份清单发起重复的按次计费请求。这不是「多算几次」的良性重复，而是**用户余额的重复消耗**，且**完全静默**——两次同步各写各的，最终水位只有一个，看不出任何异常痕迹 |
| **为何此前 42 天未暴露** | 成功路径本来就是同事务提交，只有**错误路径**存在该窗口；而错误路径在生产中只在「上游 3201 / 5xx」时才触发——恰好是 D3 长期处于阻塞态期间的常态。也就是说**该缺陷只在调度器真正开始干活之后才会咬人**。此外模块 docstring（`scheduler.py:16-17`）一直写着「认领 + 入列 + 水位推进在**同一条事务**内完成」，实现与文档不符——与 D22（外部文档与实测不一致）属同一类缺陷，只是这次是**自家文档与自家实现不一致** |
| **修复** | ① 用 `async with session.begin_nested()`（SAVEPOINT）只包住 `self._sync` 这一半的写入；<br>② 错误路径的水位推进改为在**同一事务**内完成（`sub.next_run_at = ...` + `await session.commit()`），行锁持有到水位落库，**窗口消失**；<br>③ 删除 `_advance_after_error()`——唯一调用点已内联，无其他测试引用。<br>SAVEPOINT 安全性已预先验证：`_create_sync_job` 只 `flush`、`create_or_get` 自带 savepoint、`run_incremental_sync` 从不 `commit`，故内层不会提前结束外层事务 |
| **验收（直接检测器，而非巧合）** | 把该用例从「断言最终状态」升级为**直接断言 runner 只被调用一次**（`calls == 1`）——若再出现重认领，测试报的将是明确的「同一条订阅被认领 N 次」，而不是一个看不出原因的 `assert 2 == 1`。**连续 5 次全量跑零失败**（修复前 2/5） |
| **⚠️ 接受的权衡（须留档）** | 语句级错误（死锁 / `SerializationFailure`）会**中止外层事务**，SAVEPOINT 无法恢复；这类错误现会上抛至 `_claim_and_process_one` 的兜底捕获并结束本轮，由下个 tick 重试。这是**有意的 at-least-once 方向**：宁可重试一次（可能被 SKIP LOCKED 挡下而零消耗），也不要在事务已损坏时尝试提交。与模块 docstring 声明的 at-least-once 语义一致 |
| **残留** | 无代码残留。该缺陷**只存在于错误路径**，故「日常跑测试是绿的」不足以排除此类问题——本条的存在说明**并发 + 事务边界**这类缺陷只能在错误路径 + 高并发配置下被看到 |

## D26：仓库零本地门禁——反馈回路只有 CI（同类红灯已连续两次）

> **新增（v1.10，2026-09-28）**。与 D24 同属「门禁」议题但方向相反：D24 是 **CI 覆盖不足**，
> D26 是 **本地覆盖为零**。（编号避开已被调度器双重认领竞态占用的 D25。）

| 字段 | 内容 |
|---|---|
| **现象** | 实测仓库**没有** `.pre-commit-config.yaml`、`.git/hooks/` 下**只有 sample**、`pre_commit` 未安装。所有门禁（ruff / mypy / tsc / vitest）**只在 CI 上跑** |
| **后果（已实证两次）** | ① §56 前端 `t0263` 微任务竞态——只在本机 Windows/UTC+8 跑过，CI 的 UTC + 慢 runner 踩中；② §60 后端 `ruff UP038` + `mypy arg-type` 双红——本地**零机检**，违规直接入库。两次**同一成因** |
| **更严重的次生问题** | §60 取证发现：提交 `7cf0c16` 记录写「**725 passed**」，而干净容器复现为 `ruff` **exit 1** / `mypy` **exit 1** / `pytest` **354 passed**。**725 只是「只跑 pytest」的数**——两道门禁在该提交上**从来没绿过**。属**记录层面的假绿**（§56.6-1 的同型再犯，这次进了报告） |
| **处置（已实施）** | 新增 `scripts/preflight.sh`：CI 四道门禁搬到提交前（`ruff` / `mypy` / `tsc` / `vitest`），后端两关**与 CI 同命令**，前端 `vitest` 强制 **`TZ=UTC`** 与 runner 同构。头部写入三条铁律：退出码**禁管道**、前端**必须 UTC**、缺工具**须报错不可静默跳过** |
| **未上锁** | preflight **需手动跑**，是「补回路」不是「上锁」。彻底闭环比 pre-commit hook（需 `pip install pre-commit`、且 hook 可 `--no-verify` 逃逸）更重；**「是否上锁」待裁定**。不强推 hook 的理由：hook 装不上时 CI 仍会红，而**脚本 + 纪律**不会留下「以为有防护」的错觉 |
