## 二、Redfox 实证详情（T0.2）

### 优质库
- `POST https://redfox.hk/story/api/gzhData/queryWorkList`
- 定位：`account`（公众号微信号，必填）+ `accountName`（可选）
- 时间过滤：`publishTimeStart`（**最早 2026-04-01，不传默认此值**）/`publishTimeEnd`——优质库数据覆盖有边界
- 响应字段：`workUuid/workUrl/publishTime/title/summary/readCount/isOriginal/orderNum...`

### 广域库
- `POST https://redfox.hk/story/api/gzh/data/queryWorkList`
- 定位：`account`/`wxId`/`bizInfo` 三选一，优先级 **wxId > bizInfo > account**
- **`bizInfo` 即文章 URL 的 `__biz` 参数**（示例 `MjM5MDMyMzg2MA==` 与 URL 中 `__biz` 同构）
- 响应：清单含 `workUuid/workUrl/publishTime/title/bizInfo/author`；`content` 恒为 null（**列表不含正文，正文需直抓文章页**）

### 计费与限流
- 鉴权头：`REDFOX_API_KEY` 或 `X-API-KEY`
- 实测单价（优质库）：**0.4 积分/次**；当前余额 0.0 → 数据级验证（定位成功率、清单完整率、分页游标行为）**待充值后执行**

**R8 新确认的契约事实**（此前全部未验证，代码是按文档推导的）：
`total` 位于 **`data.total`**（非顶层）；行**含 `workUrl`、无 `url` 键**；`publishTime` 是
**无时区北京时间串**（如 `2026-09-27 07:42:00`）；分页 `offset` 为 **0 基、步长 20、页间零重叠**，
时间线倒序无缝拼接。

**由此暴露的三处与积分无关的致死缺陷**（详见《阻塞项登记表》D3.5）：

| | 缺陷 | 后果 |
|---|---|---|
| F1 | 调错接口 + 传错请求体键 | 上游恒定 500，发现链从未成功过 |
| F2 | `_URL_KEYS` 缺 `workUrl` | 入库 `url=""` → worker 抛 `ValueError`，**100% 硬失败** |
| F3 | 无时区时间按 UTC 解析 | 全部文章时间**整体早 8 小时** |

**F2 与积分无关——「等积分到位」永远修不好它。** 这是本次复验最重要的结论：42 天来
围绕「充值」等待，而真正阻断采集的缺陷在代码侧且与余额无关。

**成本模型（与单价无关）**：清单同步已改为增量化，稳态与空日均为 **1 次调用/号/轮**
（原为固定 10 次）。即使按 M0 的 0.4 计，稳态每日约 0.4 积分/号，仍比红狐自家订阅
（1000 积分/号/年 ≈ 2.74 积分/天）**便宜 6.8 倍**；1 次/天是信息论下界。

**新增阻塞（与凭据无关）**：`searchUser`（关键词搜号，文档 `interfaceNo=5Y84NI1D`）
**上游故障**——连文档自带的示例关键词「十点读书」也返回 `code 500`，两次复测一致。
红狐一侧已无第二条可用通道，见《阻塞项登记表》D21 / D22。

**确立的纪律**：**此后凡涉及 RedFox 的新能力，一律先实测一次请求再写代码**；官方文档
降级为「未验证线索」，不作契约依据。`registry.py` 新增 `contractVerifiedAt` /
`verifiedScope` 两个字段把该纪律机器化，使「契约已实测」成为可被后台查询的事实。

### API 全链（均已验证）
```
POST /api/v1/user/init          首次管理员（需合法 email）
POST /api/v1/user/auth          登录 → JWT
POST /api/v1/provider/providers {name, requester, base_url, api_keys}
POST /api/v1/provider/models/embedding {name, provider_uuid, extra_args}
GET  /api/v1/knowledge/engines  引擎清单（caps: doc_ingestion/doc_parsing）
POST /api/v1/knowledge/bases    建库（须 knowledge_engine_plugin_id + creation_settings.embedding_model_uuid）
POST /api/v1/files/documents    multipart 上传 → file_id
POST /api/v1/knowledge/bases/<uuid>/files {file_id} → task_id（异步 ingest）
GET  /api/v1/knowledge/bases/<uuid>/files → status=completed
POST /api/v1/knowledge/bases/<uuid>/retrieve {query, retrieval_settings{top_k, search_type}} → results
```
- LangRAG 建库 schema：`embedding_model_uuid`（必填）、`index_type`（chunk/parent_child/qa）、chunk_size/overlap
- 检索 schema：`top_k`、`search_type`（**vector/full_text/hybrid**）、query rewrite（off/HyDE/Multi-Query/Step-Back）
- ingest **强制嵌入**（每批 embed+upsert）；retrieve 的 full_text 免查询嵌入

### 多库隔离（T0.5 核心结论）
- 每 KB 一个物理 collection（uuid 派生）→ **KnowledgeSpace ↔ LangBot KB 一一映射模型成立**
- 隔离验证方法论：Chroma top_k 无阈值恒返回库内最近邻，**必须用"内容归属法"**（查 A 库是否泄漏 B 库内容）而非"是否命中"
- OpenAI 兼容嵌入协议路径验证通过（本地伪嵌入服务器 host.docker.internal:18900）——主平台网关同协议形态，**协议替换面已验证**

### B-T8 复测勘误与实证补登（2026-09-07，员工B 实证 / 员工A 验收补登）
1. **登录体字段是 `user` 非 `username`**（v4.10.9 源码 `user.py:68` KeyError 实证）——上文
   `POST /api/v1/user/auth` 首探 500 即此因，M0 未记录该细节。
2. **HTTP 200 + body `{code≠0}` 表业务错误**（LangBot 惯例）；client 已按此收口 body 级检查。
3. 上传返回 `data.file_id` 为**路径形态 id**（`v1/.../xxx.md`）；KB 文件清单中文件身份在
   **`file_name` 字段（= 上传返回的 file_id）**，`uuid` 另有所指——匹配轮询必须用 file_name。
4. 清单形状 `data.engines[] / data.models[]（provider 内嵌 base_url）/ data.files[]`；
   retrieve `data.results[].content` 为**块列表**（正文在 `content[].text`）。
5. **文件级删除 `DELETE bases/<kb>/files/<id>` → 405（路由不存在）**；KB 级
   `DELETE bases/<uuid>` 实测 200——单文档移除需求挂后续版本。
6. 建库必填 `knowledge_engine_plugin_id="langbot-team/LangRAG"` + `creation_settings.embedding_model_uuid`；
   **嵌入模型注册是独立 API 步骤**（env 有 Key ≠ 已注册）——provider+model 幂等自举归入 client。
7. **勘误上文 L79**：v4.10.9 触发 ingest 响应**无 task_id 字段**（原文记载"→ task_id"不成立），
   轮询凭证以 KB 文件清单 file_name 为准（拉模式）。
8. **勘误上文 B-T8.1（2026-09-23 补）**：`POST /api/v1/user/init` 的 body 字段同样是
   **`user`，不是 `email`**（源码 `groups/user.py:78` 读 `json_data['user']`，传 `email`
   直接 `KeyError: 'user'`）——B-T8.1 只记了**登录**接口的字段，init 是同一坑的另一处。
9. **市场安装（2026-09-23 补，此前完全无文档）**：`POST /api/v1/plugins/install/marketplace`
   body 仅 `{plugin_author, plugin_name}` → `data.task_id`。**插件路由前缀是
   `/api/v1/plugins`，不是 `/api/v1/plugin/app`**（后者全 404）。
10. **异步任务状态路径（2026-09-23 补）**：`GET /api/v1/system/tasks/<id>` 的状态在
    **`data.runtime.{state, done, exception, result}`**，**不在顶层** `state`——按顶层读
    会全程得 `None`（本次因此空跑 10 分钟才定位）。另：市场安装任务最终
    `state=FINISHED` 但带 `apply_plugin_installation call timed out`，与本节「主侧超时、
    依赖按 artifact+指纹缓存、重试秒过」一致，**是已知行为不是失败**；故安装成功判据取
    **引擎在位**（`GET /api/v1/knowledge/engines` 非空），而非「任务无异常」——按异常判
    失败会误弃一个已装好的插件。
11. **勘误上文 retrieve 形状（2026-09-23 补）**：检索结果顶层键为
    `['content','distance','id','metadata','score']`——**字段是 `score`/`distance`，
    原文写的 `similarity` 不存在**。内容块键
    `['file_base64','file_name','file_url','image_base64','image_url','text','type']`，
    其中 `file_name` **等于 upload 返回的 file_id**，与 B-T8.3 的口径一致——正是
    `backend/app/api/v1/chat.py:382` 取引用标题的锚点。
