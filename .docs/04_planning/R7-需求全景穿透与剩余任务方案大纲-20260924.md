## §1 第一轮 5W1H 发散拆解

### 1.1 What（客观事实/现象是什么？）

**项目当前态**：
- git HEAD `d140c32` 已推送；代码层面 R0+R1+R4+R5+R6 已完工
- pytest 562 passed / vitest 293 passed / ruff + mypy clean
- 运行态严重落后：镜像 3+ 提交未重建、scheduler/worker 死亡、F-22 P0 数据越界漏洞在线
- 4 个知识库引擎空壳（仅 builtin 可用）
- 采集仅支持 wechat_oa（`ALLOWED_HOSTS={"mp.weixin.qq.com"}`）
- 全号订阅受 RedFox 积分=0 阻塞（D3），DEFAULT_MAX_PAGES=20 限制
- 真实后端 e2e 全部 skip（D13 阻塞）
- 公共库发布部署态恒 403（allowlist 空）
- Push 通道全桩
- 前端组件化程度高但 e2e 零执行

### 1.2 Why（深层原因/动机是什么？）

**三层根因**：

1. **凭据/授权链未闭环**：D3（RedFox 积分）、D10（引擎 Key）、D11（飞书凭据）、D13（OIDC 白名单）均为外部依赖，项目无法自主推进
2. **部署-代码双轨从未交汇**：代码修复一直在 git 进行，但从未触发镜像重建和容器重启（需管理者授权），导致"代码已修≠运行已修"
3. **引擎生态建设为零**：4 个引擎位全部空壳，非 builtin 引擎的适配器实现被锁定在外部 Key 到位后才启动

### 1.3 Where/When（适用的边界条件、时间节点是什么？）

- **时间边界**：当前为 MVP 后期，产品核心路径（单篇采集+分类+_builtin KB）已可用
- **能力边界**：微信公号图文是唯一采集源；builtin 是唯一知识库引擎；SSO 仅限 Aidean 主平台
- **部署边界**：Compose 单机部署，5/9 容器存活
- **明确不做**：抖音/B站/小红书/视频 ASR/积分体系/PKCE/compose.prod/billing

### 1.4 Who（涉及的主体/责任方是谁？）

| 主体 | 职责 | 当前状态 |
|---|---|---|
| 开发者（本 Agent） | 代码实现 + 测试 + 文档 | R0~R6 已完工 |
| 管理者 A | 授权镜像重建/容器启停 + 产品裁定 | R6.1.2/R6.1.3 待授权 |
| 外部平台（RedFox/Aidean/飞书/Coze/Dify/FastGPT） | 提供凭据/API | D3/D10/D11/D13 未到位 |
| 用户 | 使用系统 | 无真实用户使用记录 |

### 1.5 How（执行的手段、方法或实现的路径是什么？）

**剩余工作的执行路径**：

1. **运行态归一**（R6.1 遗留）→ 重建镜像 + 复活进程 → 消除 P0 在线漏洞
2. **凭据闭环**→ 逐项解锁外部依赖 → 使被锁能力可验证
3. **引擎实接**→ 按 ADR-0004 优先级逐个实现适配器 → 从空壳到可用
4. **e2e 验证**→ D13 解锁后跑通真实后端 → 使测试从 mock 升级到 L4
5. **能力补全**→ admin 扩展 / 采集源扩展 / Push 实接

### 1.6 What if（如果前提变了，结论会怎样？）

| 前提变化 | 影响 |
|---|---|
| 管理者授权镜像重建 | D15 解锁，所有 P0/P1 运行态问题一次性解决，L4 验证面打开 |

## §2 第二轮 苏格拉底致命追问 + 双向钢人

### 2.1 对"前端已完成"的追问

**追问**：11 个 page.tsx + 零 TODO = 完成？但 admin 删空间前端入口缺、real-backend e2e 全 skip、管理员 Sources 读面缺——"完成"的标准是什么？

**钢人 A（前端已完成）**：功能覆盖率 = 用户可见功能 100%；admin 删除入口只是操作便利性（curl 可用）；e2e skip 是部署阻塞不是代码缺陷。

**钢人 B（前端未完成）**：没有经过真实后端验证的前端，其"完成"只是"编译通过"；admin 删空间按钮缺意味着管理员操作需绕行 CLI；"完成"的标准应包含端到端可用性。

**幸存**：前端代码层面**功能完整**，但**验证层面未完成**。R7 须补齐 admin 前端入口 + 真实后端验证。

### 2.2 对"引擎空壳"的追问

**追问**：4 个引擎全 NotImplementedError，EngineSwitcher 展示五卡片但只有一张可点——这是"设计预留"还是"伪功能"？

**钢人 A（设计预留，合理）**：ADR-0004 明确分级；ENGINE_ORDER 提前声明让前端不必改；Key 注册系统已就绪；实接只差 API Key。

**钢人 B（伪功能，应删或诚标）**：用户看到 5 个引擎选项但 4 个灰置，体验误导；空壳代码占位但零价值；若 Key 永不到位则空壳永存。

**幸存**：空壳保留合理，但须**前端三态标注更诚实**（"未实接"比"未配置"更准确），且须**引擎实接路线图**。R7 应包含至少 1 个非 builtin 引擎的实接。

### 2.3 对"7 层去重=不会重复"的追问

**追问**：7 层去重全部在单进程内，Lock 为内存级——多实例部署时 Lock 失效，uq_doc_asset_space 的 IntegrityError 竞态窗口虽小但非零。声称"不会重复"是否过于绝对？

**钢人 A（不会重复）**：唯一性约束（uq_doc_asset_space / uq_source_type_external）在 DB 层强制，即使竞态窗口命中也只产生 IntegrityError 被回滚，不产生重复数据。Lock 只是性能优化。

**钢人 B（可能重复）**：IntegrityError 回滚后当前请求失败，用户看到错误但数据已存在——这不是"重复"但也不是"幂等成功"。用户体验不完美。

**幸存**：**数据层面不会产生重复行**（DB 约束兜底），但并发时**请求可能返回错误而非幂等成功**。R7 应评估是否需 SAVEPOINT 竞态兜底（参考 subscription.py 已有的模式）。

### 2.4 对"后台管理板块齐全"的追问

**追问**：Jobs 只有 GET、Subscriptions 只有 GET、Sources 无 admin 读面——这叫"齐全"？

**钢人 A（语义合理）**：Jobs/Subscriptions 是生命周期驱动，不应手动 CUD；Sources 已有用户面 PATCH/DELETE；admin 的核心价值是跨用户可见性，不是操作。

**钢人 B（不够齐全）**：管理员需能取消/重试 Job、取消异常 Subscription、批量管理 Sources——这些是运维刚需。

**幸存**：当前 admin **可见性已覆盖**，**操作性缺失是真实缺口**但优先级 P2。R7 应补 Job 取消/重试 + Subscription admin 侧操作。

### 2.5 对"采集某公众号所有文章=部分"的追问

**追问**：DEFAULT_MAX_PAGES=20 限制 + RedFox 积分=0 ——这两个阻塞的性质不同：前者是设计限制，后者是运营阻塞。用户问"是否支持"时，哪个才是真正的答案？

**钢人 A（支持，但有上限）**：代码路径完整（subscribe → manifest diff → job → ingest），20 页是合理的速率限制，充值后即可使用。

**钢人 B（不支持，因为无法使用）**：当前 RedFox 积分=0 意味着整个订阅管道零产出，"支持"的声明无法被任何用户体验到。

**幸存**：**代码层面支持**，**运营层面不可用**。R7 须区分两层：代码补全（无）vs 运营解锁（D3）。

### 2.6 对"SSO 正常"的追问

**追问**：OIDC 完整代码 + 541 行测试 + fail-closed 加固 = "正常"？但从未对真实 Aidean 平台执行过一次回调——这像造了一把从未开过的锁。

**钢人 A（正常）**：协议是标准的 OIDC 授权码流，FakeAideanIdP 严格模拟协议行为，iss/aud fail-closed 保证安全性；真实验证只是部署问题。

**钢人 B（未验证）**：Aidean 平台可能返回非标准字段、token 格式可能不同、回调 URL 可能不匹配——所有这些只有在真实调用后才知道。

**幸存**：**代码质量高但从未经过真实验证**。R7 须在 D13 解锁后执行真实 SSO e2e。

### 2.7 对"公共信息输出不可用"的追问

**追问**：代码完整但 allowlist 空→恒 403——这是配置问题还是设计问题？

**钢人 A（配置问题）**：代码逻辑正确（双闸门：operator 在白名单 + owner_type=system），只需填入 allowlist 即可。

**钢人 B（设计问题）**：白名单机制意味着只有预授权操作者可发布，而非任何空间拥有者可自主发布——这是产品决策，不是配置遗漏。

**幸存**：**代码与设计一致**，allowlist 是刻意的产品决策。R7 须确认：是否需要"任何用户可发布"模式（需产品裁定）。
