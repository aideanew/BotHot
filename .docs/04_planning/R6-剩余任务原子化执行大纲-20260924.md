### 2.2 Why —— 深层原因

**根因 1：验证与部署是两条从未交汇的轨道。** 所有门禁命令跑在**宿主 Python 环境**（读 git 工作树），而容器跑**镜像快照**。两条轨道之间没有任何 CI 步骤或任务把它们对齐——所以「551 passed 全绿」与「运行中的服务含 P0 数据越界漏洞」**同时为真且不矛盾**。这不是疏忽，是**缺少一个把"代码正确性"传导到"运行态正确性"的工序**。

**根因 2：能力判定与部署可达性被混为一谈。** 既有文档对"是否支持 X"的回答依据是**代码存在性**（grep 到函数即判"支持"）。B1、B2 两条断线证明：一个变量既不在 `.env` 也不在 compose 锚点里，功能就**永久不可达**，而代码 grep 完全看不出来。`check_publish_gate` 的 allowlist 硬 403 连配置提示都不给。

**根因 3：登记表是"外部等待清单"，不是"行动清单"。** D3 写"凭据超出代码仓库可见范围"——但凭据**就在仓库里**。登记表因此失效为「无事可做」，而真相是「可做且可做完了」。C1 暴露的正是这种登记与事实的漂移：**登记一次后无人复核**。

**根因 4：文档以"增量追加"演进，缺"事实收敛"机制。** 大纲 3869 行、27 次版本增补，§38.5 与 §41.6 并列存在且结论冲突；v1.3 的 §3.2 是 R5 施工**前**快照却与 §五（R5 竣工后）同处一份文件；T 骨架 35 个原子**至今 0 个打 ✅**。历史不覆盖的纪律是对的，但缺少一个**当前态权威视图**，导致每次审查都要在 4 份文档里做考古。

## 三、第二轮（收敛与拷问）：苏格拉底致命追问 + 双向钢人

每节：① 初始论断 → ② 致命追问 → ③ 双向钢人 → ④ 幸存结论。

### 3.1 拷问 1：A1「运行中跑旧代码」是缺陷，还是无害的环境常态？

**初始论断**：运行中 backend 落后 3 个后端提交，其中含 F-22 P0 跨用户数据越界——这是本轮最高优先级缺陷。

**致命追问**：AideanBot 是**个人/小团队开发环境**，不是生产系统。开发期镜像落后于 git 是**普遍常态**，把它升级为 P0 缺陷是否过度？`docker compose up -d --build` 一条命令就能解决，为什么值得占用 R6.1 的 4 个原子任务？

**双向钢人**

- **支持「是缺陷」**：① F-22 不是抽象风险，是**已发生的可执行路径**——空公共空间 link 会抄走全系统 READY 资产，任何登录用户在旧代码上触发即越界。② 更严重的是**半迁移态**（A2）：DB 已有 `content_hash` 列，旧代码不引用，看似无害；但一旦有人按文档重建（预期"恢复功能"），就会跳到新代码 + 新 schema，**两个 P0 同时消失的同时行为语义改变**（stale 判定从空间内变为内容指纹），**旧行为无任何测试锁定**。③ `/system/health` 零门禁且探针绿，**没有任何机制会让操作者意识到功能面落后**。

- **支持「是常态」**：① 若这是已知的、被文档记录的「本地开发允许滞后」，那么把它登记为缺陷属于**把惯例当事故**。② 3 个提交中有 1 个是纯前端（`39389fc`）+ 1 个是文档（`ff90a9e`）+ 1 个是 OpenAPI 标注（`09acfc1`），**真正影响运行时行为的是 2 个**；且这些提交本身**尚未在任何环境被验证过**（无 CI、无 L4）。③ 修复动作（重建 + 重启）需要**用户授权**（F-20 已确立"容器操作需书面授权"的先例），单方执行越权。

**幸存结论**：**降级为「P1 部署完整性 + 1 个 P0 止血项」**。区分两件事：(a) 镜像落后本身是 P1（可授权后一次性解决）；(b) **F-22 漏洞在线是 P0**，但其止血路径不是"重建镜像"（越权 + 未验证的新代码），而是**先确认该端点当前是否可达、是否需要临时下线**——这是一个**取证 + 决策**动作，不是施工动作。故 R6.1.1 只做取证与预案，**实际重建列为需管理者授权的动作**（R6.1.2）。

### 3.2 拷问 2：C1「凭据缺失」的更正，会不会是我的误判？

**初始论断**：`阻塞项登记表.md` D3 声称 REDFOX_API_KEY 缺失，实测 `.env` 有 35 位值，故登记失实。

**致命追问**：35 位、17/35 唯一字符——**这个熵偏低**。真实 API Key 通常是高熵随机串（35 位 base62 应有 28~31 个唯一字符）。17 个唯一字符更符合**有结构的占位串**（如 `dev-key-xxxxxxxx-xxxxxxxx`）。我只做了字符集判定，**没有打印值、也没有调用验证**。凭什么断定"凭据已到位"？我可能把一个失效 Key 当成了有效 Key，进而让管理者以为整号采集已解锁——**这是比登记失实更危险的误报**。

**双向钢人**

- **支持「我的判定成立」**：① 登记表说的是「凭据缺失，超出代码仓库可见范围」——**这句话本身已被 `.env:3` 的存在证伪**，无论该值是否有效。② 35 位非空、非 `change-me`/`xxx`/`placeholder` 类字面（已用正则排除），且 `.env.example` 中该键为空——**填入动作确实发生过**。

- **支持「我的判定不成立」**：① **有效 ≠ 存在**。35 位低熵串有相当概率是开发期占位。② 我**明确拒绝打印该值**（正确的安全行为），因此**无法在本地确认其有效性**，我的结论必然带不确定性。③ 若我表述为"凭据已到位"，管理者可能据此排产 R4.1.5 活体验证并浪费一轮。

**幸存结论**：**措辞精确化**。C1 的更正**只否认"缺失"**，不断言"有效"。D3 性质改为「**凭据已填入，有效性未验证**」，并把验证动作本身立为**零阻塞原子任务**（R6.3.4.1，一次真实调用即可定论，成本约 3201 积分以内、无需重建任何环境）。**这是本轮唯一一处我主动收窄自己结论的地方**——宁可留下可执行的未决项，不留下看似解决的误报。

### 3.3 拷问 3：R5 的竣工声明该不该被推翻？

**初始论断**：v1.3 §五 称 R5 全量竣工（16 原子 / 7 工作包），门禁 vitest 293、tsc/eslint/ruff/mypy 全绿。

**双向钢人**

- **支持「R5 有效」**：① 我复核的 10+ 项 R5 声明**无一失实**（1 处文件名偏差，不影响功能）。② R5 的**自述取证边界写得很诚实**（§6.2 明列"本会话未执行任何 pytest/vitest/docker"、"不谎报 250 达标"）。③ 结论是 R5 在其声明的 L1 静态范围内**确实竣工**。

### 3.4 拷问 4：首同步卡死（`subscription.py:526-527`）真的还没修吗？

**初始论断**：`if not created: return job` 不看状态，取消/失败的首次 Job 使该订阅永久无法自动同步——这是数据 4 问 ① 已登记但未修的缺陷。

**致命追问**：这条路径的触发需要「首次同步 Job 被取消或失败」+「用户不重新订阅」。**在无 scheduler 的当前环境（A3），首次同步根本不会跑**，Job 停在 QUEUED 而非终态，卡死不会触发。所以我实测到的 `if not created` 逻辑**在当前运行态下是一个不可达的死代码**。我应该把它列为 P1，还是列为低优先？

**双向钢人**

- **支持「降为低优先」**：① 当前 scheduler 停摆 → 首次 Job 不进终态 → 卡死不触发。② 触发需**用户主动取消**一个正在跑的 Job，这是窄场景。③ 修复涉及幂等键语义（F-19 已注「需产品语义裁定：手动触发是否复用幂等键」），**未裁定即动工有返工风险**。

- **支持「维持 P0/P1」**：① **A3 不是永久状态**——R6.1 一复活 scheduler，这条路径**立刻可达**。② 更关键的：**卡死发生时是静默的**，用户看到的只是"订阅创建了，但没有文章"，与"发现源未配置"**症状完全一致**——会把一个**永久故障**误读为一个**配置问题**。③ F-19（无手动重新采集入口）与本缺陷**叠加**：既不会自动重试，也没有手动补救入口，用户唯一的自救是删了重订——而重订走幂等返回既有订阅，**也救不了**。

**幸存结论**：**维持 P1，但必须在 R6.1（复活 scheduler）之前或与之一同修复**。理由不是当前可达性，而是「**修了 A3 之后缺陷立刻可达且静默**」。依赖关系写死：R6.3.2 ← 必须先于或与 R6.1.2 同批。

### 3.5 拷问 5：四条失实锚（C1–C4）会不会让我显得"文档不可信"，从而削弱整套体系？

**初始论断**：本轮 4 处失实锚中，C1（凭据）影响操作决策、C2/C3（改名断裂、64 键上限）**完全无代码对应**、C4（页面行数）是时态滞后。

**致命追问**：如果我强调这些，会削弱文档体系的公信力；如果我不说，下次审查会重复同样的考古。**但更根本的问题是：C2 和 C3 连"曾经正确"都算不上**——`uq_source_type_external` 一直是 (type, biz) 键，`_TERMINAL_STATUSES` 一直是 4 元组。这两条**不是时态滞后，是从未核实过的臆测**。我凭什么把它们和 C1/C4（确有时态解释）放在同一张表里？

**双向钢人**

- **支持「分级处理」**：C1/C4 是**可解释的漂移**（登记表一次性登记 / 快照时点早于施工），责任在维护节奏；C2/C3 是**无依据的断言**，责任在取证纪律。两者根因不同，应分别处置。

- **支持「统一处理」**：① 四者的**共同根因**是「结论写入文档时未做代码级核对」。② 分级的实际收益是零——用户要的是「现在哪些是真的」，不是「哪些错误更值得批评」。③ 过度区分错误类型会稀释注意力。

**幸存结论**：**统一登记、分别标注根因**。处置动作只有一条——每条失实锚必须有**对应的可执行核对动作**，否则下次还会发生。故 R6.5.3 立「结论写入前核对闸」，并在 R6.7 把"每条 R 项必须有 file:line 锚点"固化为文档同步的验收条件。**不区分错误等级，但区分根因**。

### 3.6 拷问 6：我自己差点误报的那一处，说明了什么？

**初始论断**：R5.2.3 把 `test_chat_sse.py` 桩里的 `similarity` 改成 `score`，可能是**改错方向**——因为 `langbot/client.py:208` 注释写着「实测 v4.10.9：`similarity?`」。

**致命追问**：我差点就把这个当成 F-26 报上去。但 `文档索引.md` 引 M0 报告 §四 B-T8：**「字段是 `score`/`distance`，原文写的 `similarity` 不存在」**。也就是说 `client.py:208` 那条注释**本身是已被 M0 实测推翻的过期注释**，而 R5.2.3 的修正是**对的**。

**双向钢人**

- **支持「报一个真实缺陷」**：① 既然 M0 已裁定字段是 `score`/`distance`，那么 `client.py:208` 的注释**仍写 `similarity?`** 就是**残留的过期注释**，会误导下一个读者（正如误导了我）。② `test_langbot.py:84`、`test_metadata_filter.py:59`、`test_p4_engines.py:79,97` **四个测试桩仍用 `similarity`**，与 R5.2.3 修正后的 `test_chat_sse.py` **口径分裂**。③ 且 `chat.py:124-127` 只消费 reranker 分数、**从不读 LangBot 返回的 `score`/`distance`**——检索分完全没有进入排序决策。

- **支持「不值得立任务」**：① 注释与桩字段不影响生产行为（后端从不读这些字段）。② 属纯文档卫生，与本轮 P0/P1 无关。

**幸存结论**：**拆成两条，分列 P3 与 P2**。① `client.py:208` 过期注释 + 4 处桩字段分裂 → P3（R6.6.4，一次 grep 替换即可）。② **检索分未进入排序**是**独立且更实质的问题**：`reranker` 未启用或无结果时，`chat.py:125-127` 的 fallback 是**保持 LangBot 原始顺序**，而该顺序基于 LangBot 未使用的 `score`——**即无 reranker 时排序是未定义的**。这是 P2 能力缺陷（R6.6.5）。**这一节的价值在于：它证明"实测 ≠ 轻信"必须双向执行**——我不轻信文档，也不轻信自己第一轮的结论。
