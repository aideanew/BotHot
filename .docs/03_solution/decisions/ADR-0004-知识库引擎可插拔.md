# ADR-0004：知识库引擎可插拔（内置默认 + 主平台 RAGFlow 系 + 第三方 SaaS API）

> 状态：已采纳为后续实现标准 | 日期：2026-09-13 | 归属：`.docs/03_solution/decisions/`
> 取代关系：不推翻 ADR-0001（LangBot = 当前默认引擎实现），新增引擎选择层。
> 关联：`SPEC-素材资产化与公共知识库.md`（资产层不动，引擎只承接 upload/retrieve）。

## 一、决策

**知识库引擎可插拔，用户可选择；默认顺序：① 本项目内置引擎（ADR-0001 LangBot 系）② 主平台知识库（RAGFlow 拓展系）③ 第三方 SaaS API（上手即用）。**

小白路径：注册 → 拿 API Key → 调 API（建库/上传/解析/检索全托管），不部署向量库/Embedding/解析器。

## 二、引擎位（5 个，按默认顺序）

| 位 | 引擎 | 形态 | 适用 |
|---|---|---|---|
| E0 内置默认 | 本项目引擎（现 LangBot KnowledgeEngine 系） | 已部署，最快最好用 | 默认全部用户 |
| E1 主平台 | 主平台知识库（RAGFlow 拓展而来） | 内网/同一账号体系 | 需要主平台统一知识时 |
| E2 SaaS-A | Coze 知识库 API | 注册即 `Token`，托管存储/解析/chunk/embedding/检索 | 小白首选（快速用起来） |
| E3 SaaS-B | Dify Cloud Knowledge API | 同上，知识/文档/chunk 管理 API 更完整 | 小白转专业（当标准 infra 用） |
| E4 SaaS-C | FastGPT Cloud Dataset API | 同上，中文内容友好 | 中文场景重点 |

OpenAI Vector Store / File Search 列备选（极简但中文知识管理弱）；Notion 列 CMS（存原文/元数据，不当 RAG 引擎）；RAGFlow 自建暂不考虑（违背“第三方托管”）。

## 三、架构：端口 + 适配器（防腐层与 LangBot 客户端同级）

```text
kb.ingest_url / chat.ask
  → KnowledgeEnginePort（create_kb/upload_file/ingest_status/retrieve/delete_kb/delete_file）
  → E0 LangBotAdapter（现状 providers/langbot，1:1 KB/collection）
  → E1 RagflowAdapter（主平台系，kb 映射主平台库 id）
  → E2/E3/E4 SaaSAdapter（Coze/Dify/FastGPT：dataset_id + API Key 托管）
```

规则：

1. **资产层与引擎解耦**：`ContentAsset(content_markdown)` 是唯一真源；引擎只收文件/文本上传，不参与抓取解析。
2. **空间绑定引擎**：`KnowledgeSpace.engine: str = "builtin|main|coze|dify|fastgpt"` + `engine_kb_id`（替代/并存 `langbot_kb_uuid`，迁移时双写）；`KnowledgeDocument.engine_file_id` 并存。
3. **问答扇出**：`ask` 按 `space.engine` 路由到对应适配器；跨引擎公共库引用走拷贝式（默认），扇出列 M4。
4. **密钥纪律**：第三方 `API Key` 只走 `env`/密钥服务 + 用户级 `Key` 加密列，不入库明文、不入码（沿 `config.py` 注释纪律）。

## 四、SaaS 适配器最小契约（8 项，上手即用验收）

```text
① 注册后能否直接拿 API Key
② API 创建知识库/数据集
③ API 上传 PDF/Word/Markdown/TXT
④ API 上传 URL（无则由我方下载后转文件上传兜底）
⑤ 自动解析完全托管（我方只传文件/文本）
⑥ API 查询/检索（返回 原文+来源+文档ID）
⑦ API 更新/删除
⑧ 小白从注册到第一次 API 检索步数（越少越好，选型权重最高）
```

任一 SaaS 缺 ④ 时：我方用 `ContentAsset` 已有 `markdown` 转文件上传，不阻塞。

## 七、风险与取舍

- SaaS 延迟/费用/数据出境：默认仍走内置，SaaS 仅用户自选；Key 泄露面用加密列 + 最小权限。
- 主平台 RAGFlow 系联调依赖主平台排期：先 P0+P1 让出插槽，不等主平台。
- 多引擎 `citations` 归属：统一 `{title, spaceName, engine}` 三元，跨引擎融合列 M4。

## 九、引擎可用性不变式（2026-09-22 增补，AB-P004 R0.3 收口）

### 9.1 不变式：切换谓词 ≡ 消费谓词

**任一「引擎可用」判断必须走同一谓词 `available(engine) = configured ∧ allowlisted ∧ implemented`。**
`builtin` 恒 True（回退通道，不随 allowlist 判定）。

三处必须同口径：

| 落点 | 代码锚 | 用途 |
|---|---|---|
| `GET /engines` 的 `available` 键 | `app/api/v1/engines.py::_engine_available` | 前端卡片是否可点 |
| `PATCH /spaces/{id}/engine` 前置校验 | `assert_engine_switchable` | 服务端拒绝切换 |
| `kb.ingest_url` 前置检查 | `EngineRouter.available` | 实际入库路由 |

`frontend/components/EngineSwitcher.tsx` 的 `canSelect = e.available` 只读 `GET` 数据，属第四份同源副本，不新增谓词。

**反例（已修复）**：PATCH 曾只查 `allowlist + configured`，漏查 `ENGINE_IMPLEMENTED`。后果链：
空间可被切到骨架引擎 → `ingest` 全 403（消费侧三条件拦截）→ `delete_space` 走
`SaasAdapter.delete_kb` 抛 `NotImplementedError` 整体回滚 → **空间无法删除**。
前端因读 `GET` 数据天然挡住点击，故该缺陷只能经直调 API 触发——恰是「同一份数据、两个谓词」的典型。

### 9.2 拒绝原因分层（顺序不可换）

`assert_engine_switchable` 按**最具体原因优先**拒绝，顺序换错会让管理员按错误指引行动：

1. 未知引擎位（不在 `ENGINE_ORDER`）→ `RequestInvalidError` 10005/422
2. 不在 allowlist → `ForbiddenError` 10004/403「未开放」
3. 未配置 API Key → `ForbiddenError` 10004/403「未配置 API Key」
4. 已配 Key 但未实接 → `ForbiddenError` 10004/403「尚未实接」

前端 `EngineSwitcher` 的三态标签（未开放 / 未配置 Key / 未实接）与 tooltip 同序，与上表逐条对齐。

### 9.3 新增引擎位的准入条件（扩槽前置约束）

新增引擎位（如飞书，见 `SPEC-T4.3飞书知识库扩槽-20260922.md`）必须同时满足：

1. 六方法实接（`ENGINE_IMPLEMENTED[slot] = True` 之前一律 False，骨架位仅占槽）；
2. `assert_engine_switchable` 第 4 条拒绝分支覆盖该位；
3. `EngineRouter.available` 三条件覆盖该位；
4. 至少一条不变式回归测试遍历 `ENGINE_ORDER` 全位（见 `backend/tests/test_p4_engines.py::test_r032_switchable_predicate_equals_available_across_all_slots`）；
5. 前端三态提示无需改动（判定复用 `available`）。
