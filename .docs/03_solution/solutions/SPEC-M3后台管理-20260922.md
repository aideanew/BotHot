## 二、扩展点①：权限模型（批次 1 前置，D9=a 终底）

### 2.1 角色定义（三态，最小必要集）

| role | 数据可见域 | 授权动作 | 对应板块 |
|---|---|---|---|
| `user`（默认） | **仅本人**（现状语义，零回归） | 既有全部用户端点 | — |
| `operator` | 全站**只读**业务数据 | 公共库审核（T5.5）、引擎 Key 配置（T5.4）、推送触发（T6.2） | 批次 3/5 |
| `admin` | 全站**读写** | 以上 + 信息源删除（T5.2）、文章删除（T5.3） | 批次 2/3 |

**明确不做**：全用户管理（`users` 增删改、批量改角色之外的账号生命周期）——D2 裁决边界维持，账号域仍归主平台（D4）。

### 2.3 判定函数（单一来源，禁在路由层散落）

```
async def require_role(session, user_id, *roles) -> User:
    1. 本地无该行            → UnauthenticatedError 10001/401（授权前先确认身份存在）
    2. ROLE_RANK[role] >= max(ROLE_RANK[r] for r in roles)
                              → 放行（单调秩语义，admin 自动覆盖 operator 端点）
    3. 否则 → ForbiddenError 10004/403
```

**实测更正 ①（v0.1.2）——判定语义：单调秩，非成员判断。** 起草原文写 `role ∈ roles`。成员语义下，端点声明 `require_roles("operator","admin")` 会把 `admin` 也拒掉（`admin ∉ {operator}`），与本 SPEC §2.1 的「admin 全站读写」及 §2.4 的「admin 全放行」验收锚**自相矛盾**。故实现取 `need = max(ROLE_RANK[r] for r in roles)`，声明 `("operator","admin")` 等价于 `("admin",)`。该取舍由 `tests/test_r11_roles.py::test_role_ladder_matrix` 显式锁定，防止日后被"忠实实现原文"回改。

**实测更正 ②（v0.1.2）——紧急通道锚点：本地 `users.id`，非 `sub`。** 起草原文写 `sub ∈ PUBLIC_ADMIN_ALLOWLIST`。但既有的公共库写闸 `check_publish_gate`（`public_library.py`，有测试覆盖）与 `config.py` 的字段注释均写「本地 user_id」。若按原文改用 `sub`，**既有 allowlist 条目会静默失效，紧急通道当场失守**——这正是 c 过渡期要避免的故障模式。故锚点沿用 `users.id`。**（v0.1.4 追记）** 批次 3 收敛后该锚点不再属于 `require_role`——`users.id` 口径现由 `check_publish_gate` 闸① 独占持有，回归锁随之迁至 `tests/test_public_library_admin.py`。

**依赖方向**：`require_role()` 在 `app/services/roles.py`（纯逻辑，不引 FastAPI，**批次 3 后亦不引 settings**）；依赖工厂 `require_roles(*roles)` 在 `app/api/deps.py`。`services` 层不得反引 `api` 层（与 `job_worker.py` 的装配纪律一致）。空角色元组与未知角色名均 fail fast（`ValueError`）——端点漏传角色若被当成"无要求"，授权面会无声放大。

## 三、扩展点②：引擎位扩槽协议（引 ADR-0004）

M3 **不新增引擎位**，但必须把"新引擎如何接入"写成协议，否则 T5.4 的 Key 配置无处落地。

**注册一个新引擎的完整清单**（ADR-0004 §四 八项契约为上手机器门）：

1. 实现 `KnowledgeEnginePort` 六方法（`create_kb / upload_file / ingest_status / retrieve / delete_file / delete_kb`，engine_port.py:22-49）
2. 在 `ENGINE_IMPLEMENTED` 登记 `name → True`（唯一开关点，BE-02 前置检查依赖此值）
3. `config.py` 加字段（env 直映，无 prefix）：**SaaS 位仅 `{engine}_api_key`**；仅 main 位另有 `main_kb_api_base`。**KB id 不属配置**——存 PG `knowledge_spaces.engine_kb_id`，由 `EngineRouter.kb_id_for()` 读取

### 6.1 批次 2 后端施工记录（v0.1.5，已竣工 `9f12f40`）

**设计判定：抽 core，不复制实现。** 两 admin 端点与既有端点的**全部差异只有一处判据**
（`space.user_id == owner`），故不写两份方法体：

| 入口 | 委托 | `owner` |
|---|---|---|
| `update_space(user_id, space_id, description)`（既有，签名不变） | `_update_space(space_id, description, owner=user_id)` | 本人 id |
| `update_space_any(space_id, description)`（新增） | `_update_space(space_id, description)` | `None` |
| `delete_doc(user_id, space_id, doc_id, kb)`（既有，签名不变） | `_delete_doc(..., owner=user_id)` | 本人 id |
| `delete_doc_any(space_id, doc_id, kb)`（新增） | `_delete_doc(...)` | `None` |

**为什么不复制**：若简介校验顺序、commit 纪律、引擎先行顺序、资产孤儿收敛在两份拷贝里各写一份，
日后修一处忘另一处即漂移——最典型的表现是「非法取值对不存在的空间返回 30004 而非 10005」，
即校验与取行的先后被悄悄换掉了，且**没有任何调用方会报错**。已由
`test_update_space_both_entries_validate_before_fetch` 直接锁定「两条入口都先校验后取行」。

**先例**：同文件 `_delete_doc_core(space, doc, kb_client)` 自批次 1 起即为「无归属、无事务态」
的 core。本次沿用同一手法——`_delete_doc` 保留事务边界与 `doc.space_id` 判据，`_delete_doc_core` 不动。

**服务层不校验角色**：角色判定的唯一来源是 `app/services/roles.require_role`，经
`app/api/deps.require_roles("admin")` 挂在路由上。故服务方法命名为 `..._any`（「无归属约束」）
而非 `admin_*`——后者会被误读为「方法内做了授权」。授权面留在路由层，与 `jobs`/`spaces` 既有纪律一致。

**契约分歧（刻意不一致，勿「统一」）**：`description` 在既有端点是可选（PATCH 部分更新，
缺省返回详情视图），在本批 admin 端点**必填**（缺失 → 10005）。理由：admin 端点返回**写回执**
`{ok, id, description}` 而非详情视图——详情视图带**本人归属**语义，跨用户取视图另议；
而写回执端点没有「no-op 也有信息可返回」的语义，唯一可写字段缺失即客户端 bug。
两侧形状均有测试双向锁定。

**新增面特有的风险**：`doc.space_id` 归属判据**不随**空间归属一起放开。admin 能跨租户操作空间，
但「该 doc 属不属于这个空间」仍是硬校验——否则可凭任意 `doc_id` 越界删除。
`test_admin_delete_doc_invalid_targets_30004` 覆盖 4 种无效目标（无效空间 / doc 不存在 /
doc 属其他空间 / 空间属他人）。

**测试面（14 测，全走真实 PG）**：admin 端点 9 + 授权门禁 2 + **零回归锁 3**
（用户端点跨用户仍 30004 / 本人 PATCH no-op 仍返回详情视图 / 本人删除路径不变）。
零回归锁是 A-2 承诺面的直接断言——若抽 core 时把 `owner` 判据漏成可选，
旧端点会静默失守而没有任何调用方报错。

### 6.2 批次 3 / T5.4 施工记录（v0.1.6，已竣工 `e013bc3`，迁移 `ab1004m3b`）

**交付面（三条新端点，均 `operator`+，落在既有 `app/api/v1/admin.py`）**

| 端点 | 语义 | 返回 |
|---|---|---|
| `GET /admin/engines/keys` | 列表（**不含明文**），含 `masterKeyConfigured` | `{masterKeyConfigured, items[]}` |

| `DELETE /admin/engines/keys/{engine}` | 撤销（无登记行 → 30004，不谎报已撤销） | `{ok, engine, revoked}` |

`keyId` 是轮换句柄：明文落库后不回显，唯一能对外暴露的登记凭据。

**设计判定 ①：凭据解析收敛为单一谓词 `resolve_engine_key()`。** 施工前 `main` 位有**两份互相分歧的 `configured` 谓词**——`engines.py` 只查 `main_kb_api_base`（忽略 Key），`engine_port.py` 查 base **且** key。base 已配而 Key 为空时，`GET /engines` 报「已配置」而入库路径说「未配置」。既有 `test_p4_engines.py::test_r032_switchable_predicate_equals_available_across_all_slots` 遍历全 5 位锁定两谓词相等，**但从未覆盖 base-only 分支**，故缺陷得以上线。现两处消费者（状态上报 / 切换闸 + 路由判定 / 引擎构造）全部改走 `resolve_engine_key()`，不变式**由构造保证**；新增 `test_main_requires_base_and_key` 补 base-only 与 key-only 两个分支，`test_all_slots_two_predicates_agree` 遍历 5 位 × 2 配置。base 是端点不是凭据，**永远只认 env**（登记表无 `main` 的 base 项）。

**设计判定 ②：主密钥缺失 = 50002，不是 10004/10005。** 10004 说「无权限」会误导 operator（他有角色）；10005 说「请求无效」同样误导（请求没问题）。50002「依赖不可用」准确——加密能力未就绪。且 50002 已在 `ERROR_CODES` 注册，**不新增码位**（`errors.py` 明令新增码位属契约变更须报 A 登记）。

**设计判定 ③：绝不回落明文。** 静默明文回落比明文更坏——UI 显示「已加密登记」而库里是明文，比一开始就写明文更难被发现。畸形 base64 与长度不符同样拒绝（静默按截断处理会把「配置错了」伪装成「配置对了」）。

**设计判定 ④：优先级 registered > env，由 `activeSource` 显式回报**（`"env"` / `"registered"` / `None`）。登记覆盖 env 必须是可见的——「存了但没生效」是最差失败形态（F-4 教训）。`GET /engines` 与管理端列表均带 `envConfigured` 与 `configured` 两个可比字段，登记覆盖 env 因此不是静默的。

**设计判定 ⑤：同步惰性路径用进程内快照，不把 async DB 织进同步热路径。** `make_engine` / `EngineRouter` 是 sync 且无 DB session，共 5 处构造点（含 `deps.py` 模块级单例），改 async 是大手术。**正确性论证**：所有 async 路由**直读 PG**（权威、永不陈旧），只有同步惰性路径用快照；当前非 builtin 位 `ENGINE_IMPLEMENTED` 全为 `False`，`available()` 恒 False，`adapter_for` 不会对它们调 `make_engine`——**快照陈旧现在无法造成错误入库判定**，最坏回落 env 行为。快照在每次写后刷新，并由 `GET /engines` 预热（覆盖「重启时已有登记行」的场景）。`snapshot_age()` 暴露为观测钩子；多进程部署的跨进程刷新**登记未构建**（D10 实接时会一并处理）。

**设计判定 ⑥：`secret_ref` 用 `Text` 而非 `VARCHAR(512)`。** 密文长度随明文线性增长（GCM tag +16 字节），长度上限会制造**静默截断/写失败**路径。真实边界放在请求侧：明文上限 1024 字符（`MAX_KEY_CHARS`），另拒空白与控制字符（`ord < 0x20` 或 `0x7F`）。

**实修缺陷（生产代码，非测试修补）**：`decrypt_secret` 原 except 元组 `(LookupError, ValueError, binascii.Error, TypeError)` **漏 `cryptography.exceptions.InvalidTag`**。实测 `InvalidTag.__mro__ = (InvalidTag, Exception, BaseException, object)`——**不继承 `ValueError`**。后果：AAD 不匹配（**这正是 AAD 存在要拦的攻击**——密文在引擎位间搬移）会以未处理异常（500）告终，而非设计要求的 fail-closed。已补入元组并加注释说明为何必须显式列出。

**迁移核对（PG:5433 反射，非信任 DDL）**：`engine VARCHAR(32)` PK / `secret_ref TEXT` / `key_id VARCHAR(32)` UQ / `registered_by VARCHAR(36)` FK → `users.id` ON DELETE CASCADE / `created_at`、`updated_at` TIMESTAMP 默认 `now()`。`downgrade ab1004m3a` + `upgrade head` 往返实测通过（head 现为 `ab1004m3b`）。

**T5.5 裁定（2026-09-23，管理者）：不加 `POST /admin/public/{space_id}/approve`，登记为双路径风险。** 该位是 T5.5「公共库审核位」，本批不构建。登记为**双路径风险**而非遗漏：`PATCH /spaces/{id}/public` 的既有双闸（T1.4.1）已构成一条发布路径，未来若再增一条 admin 审批路径，两条路径的先后与冲突语义需另行裁定，届时不得静默叠加。**R1.1 后端施工面由此收敛为批次 5 余路由。**

**设计判定 ②：`/me` 只读、绝不抛错；故谓词返回布尔而非依赖。** `require_role` 靠抛
`PermissionError` → 10001/10004 表达拒绝，那是**写侧门禁**的语义；`/me` 是**读侧回显**，
任何角色都必须拿到 200 与自己的身份，否则非 admin 用户连登录态都拿不到、前端无从渲染。
`has_min_rank` / `sub_has_min_rank` 一律返回布尔，缺用户时返回 `False` 而非抛错。

**设计判定 ③：未知 role 取值 fail closed 到默认秩。** `ROLE_RANK.get(role,
ROLE_RANK[DEFAULT_ROLE])`——脏值（大小写错、枚举外的历史值）一律按 `user` 处理，**不**按

**设计判定 ④：admin 读面承 `_any` 手法，归属走 LEFT JOIN。** `SpaceRepository

**设计判定 ⑤：前端门禁只认 `/me` 的 `is_admin`，绝不从 `user.role` 推导。** 真实主平台
userinfo 的 `role` 是**大写枚举**（`"USER"`），与本地授权阶梯（`user`/`operator`/`admin`）
**不同源、不同形**；拿它门禁会与后端 10004 **双向分歧**（前端认为可进而后端拒，或反之）。

**设计判定 ⑥：fail closed，且门禁在渲染层解决、不发请求。** `is_admin` 缺失（旧后端未回显）
