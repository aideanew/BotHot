# R8 · RedFox 对接活体实测取证与剩余任务方案大纲

> 版本：v1.0 | 创建：2026-09-28 | 状态：**PLAN + SPEC 已完成，待 APPROVE**
> 前序：R6（2026-09-24）、R7（2026-09-24）、R7.7 批次（提交 `cbbfe1b`，进程存活可观测）
> 本轮目标：完成公众号整号采集的 RedFox 对接（需求 Step 3 核心第 1 条），以**最小积分成本**。
> 本轮取证方式：**5 次活体调用**（2 次成功 = 0.08 积分；3 次被上游以 500 参数错拒绝，未计费）+ **零成本本地取证**（DB 实况、源码穿透、官方文档目录抓取）。

## §0 结论先行（裁决摘要）

1. **管道双重致死，且与积分无关。** 现行代码即使拿到足额余额，也**必然 100% 失败**。两个独立致命缺陷：
   - **F1**：请求体 `{biz, page}` 与官方契约不符 —— 实测只有 `bizInfo` 被接受，`account`/`keyword` 均返回 500。
   - **F2**：`_URL_KEYS` 缺 `workUrl` → 100% 清单行 `url=""` → `job_worker.py:264` `raise ValueError("item.url 为空，无可采地址")`。
2. **契约形状已由活体实测确立，不再是假设。** `bizInfo` + `offset` + `sortType` → `code 2000`，20 行/页，`total` 位于 `data.total`，`offset` 步长 20 且零重叠。
3. **T+1 延迟已由活体实证确认。** 探测时刻 2026-09-28 11:58（Asia/Shanghai），被测号日更，最新行为 2026-09-27 07:42 —— 今日零行。**每天 10 点的任务本质上只能拿到昨天为止的数据。这是产品事实，必须披露而非隐藏。**
4. **成本可降 10 倍。** 现状稳态 10 次调用/天/号 → 修复后 1 次调用/天/号（自适应缺口翻页）。按目录价 0.04 计：146 → 14.6 积分/年/号。
5. **无需购买 RedFox 订阅制。** 其「订阅账户收录」1000 积分/号/年 = 2.74/天；本方案 0.04/天，**便宜 68 倍**。盈亏平衡点 = 每天 68.5 次调用/号，我们只调 1 次。
6. **「多种方式」现状 = 2 个真实入口，不是 1 个。** ①按 `__biz` 定位（实测通）；②按文章 URL 直抓反解 `__biz`（免费，0 积分，已在 `source_resolver.py`）。第三候选 `searchUser` **实测不可用**，不接入 —— 接入已知坏端点等于假交付。
7. **测试 key ≠ 生产 key。** 本轮验证的是用户提供的测试 key（有余额）。`docker/.env` 中的生产 key 余额**本轮未验证**，仍是 D3 的未决部分。
8. **零 schema 变更。** 增量游标用 `COUNT(ArticleManifest WHERE source_id=?)`（命中 `uq_manifest_source_external` 前缀索引）对 `data.total` 求缺口，无需新列、无需迁移、零数据回滚风险。

## §2 缺陷清单（按致命度降序）

### 2.1 致命缺陷

**F1 — 请求契约全错（`app/providers/redfox/client.py:39-40, 63, 72`）**

| 现行代码 | 官方契约（实测） |
|---|---|
| `QUERY_WORK_LIST_PATH = "/story/api/gzhData/queryWorkList"`（优质库） | `/story/api/gzh/data/queryWorkList`（广域库） |
| 请求体 `{"biz": biz, "page": page}` | `{"bizInfo": …, "offset": …, "sortType": "2"}` |

`biz` 与 `page` **都不在任一库的文档参数表内**。且实测证明优质库连它文档里明列的 `account`（`required=True`）都拒（探测 #4）。
**影响**：无论积分是否充足，清单永远为空 → `sync_source` 收到 0 行 → 无任何发现 → `run_incremental_sync` 返回 0 → Job 空转。
**证据**：`client.py:72`；探测 #1/#4/#5；官方目录 17 个端点的参数表。

**F2 — URL 映射缺失 → 全链路入库必败（`app/services/manifest.py:41`）**

```python
_URL_KEYS = ("url", "link", "articleUrl", "article_url")   # ← 无 "workUrl"
```

实测行内**有 `workUrl`、无 `url`** → `_map_row` 恒得 `url=""` → `ArticleManifest.url=""` →
`subscription.py:771` `item = self._item_repo.create(..., url=m.url or "")` →
`job_worker.py:264` **`raise ValueError("item.url 为空，无可采地址")`**。

**影响**：即使 F1 修好、数据真的回来了，**100% 的 JobItem 也会因为空 URL 抛异常**。这不是概率缺陷，是确定性 100% 失败。
**危害性**：与积分**完全无关**，因此「等 D3 解封再修」无法解锁它。
**连带伤害**：`content_hash` 派生为 `sha256("|" + title)`（url 为空）→ 同源同标题的不同文章哈希碰撞，去重语义被削弱。

### 2.3 缺陷发现链：为什么这些一直没被发现

三层原因叠加，缺一层都能被更早抓到：

1. **契约是凭空预写的，且从未有机会被证伪。** `client.py` 头注明确写着「字段以 1.1.2 活体响应实测为准回写」—— 而活体实测的前提是有余额。D3（余额 0）卡住的那天起，契约就停在猜想状态。
2. **测试用 mock 把这个猜想固化成了绿灯。**
   - `tests/test_redfox_client.py:62` → `assert body == {"biz": "MzUxNzU", "page": 1}`（断言了错误的请求体）
   - `tests/test_manifest_sync.py:118,127` 的 mock 行用 `"url"`（真实响应里根本不存在的字段名）
   - **这是「测试自己造数据源」的自证陷阱**：mock 从不含 `workUrl`，所以 `_URL_KEYS` 缺它这件事在测试里永远不可能暴露。测试证明的是「代码与 mock 一致」，不是「代码与上游一致」。
3. **错误路径先于参数校验返回。** 3201（积分不足）在任何 payload 校验之前短路返回 → 参数名错误永远没有机会浮现。**错误码是成功的伪装。** 这一模式在项目里已两次记录（D17、D20），本轮是第三次。

## §3 成本模型（量化）

设 `P` = 单次调用积分（预期 0.04，上界 0.4）。被测号 `total=173` → 全量页数 `⌈173/20⌉ = 9`。

### 3.1 现状（若 F1 修好但 N4 未修）

| 项 | 计算 | P=0.04 | P=0.4 |
|---|---|---|---|
| 稳态每日 | 9 数据页 + 1 空页 = 10 次 | 0.40/天 | 4.0/天 |
| 年化（单号） | ×365 | **146/年** | **1460/年** |
| 20 号年化 | ×20 | 2920/年 | 29200/年 |

### 3.2 修复后（自适应缺口翻页）

| 项 | 计算 | P=0.04 | P=0.4 |
|---|---|---|---|
| 稳态每日 | **1 次**（offset=0，20 篇含当日新增，唯一键去重） | 0.04/天 | 0.4/天 |
| 年化（单号） | ×365 | **14.6/年** | **146/年** |
| 首次回填（一次性） | 9 次 | 0.36 | 3.6 |
| 20 号年化 | 20×14.6 + 20×0.36 | **≈299** | **≈3012** |

**稳态节省 10 倍。回填是一次性的 0.36/号。**

### 3.3 与 RedFox 自有订阅制对比（业务模型裁决）

| 方案 | 成本 | 说明 |
|---|---|---|
| 本方案（按次 + 游标） | 0.04/天/号 | 稳态 |
| RedFox「订阅账户收录」 | 1000/年/号 = **2.74/天/号** | T+1 推送，服务期一年 |
| RedFox「付费回溯」 | **`disabled:true`「暂未开放」** | 不可用，无成本可谈 |

**盈亏平衡点** = 2.74 / 0.04 = **68.5 次调用/天/号**。我们每天调 1 次 → **永不到达订阅制更便宜的区间**。
**裁决：不买订阅。** 按次 + 游标在所有合理调用频率下都更优，且无一年期承诺。

### 3.4 成本可观测性（防再次失控）

N4 之所以能潜伏到「烧钱」量级而不被察觉，是因为**系统没有"我已经花了多少"这个信号**。
L1-4 修复：`ManifestSyncReport` 增补 `calls_made` / `total_remote` / `pages_planned`，落日志 + Job 元数据。使「本轮调用了几次、花了多少积分」成为可审计事实，而非估算。

## §4 方案大纲（4 层级 / 原子化 / 可执行）

> **层级约定**：`L1` 阶段（可独立验收）→ `L2` 批次（同文件/同关注面）→ `L3` 原子任务（单次改动，一个断言即可验收）→ `L4` 实现要点。
> **成本列**：`= 本轮代码改动所需积分（0 = 纯本地）**。所有 L1-1 ~ L1-5 的实施均**零积分**（离线契约测试即可验收）。
> **零 schema 变更**：全程不加列、不加表、不加迁移 revision。

### L1-1 契约纠偏（消除双重致死）· 成本 0 积分

**验收口径**：契约测试用 mock httpx 断言真实字段形状；`pytest` 全绿；F2 的入库路径用真实 `workUrl` 样本走通 `manifest → JobItem → worker 非空校验`。

#### L2-1.1 客户端层（`app/providers/redfox/client.py`）

- **L3-1.1.1** 端点切换为广域库
  - `QUERY_WORK_LIST_PATH = "/story/api/gzh/data/queryWorkList"`
  - 证据：探测 #1/#5 成功；优质库 `account` 实测拒（#4）。
  - 验收：`test_redfox_client.py::test_query_work_list_success_shape` 的 URL 断言同步改。
- **L3-1.1.2** 请求体改为 `{bizInfo, offset, sortType}`
  - 保留方法签名的 `page`（上层语义为"第几页"），**在 client 内换算** `offset = (page - 1) * PAGE_SIZE`，`PAGE_SIZE = 20`（模块常量）。
  - **理由（钢人裁决）**：若直接把 `offset` 暴露给上层，`manifest.py` 的 `while page <= max_pages` 循环语义要整体重写，改动面扩大且更易错；在 client 这一处收口换算，上层零改动。
  - 证据：探测 #1（offset=0 → 20 行）、#5（offset=20 → 另 20 行、零重叠）。
  - `sortType` 恒传 `"2"`（最新优先）—— 这是增量游标的**可用性前提**（降序才能让最新文章落在 offset=0）。
  - 验收：新增断言 `json.loads(req.content) == {"bizInfo": biz, "offset": 0, "sortType": "2"}`。
- **L3-1.1.3** 返回结构升级为 `(rows, total)`
  - `total` 取自 **`data.total`**（非顶层 —— 官方示例位置是错的）。
  - 返回 `WorkListResult` dataclass（`rows: list[dict]`, `total: int | None`）。
  - **理由**：这是 §3.2 自适应翻页的输入。只读 `data.list` 无法收敛分页。
  - 验收：mock `{"code":2000,"data":{"total":173,"list":[...]}}` → `total == 173`；缺 `total` → `None` 且不崩（防御式）。

### L1-2 增量化（成本降 10 倍）· 成本 0 积分

**验收口径**：稳态 = 1 次上游调用；首次回填 = `⌈total/PAGE_SIZE⌉` 次；`total` 误报时仍不漏采。

#### L2-2.1 自适应缺口翻页（`app/services/manifest.py`）

- **L3-2.1.1** 计算缺口页数
  - `seen = COUNT(ArticleManifest WHERE source_id = ?)`（命中 `uq_manifest_source_external` 的 `source_id` 前缀索引）
  - `needed = max(0, total - seen)`
  - `pages = min(max(1, ⌈needed / PAGE_SIZE⌉) + BUFFER_PAGES, max_pages)`，`BUFFER_PAGES = 1`
  - **`+1` 缓冲的理由**：`total` 是上游自报值，若漏统计则 `needed` 偏小 → 漏采。缓冲页 + 唯一键幂等 = 漏采被兜住，代价 1 次调用。**若 `total` 准确，这一页是空翻页，会被空页判断提前 break**（见 L3-2.1.4）。
- **L3-2.1.2** 稳态与回填两条路径统一
  - 首次（`seen=0, total=173`）→ `pages = 9+1 = 10`，实际翻到第 10 页遇空 break → **9 次有效调用 = 0.36 积分**
  - 稳态（`seen=173, total=174`）→ `needed=1` → `pages = 1+1 = 2`，第 2 页可能空 → 通常 **1 次调用 = 0.04 积分**
  - 空日（`seen=173, total=173`）→ `needed=0` → `pages = 1+1 = 2` → 仍需 **1 次调用**探测 `total` 是否变化
  - **不可再降的论证**：不调用就无法得知 `total` 变了没有。1 次/天是**信息论下界**，不是设计妥协。
- **L3-2.1.3** 幂等安全网
  - 唯一键 `(source_id, external_id)` 已存在（`entities.py:115`）；重复行走 `_apply_update` 计 `unchanged`。
  - **即使上游 `offset` 分页语义劣化（返回重复页），本设计不产生脏数据，只浪费调用** —— 这是把"依赖上游正确性"降为"容忍上游不精确"的关键。
- **L3-2.1.4** 空页提前终止保留
  - 现有 `if not rows: break` 语义保留，与 L3-2.1.1 叠加：既收敛于 `pages` 上限，又能在空页时提前停。
- **L3-2.1.5** `ManifestSyncReport` 增补记账字段
  - `total_remote: int | None`、`pages_planned: int`、`calls_made: int`
  - `sync_source` 的日志行追加这三项 → **成本可观测（§3.4）**。
- **L3-2.1.6** `max_pages` 语义澄清
  - 现有 `DEFAULT_MAX_PAGES = 20`、`manifest_sync_max_pages = 20` 保持不变，作为**回填上限**而非稳态值。173 篇需要 9 页，上限 20 页够；若某号超过 400 篇，回填会被截断 —— **这是有意的成本闸**，需在此处显式声明（否则会被误读为 bug）。超出的号按天追赶（每天 1 页新增量），最终收敛。

#### L2-2.2 测试

- **L3-2.2.1** 稳态 1 页断言：`seen=173, total=174` → `provider.calls == [1]`（1 页）
- **L3-2.2.2** 首次回填页数断言：`seen=0, total=173` → 翻到 10 页、第 10 页空 → `calls == 9`
- **L3-2.2.3** 空日断言：`seen=173, total=173` → `calls == 1`（信息论下界）

## §8 执行摘要（一段话）

RedFox 对接的卡点不是「凭据」，而是**契约**。现行代码的请求体、端点、分页参数、字段映射四者与上游契约全部不符，其中两处是致命且与积分无关的 —— 即使余额充足，管道也必然 100% 失败。本轮以 5 次活体调用（0.08 积分）确立了真实契约，证实「每天 10 点自动采集」在 T+1 时效下本质只能拿到昨天为止的数据，并把稳态成本从 10 次/天/号压到 1 次/天/号（信息论下界）。方案 6 个阶段、22 个原子任务，**全部零积分实施、零 schema 变更**，仅最终端到端核验需 0.36 积分/号。`searchUser` 与优质库经实测不可用，按诚实回报纪律不接入，另立 D21/D22 待上游解封。
