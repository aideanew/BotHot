## 一、模型总览

| 表 | 职责 | 关键约束 |
|---|---|---|
| `users` | 主平台账号快照（SSO 锚点） | `sub` 唯一（主平台 User.id） |

| `sources` | 信息源（wechat_oa） | `(type, external_id)` 唯一（external_id=公众号 biz） |
| `source_subscriptions` | 订阅（增量同步生命周期） | `(user_id, source_id, space_id)` 唯一 |
| `article_manifests` | 发现快照（Redfox 清单行） | `(source_id, external_id)` 唯一（external_id=workUuid） |
| `content_assets` | 内容资产（标准化 Markdown） | `(source_id, external_id)` 唯一 |
| `knowledge_documents` | 资产↔空间入库映射 | `(asset_id, space_id)` 唯一 |
| `jobs` | 任务状态机 | `idempotency_key` 唯一 |
| `job_items` | 整库导入子任务 | 按 job_id 索引 |
| `bot_bindings` | M2 机器人通道绑定 | `(channel, external_user_id)` 唯一 |

## 二、核心设计决策（溯源 ADR）

1. **余额/tier 不落库**（SSO 铁律，ADR-0002）：实时查主平台 `/api/v1/internal/billing/wallet`。
2. **幂等键三件套**（M0 实证 → ChatGPT_V2 结论）：
   - 资产：`source_id + external_id`（external_id 为规范化的 article_key）
   - 同步：Manifest 行 `content_hash` 比对（NEW/UPDATED/UNCHANGED），不用 publish_time
   - 任务：`jobs.idempotency_key` 唯一约束
3. **Job 持久化状态机**：`QUEUED → RUNNING → SUCCEEDED / PARTIAL_SUCCESS / FAILED`；worker 心跳 `worker_heartbeat_at`；队列（Celery/Redis）仅触发，任务事实以本表为准。
4. **KnowledgeDocument 状态机**：`FETCHED → INDEXED → READY`——"可检索"才告知用户（ChatGPT_V2 §十六）。

## 十一、R8 契约纠偏与增量化（2026-09-28，零 schema 变更）

> 与 §九 同类：**本批无任何新增迁移**。Alembic head 仍为 **`ab1004h1a`**，无新表、无新列、
> 无新索引、无数据回填脚本。此处留档的目的是让「零变更」成为**可核对的事实**而非默认假设。

**为何增量化不需要新列**：旧实现按固定页数翻页，无状态；新实现需要知道「本地已入库多少篇」
作为增量游标基线。选用了**现有唯一约束的前缀**：

- 表：`article_manifests`
- 约束：`uq_manifest_source_external` = `UniqueConstraint("source_id", "external_id")`
- 用法：`COUNT(ArticleManifest WHERE source_id = ?)`

`source_id` 是该唯一约束的**前导列**，PostgreSQL 自动为其建立 btree 索引，
故该计数是**索引服务**的，无需另建索引。这是零 schema 变更成立的直接原因。

**为何不用 `MAX(publish_time)` 作游标**：同一 `__biz` 下存在**完全相同的发布时间戳**
（实测批量发文场景），`MAX` 无法唯一定位「最后一条已入库」，会出现「等于游标的文章被跳过」
或「每次重复扫描」两类错误。行数计数不受同一时间戳并列影响，语义稳定。

**代价与权衡**：行数计数是 O(log n) 的一次索引范围扫描，对「单号 400 篇以内」的量级
可忽略；换来的是游标语义与发布时间解耦。**若未来单号篇数达到十万级，应重新评估**
（届时可考虑为 `(source_id, publish_time)` 建复合索引并改用区间游标，那将是一次真实迁移）。

**历史空 `url` 行无需迁移**：R8 之前按错误契约入库的行 `url=""`。修复后 `_apply_update`
对可变字段（`url` / `title` / `publish_time` / `content_hash`）做差异更新，
下一轮同步即**原地补齐**，计为 `updated`。写一条一次性 UPDATE 脚本反而绕过了幂等路径、
且会丢失「哪些行被修正过」的记账——原地补齐同时更新了 `updated` 计数，是可审计的。
