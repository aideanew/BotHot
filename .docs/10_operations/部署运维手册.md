## 一、全栈启动（标准流程）

```powershell
# 0) 前置：Docker Desktop 引擎在位（npipe:////./pipe/dockerDesktopLinuxEngine 可达）
docker version --format "{{.Server.Version}}"

# 1) 配置：docker/.env（参照 .env.example；密钥只进 .env，不入库不入码）
cp docker/.env.example docker/.env

# 2) 最小验证栈（测试/开发，无需 LangBot）
docker compose -p aideanbot up -d postgres redis

# 3) 数据库迁移：已由 migrate 服务声明式承担（见 §3.1/§3.2），up -d 会自动执行
#    幂等（已是最新即空跑）；下方手工口径仅在绕过 compose 直连宿主 venv 时需要
cd backend && .venv\Scripts\python.exe -m alembic upgrade head

# 4) 全栈（含 backend/frontend 镜像构建；同时拉起 migrate/scheduler/worker）
docker compose -p aideanbot up -d --build

# 5) 健康巡检
curl --noproxy "*" http://localhost:8000/api/v1/system/health   # {"code":0,...}
curl --noproxy "*" http://localhost:3333/api/v1/system/health   # 经 rewrite 链

# 6) 服务面核对（9 服务；migrate 的 Exited(0) 是设计态，见 §3.1）
docker compose -p aideanbot ps -a
```

**端口准则（AGENTS.md 铁律）**：3000=主平台专用；AideanBot frontend=3333（容器内 3000）；
backend=8000、LangBot=5300、PG=5433、Redis=6380。

## 三、进程拓扑（9 服务；R4.1.4 / 2026-09-23 增补）

> 本节此前完全缺失：F-10 记录「本手册对 `scheduler`/`worker`/`定时` **零提及**」——即使
> compose 部署正确，**照本手册运维的系统里 U7「定时自动同步入库」会静默不工作**。
> 以下为 `docker/compose.yml` 与本机会话实测口径（2026-09-23）。

### 3.1 服务清单与职责

| 服务 | 容器名 | 镜像 | 宿主端口 | 数据卷 | 网络 | 职责 |
|---|---|---|---|---|---|---|
| `postgres` | `aideanbot-postgres` | `postgres:16-alpine` | 5433→5432 | `aideanbot_pgdata` | default | 全部业务表；**Job 队列也在 PG**（`FOR UPDATE SKIP LOCKED`），不经 Redis |
| `redis` | `aideanbot-redis` | `redis:7-alpine` | 6380→6379 | `aideanbot_redisdata` | default | 会话 / SSO state（`SESSION_STORE_BACKEND=redis`） |
| `langbot` | `aideanbot-langbot` | `rockchin/langbot:latest` | 5300 | `langbot_data`→`/app/data` | langbot_net | 知识引擎；`/app/data` 内含 `langbot.db`/`chroma`/`labels`/`storage`/`config.yaml`/`logs` |
| `langbot_plugin_runtime` | `aideanbot-langbot-plugin-rt` | `rockchin/langbot:latest` | — | `langbot_plugins`→`/app/data/plugins` | langbot_net | 插件运行时（LangRAG 等） |
| `backend` | `aideanbot-backend` | 本地 build | 8000 | — | default + langbot_net | FastAPI Web 层；自带 `/api/v1/system/health` 零门禁探针 |
| `migrate` | `aideanbot-migrate` | 本地 build | — | — | default | **一次性** `alembic upgrade head`，`restart: "no"` |
| `scheduler` | `aideanbot-scheduler` | 本地 build | — | — | default | `python -m app.services.scheduler`：认领到期订阅 → Diff 新篇 → 建 Job/JobItem → 推 `next_run_at` 水位 |
| `worker` | `aideanbot-worker` | 本地 build | — | — | default + langbot_net | `python -m app.services.job_worker`：锁取 Job → 逐篇 ingest → 推 LangBot RAG |
| `frontend` | `aideanbot-frontend` | 本地 build | 3333→3000 | — | default | Next 前端；rewrite 到 `http://backend:8000` |

**三条最易误解的拓扑事实**：

1. `scheduler` 与 `worker` 是**独立常驻进程**，**不进 `app/main.py` 挂接**（`main.py`
   至今只有路由装配，无 lifespan 起后台任务）。**backend 起来 ≠ 系统在工作**：没有
   scheduler 就没有订阅被认领，没有 worker 就没有 Job 被消化。二者任一缺失，U7 静默失效。
2. `worker` 的真实前置是 **LangBot 而非 backend**（`depends_on: langbot: service_started`）——
   worker 直连 `langbot:5300`，与 backend 无 HTTP 互调。故 backend 起不来不阻塞 worker，
   langbot 起不来会阻塞。
3. `migrate` 的 `Exited (0)` 是**设计态**（`restart: "no"`），不是故障；backend /
   scheduler / worker 都以 `service_completed_successfully` 等它。`Exited (137)` 才是被
   kill（128+9 = SIGKILL，OOM 或人工 stop）。

### 3.2 依赖与启停顺序（声明式，非人工步骤）

```
postgres(service_healthy) ─┬─ migrate(completed, restart:no) ─┬─ backend(service_healthy) ── frontend
                           │                                   ├─ scheduler
                           │                                   └─ worker（另需 langbot started）

langbot / langbot_plugin_runtime：无 depends_on，独立起
```

- `redis` **没有任何服务 `depends_on` 它**——backend 起在 redis 之前是 compose 合法的，
  但此时 `SESSION_STORE_BACKEND=redis` 下的登录会失败。见 backend healthy 而登录报错，先查 redis。
- 受控停序（避免丢在飞工作）：`worker` → `scheduler` → `backend` → langbot 两个 →
  `postgres`/`redis`。队列在 PG 且用行锁取件，进程被 kill **不丢件**；在飞那一篇留在非终态，
  由下一次认领重试（是否重跑取决于幂等键）。
- 单独恢复两个执行进程（不动其余）：
  `docker compose -p aideanbot -f docker/compose.yml start scheduler worker`。

### 3.4 ⚠ U7 静默失败判据（定时自动同步空转）

`scheduler` 同步失败（典型：`REDFOX_API_KEY` 缺失/失效、RedFox 3201 积分不足、上游 5xx）时
**不退出、不告警**，行为如下（`app/services/scheduler.py` 错误路径实测口径）：

1. 整轮事务回滚 → **不建任何 Job**；
2. 打一条 `logger.exception("scheduler 同步失败 subscription=%s，水位按基准间隔推进")`；
3. `next_run_at = now + 基准间隔`（**不叠加指数退避**——退避倍数只作用于「空轮询」，不作用于「错误」）；
4. `consecutive_empty_syncs` 不动；
5. **`last_success_at` 不更新**（只有成功路径会写它）。

即：**水位看起来在正常前进，实际 0 篇入库**。基准间隔默认 360 分钟，静默可以持续很久。
巡检判据（可直接照抄）：

```bash
# ① 决定性判据：水位在动但 last_success_at 停滞 = 同步从未成功
docker exec aideanbot-postgres psql -U aideanbot -d aideanbot -c \
  "select next_run_at, last_success_at, consecutive_empty_syncs from source_subscriptions;"

# ② 失败日志直查（非零即有空转）
docker compose -p aideanbot -f docker/compose.yml logs --since=6h scheduler | grep -c "同步失败"
```

### 3.4b ⚠ U7 静默失败判据之二：容器**不存在**（比空转更难发现，2026-09-28 实测新增）

§3.4 覆盖的是「容器在跑但同步空转」。还有一种更隐蔽的失效：**容器根本不存在**。

**实测（2026-09-28）**：`docker ps -a` 全量输出中**无 `aideanbot-scheduler`、无 `aideanbot-worker`**，
连 `Exited` 记录都没有；同栈内 backend / frontend / postgres / redis / langbot×2 均 `Up`。
而 `docker/compose.yml:231` 与 `:272` 明确声明了这两个服务，均带 `restart: unless-stopped`。

**为何 `restart` 策略救不了它**：`restart: unless-stopped` 约束的是「容器**存在**但退出后自动拉起」。
它管不到「容器从未被创建」。栈若按**服务子集**拉起（`docker compose up -d backend frontend ...`）
或经 override 排除了这两个服务，它们就不存在于该栈，`restart` 策略无从生效。

**同根证据**：`migrate`（`restart: "no"`，`Exited(0)` 是设计态）同样缺失。
**compose 文件本身没有错，是运行态与文件不一致**——三个服务进 compose 的时点
（提交 `9362d3c`，2026-09-23 17:40）**晚于**该栈容器创建的时点
（`docker inspect .Created` 实测 2026-09-08 ~ 09-14）5 天，
此后线上只有 `docker cp` 与 `docker restart`，从未跑过 `up -d`。
`docker restart` 只能重启**已存在**的容器，无法创建不存在的容器。

> **⚠️ 更正（v1.5，2026-09-28）：本节此前的「同根证据」第二句有误，已按实测改正。**
> 原写「PG 的 `alembic_version` 因此停留在 `ab1004d04a`，而代码头为 `ab1004s1a`（差 8 个 revision）」——
> **两处都不对**：① 库从未回退，`alembic_version` 当时已在 `ab1004s1a`；
> `ab1004d04a` 是**容器内** `/app/alembic/versions/` 的 head（该镜像只含 11 个 revision 中的 4 个）。
> ② `ab1004d04a` → `ab1004s1a` 实为 **6** 个 revision。
> 结论相应修正：`migrate` 缺失**不等于**「结构迁移没跑」——迁移经下方 §3.4c 的
> **手工宿主步骤**执行过。它真正导致的是 scheduler / worker 两个常驻进程从不存在，
> 以及「今后没有东西会自动跑迁移」。镜像落后另见《阻塞项登记表》**D20**。

**决定性判据（照抄）**：

```bash
# ① 文件声明 vs 运行态差集（非空即漂移）
docker compose -p aideanbot -f docker/compose.yml config --services | sort > /tmp/declared.txt
docker ps -a --format '{{.Names}}' | sed 's/^aideanbot-//' | sort > /tmp/running.txt
comm -23 /tmp/declared.txt /tmp/running.txt   # 期望空输出；有输出 = 该服务不在运行栈中

# ② 结构与代码是否对齐（漂移的伴生症状）
docker exec aideanbot-postgres psql -U aideanbot -d aideanbot \
  -c "select version_num from alembic_version;"   # 与 backend/alembic/versions 最新 revision 比对

# ③ 镜像内的代码是否与仓库一致（② 只能发现「库 vs 镜像」差，此步发现「镜像 vs 仓库」差）
docker exec aideanbot-backend sh -c 'ls /app/alembic/versions | wc -l'   # 期望与仓库一致（11）
docker exec aideanbot-backend sh -c 'grep -rl sync_anchor_hour /app/app | wc -l'   # 期望 > 0
```

> ③ 是本批新增。2026-09-28 实测：当时 ② 全绿（库 `ab1004s1a` = 代码 head），
> 但 ③ 暴露镜像只有 4 个 revision、`sync_anchor_hour` 一处都不出现——
> 即 **② 通过的部署仍可能是坏的**。① 和 ② 都不覆盖「镜像落后」这一类漂移。

**修复动作（已于 2026-09-28 执行，见 §3.4c）**：
`docker compose -p aideanbot -f docker/compose.yml up -d migrate scheduler worker`
（注意是 `up -d` **不是** `start`——`start` 只对已存在的容器生效；
该命令会向线上库写入 `next_run_at` 等行级状态）。详见《阻塞项登记表》D17。

**影响**：订阅不自动同步、清单不自动发现、非终态文档不自动推进。
**backend 健康检查全绿，该停摆完全静默。**
**潜伏特性（关键）**：2026-09-28 实测当时 `source_subscriptions` = 0 行、`jobs` = 0 行——
调度器即使在线也**无事可做**，因此 5 天内零可见症状。已有 250 条 `knowledge_documents`
全部来自 backend HTTP 路径（健康）。**缺陷在第一条订阅被创建的那一刻激活。**
现已落地 `GET /api/v1/admin/ops/liveness`（§3.4d）使此类停摆可被主动查询。

### 3.4c 部署 / 重建流程：单一镜像 + 部署顺序铁律（2026-09-28 落地）

**镜像拓扑变更（L2 消除漂移源）**：`backend` / `migrate` / `scheduler` / `worker` 四个服务
现共用**同一份镜像** `aideanbot-backend`，入口差异由各自 `command:` 决定。
此前三服务各自 `build: context: ../../backend`，即同一上下文产出**三张可各自漂移的独立镜像**——
这正是 2026-09-28 那次漂移的结构性温床（容器代码停在 11 个 alembic revision 中的 4 个）。
合并后「同一时刻四个进程跑不同代码」这类失配在结构上不再可能发生。

**部署顺序铁律（强制）**：

```
① docker compose build backend      ← 唯一的 build 定义源，必须先做
② docker compose up -d migrate      ← 一次性迁移（alembic upgrade head，幂等）
③ docker compose up -d scheduler worker   ← 常驻进程
④ docker compose up -d --force-recreate backend   ← 追平代码
```

理由：`migrate` / `scheduler` / `worker` 只声明 `image:`、**不声明 `build:`**，
故镜像缺失时会**显式 pull 失败**——不会静默跑旧镜像。这是有意的失败模式。

同时，**先 migrate、再上新 backend 代码**不可颠倒：`main.py:_assert_schema_current`
（`app/main.py:185-233`）是**只读守卫**，它不跑迁移；
生产环境（`APP_ENV=production`）下 DB 版本 ≠ head 会直接 `RuntimeError` 拒启。
开发环境仅告警，所以本地可能漏过去——**上线前按此顺序执行**。

**验证三件套（部署后照抄）**：

```bash
# ① 差集：声明 vs 运行态（期望空输出）
docker compose -p aideanbot -f docker/compose.yml config --services | sort > /tmp/d.txt
docker ps -a --format '{{.Names}}' | sed 's/^aideanbot-//' | sort > /tmp/r.txt
comm -23 /tmp/d.txt /tmp/r.txt

# ② 结构：库版本（期望 ab1004h1a）
docker exec aideanbot-postgres psql -U aideanbot -daideanbot -tAc "select version_num from alembic_version;"

# ③ 镜像代码：revision 数 + 关键符号（期望 12 行 / 8 个文件 / 存在）
docker exec aideanbot-backend sh -c 'ls /app/alembic/versions | wc -l; grep -rl sync_anchor_hour /app/app | wc -l'
```

> ② 全绿**不代表**部署正确——2026-09-28 实测即 ② 通过而镜像落后 6 个 revision。
> ③ 是本批新增的判据，覆盖「镜像 vs 仓库」这一类漂移。三步都过才算追平。
> 详见《阻塞项登记表》**D20**。

### 3.4d 常驻进程存活查询（R7.7，替代「只能靠 docker ps 猜」）

`scheduler` 与 `worker` **不开任何端口**，TCP 探针无从谈起。此前唯一的存活信号是
`docker ps` 的 `(healthy)`——但那只对 backend 有效（它探 `/api/v1/system/health`），
两个常驻进程此前**没有 healthcheck**。

**新机制（数据库心跳，唯一诚实信号）**：

| 环节 | 实现 |
|---|---|
| 上报 | 每个进程每轮循环首句向 `process_heartbeats` upsert 一行（`ON CONFLICT DO UPDATE`），时间戳用 SQL `now()` |
| 节流 | `BeaconGate`（单调时钟），最小间隔 **30s**——跨 `await` 安全，不会因 `await` 挂起而重入 |
| 位置 | 放在**每轮循环的开头**而非结尾：卡在循环体里的进程会立刻过期，而不是要等 stale 阈值过后才暴露 |
| 容错 | **吞掉所有异常**。心跳写库失败绝不能变成采集中断——心跳是遥测，不是关键路径 |
| 阈值 | healthcheck 与端点默认 **300s** > 心跳节流 30s，健康进程不会误报 |

**查询方式一：`docker ps` 的 HEALTH 列**（零门槛）

两个服务已配 healthcheck：`python -m app.services.process_heartbeat <key> --max-age 300`
（退出码 0 = 新鲜，1 = 过期或缺行）。

> ⚠️ **unhealthy 不会自动重启**。`restart: unless-stopped` 只认**容器退出码**，
> 而「进程活着但循环卡死」时容器并未退出。healthcheck 的作用是把卡死**暴露**在
> `docker ps` 上，恢复仍需人工 `docker restart`。

**查询方式二：管理端端点**（需要 operator 角色）

```bash
GET /api/v1/admin/ops/liveness[?max_age_seconds=300]
```

返回每个期望进程的 `lastHeartbeatAt` / `ageSeconds` / `stale` 与整体 `allHealthy`。
**设计上区分两种不健康**：「从未报到」（`lastHeartbeatAt: null`，说明进程从未启动，
对应 §3.4b 的容器缺失类故障）与「曾报到但已过期」（进程启动过但卡死或已死）——
两者的处置动作不同，故不合并为一个布尔。

**2026-09-28 实测（上线验证）**：部署后 `docker ps` 显示
`scheduler` / `worker` 均 `Up ... (healthy)`，`process_heartbeats` 两行
`age ≈ 11s`；端点返回 `allHealthy: true`、两者 `stale: false`；
伪造进程键 `ghost` 经 healthcheck CLI 返回退出码 1（负向对照成立）。
参数越界 `?max_age_seconds=5` 返回 422（`ge=10, le=3600` 生效）。

**测试副作用说明**：`tests/test_scheduler.py`、`test_job_worker.py`、`test_docs_batch.py`、
`test_manifest_sync.py` 四个套件自造数据库工厂、**真提交到线上库**（D19），
若不关闭心跳会留下**运维可读的假存活信号**（实测抓到过残留行，已清除）。
故这两个类提供 `heartbeat_enabled: bool = True` 构造参数，上述套件一律传 `False`；
生产路径默认开启，覆盖不被牺牲。

本特性自己的测试（`tests/test_process_heartbeat.py`，17 条）**同样必须避开线上表**：
它的断言对象就是 `scheduler` / `worker` 这两个键，与线上进程写的是同一批行。
若共用真表，「从未报到」的语义根本测不出来（线上每 30s 补回一行新鲜心跳）；
而「为了造缺行去删真表行」会让本手册 §四 第 2 项巡检与上面的 healthcheck 立刻报
`lastHeartbeatAt=null`「从未报到」——即**跑一次测试就把生产可观测性弄坏 ≤30s**。
故该测试文件用 autouse fixture 把表名指向专用隔离表 `process_heartbeats_r77test`
（结构从 ORM 模型拷来再改名，teardown 无论成败都删表）。
**运维侧无需为此做任何事**：正常巡检看到的永远只有真实的那 2 行。

### 3.4e 独立测试库（`aideanbot_test`，2026-09-28 落地 · 一次性设置）

**为什么必须有它**：测试与线上常驻进程共库时是**双向耦合**（见《阻塞项登记表》D23）——
测试用**固定时钟**（落在真实过去），线上 `scheduler` 会把测试造的订阅当成到期任务真实认领并
推进水位，线上 `worker` 会对测试占位链接发起**真实外网 HTTP 抓取**。后果是「全量 `pytest`
的通过数不是稳定基线」。**全程未通过停线上 `scheduler`/`worker` 换取干净数字**——那是触碰
共享运行态，代价高于收益。

```bash
# ① 建库（幂等：库已存在会报错但不影响后续步骤，可忽略）
docker exec aideanbot-postgres createdb -U aideanbot aideanbot_test

# ② 跑全部迁移（与生产库同一条链，head 应同为 ab1004h1a）
cd backend
DATABASE_URL="postgresql+psycopg://aideanbot:aideanbot@localhost:5433/aideanbot_test" \
  python -m alembic upgrade head

# ③ 配一次环境变量（写入 backend/.env，已 gitignore——换机器需重做这一步）
echo 'AIDEANBOT_TEST_PG_DSN=postgresql+psycopg://aideanbot:aideanbot@localhost:5433/aideanbot_test' \
  >> .env
```

**结构核对**（期望 14 张表、`alembic_version` = `ab1004h1a`，与生产库一致）：

```bash
docker exec aideanbot-postgres psql -U aideanbot -d aideanbot_test -c "
SELECT count(*) AS tables FROM information_schema.tables WHERE table_schema='public';"
docker exec aideanbot-postgres psql -U aideanbot -d aideanbot_test -c "SELECT * FROM alembic_version;"
```

**解析优先级**（`tests/conftest.py`，三级）：环境变量 `AIDEANBOT_TEST_PG_DSN` → `backend/.env`
→ 默认生产 DSN **并显式告警**。第三级不是「顺手用生产库」，而是把共库的成因写进告警文本。
`conftest` 解析后**回写环境变量**（`setdefault`，不覆盖显式值）——下游 7 个连库文件各自独立
读取该变量，若只解析不回写，它们仍会直连生产库，**隔离形同虚设**。

**新增迁移后须同步测试库**：与生产库一样手动执行一次 `alembic upgrade head`（`migrate` 服务
只跑生产库，见 §3.4b 的纠偏注释）。CI 侧仍无 PostgreSQL service，见《阻塞项登记表》D24。

### 3.5 容器名 vs 项目名（`name: aideanbot` + 9 处 `container_name`）

`compose.yml` 顶部 `name: aideanbot` 决定**命名卷前缀**与容器 label
`com.docker.compose.project`；9 处硬编码 `container_name: aideanbot-*` 则**固定容器名**，
不随项目名变化。二者叠加后本栈出现了一次实测漂移：

> **实测（2026-09-23）**：`aideanbot-langbot` 与 `aideanbot-langbot-plugin-rt` 的 label 是
> `com.docker.compose.project=docker`——早期曾在 `docker/` 目录下**裸跑**
> `docker compose up`（该目录当时无 `name:`，项目名回落为目录名 `docker`）。
> 其余 7 个属于 `aideanbot`。

| 后果 | 表现 |
|---|---|
| 项目名不匹配 | `docker compose -f docker/compose.yml down/logs/langbot` **找不到**它们 → 必须加 `-p docker` |
| 可见性缺口 | `docker compose ps`（项目 `aideanbot`）只列 3 个运行服务，langbot 侧完全不可见 |
| **数据卷已部分分裂** | 运行中的 langbot 挂的是 `docker_langbot_data`（旧项目卷）；而 `aideanbot_langbot_data`（新项目卷）**已存在但空置**——两套卷并存 |

**为何不能直接删掉 `container_name`**：它是「同卷单实例」的事实护栏。命名卷按项目名隔离，
删掉 `container_name` 后容器名变为 `aideanbot-postgres-1`；若旧的 `aideanbot-postgres` 仍在跑
（`restart: unless-stopped` 会在引擎重启后自动复活），再次 `up -d postgres` 会起**第二个实例
挂同一个 `aideanbot_pgdata`** → 两个 Postgres 共享一个数据目录 = WAL 损坏，且错误延迟暴露。
保留 `container_name` 时冲突是**同步且显式**的（`container name already in use`），立刻失败、
零数据损失。

**F-20 一次性旧栈清理（需人工执行；本会话未执行）**：

```bash
# 0) 备份旧卷——/app/data 含 langbot.db / chroma / labels / storage / config.yaml，
#    插件安装与 KB 索引不是可再生资产，先备份再做任何动作
docker run --rm -v docker_langbot_data:/src -v "$PWD":/dst alpine \
  tar czf /dst/langbot_data_backup.tgz -C /src .

# 1) 停旧 langbot 两个（属 docker 项目，不带 -p docker 找不到）
docker compose -p docker -f docker/compose.yml down --no-deps langbot langbot_plugin_runtime
#    注意：不带 -v，docker_langbot_data 仍保留

# 2) 以统一项目名重建（会自动创建 aideanbot_langbot_data）
docker compose -p aideanbot -f docker/compose.yml up -d langbot langbot_plugin_runtime

# 3) 恢复数据
docker run --rm -v aideanbot_langbot_data:/dst -v "$PWD":/src alpine \
  tar xzf /src/langbot_data_backup.tgz -C /dst
#    恢复后插件依赖与 embedding 模型注册可能仍需 WebUI(:5300) 复核；
#    KB 本身可由 AideanBot ensure_kb 按需重建，优先级低于插件与 embedding

# 4) 旧卷确认无用后再删（须用户书面授权）
docker volume rm docker_langbot_data docker_langbot_plugins
```

清理完成前**不要**移除 `container_name`；备份与清理的顺序不可倒置。

### 3.6 故障排查表

| 现象 | 首查 | 判据 / 处置 |
|---|---|---|
| 订阅到期但无新文章入库 | §3.4 的 `last_success_at` 判据 | 停滞即同步从未成功；查 scheduler 日志「同步失败」那条的 exception 原因 |
| Job 停在 QUEUED 不动 | `docker compose ps -a` 的 `worker` 状态 | worker `Exited` 即不消化 → `start worker`；再查 langbot:5300（worker 的真前置） |
| `migrate` 显示 Exited(0) | — | **设计态**，不是故障 |
| 任一容器 `Exited (137)` | `docker inspect <c> --format '{{.State.OOMKilled}}'` | 被 SIGKILL；`true` = OOM，`false` = 人工 stop 或外部 kill |
| backend healthy 但登录失败 | `docker compose ps redis` | redis 无 `depends_on`，可能未起；`redis-cli ping` → PONG |
| `docker compose logs langbot` 无输出 | §3.5 | langbot 属 `docker` 项目 → 改 `docker logs aideanbot-langbot` |
| 重建后 langbot 报「无 KB / 无插件」 | §3.5 卷分裂 | 新卷是空的 → 走 F-20 清理步骤恢复 |
| `container name already in use` / `port is already allocated` | `docker ps -a` | 旧容器未清理 → 先按 F-20 清理；**不要**为绕过报错而删 `container_name` |

## 四、巡检清单（每日/每次窗口）

1. `docker compose -p aideanbot ps -a`：9 服务面——postgres / redis / backend / frontend Up 且
   backend+postgres healthy；`migrate` **Exited(0) 是设计态**；`scheduler` 与 `worker` 必须
   Up **且 `(healthy)`**（任一缺失 = 容器从未创建，见 §3.4b；任一 unhealthy = 进程卡死，
   见 §3.4d）。langbot 两个不在该命令可见范围内，单独查
   `docker ps -a --filter "name=aideanbot-langbot"`（见 §3.5）；
2. **进程存活（R7.7，零登录成本）**：`process_heartbeats` 两行且 `age_s < 300`
   ```bash
   docker exec aideanbot-postgres psql -U aideanbot -daideanbot -c \
     "select process_key, extract(epoch from now()-last_heartbeat_at) as age_s, left(last_detail,50) from process_heartbeats;"
   ```
   **零行 = 两个进程从未报到**（容器缺失类，处置见 §3.4b）；
   **有行但 age_s 大 = 曾运行但已卡死**（处置 `docker restart`，并查卡死点）。
   需要更细信息用 `GET /api/v1/admin/ops/liveness`（operator+，见 §3.4d）；
3. 端口：3333 唯一前端监听、3334/3335/3456 零前端监听（错峰铁律）；
4. health 三连：8000 直连 / 3333 rewrite / LangBot 5300；
5. Redis：`docker exec aideanbot-redis redis-cli ping` → PONG；
6. 会话持久化：`sso:session:*` 键存在（SESSION_STORE_BACKEND=redis 生效佐证）；
7. **U7 静默失败判据**：`last_success_at` 是否随 `next_run_at` 一起前进（§3.4，
   水位在动不等于有入库）；
8. **漂移三件套**：① 声明 vs 运行态差集、② 库版本、③ 镜像代码（§3.4c 可照抄）。
   **② 全绿不代表部署正确**——2026-09-28 即 ② 通过而镜像落后 6 个 revision；
9. 门禁三绿：pytest（连栈口径）/ ruff+mypy / vitest+tsc+build。

## 五、回滚与故障处置

| 场景 | 处置 |
|---|---|
| backend 镜像异常 | `docker compose -p aideanbot up -d --force-recreate --no-build backend`（重建不重构建） |
| scheduler / worker 未运行 | 先用 §3.4b 判据① 区分**存在但停了**还是**不存在**：前者 `docker compose -p aideanbot start scheduler worker`（只拉这两个，不动其余），后者必须 `up -d scheduler worker`（`start` 对不存在的容器无效）；**backend 起来不等于系统在工作**（§3.1） |
| scheduler / worker **up 但 unhealthy** | **不会自动重启**（`restart: unless-stopped` 只认退出码，卡死时容器并未退出）。`docker restart aideanbot-scheduler` / `-worker` 拉起，然后查 `docker logs` 找卡死点（常见：LangBot DNS 断连、RedFox 长请求）；§3.4d |
| **镜像落后于库/仓库**（D20） | ② 库版本判据可能全绿但镜像仍旧——务必跑 §3.4c 判据③。处置：`build backend` → `up -d migrate` → `up -d scheduler worker` → `--force-recreate backend`。**顺序不可颠倒**（`_assert_schema_current` 生产环境拒启） |
| 迁移失败 | `logs migrate` 取错因 → 修迁移 → `up -d`（backend/scheduler/worker 会因 `service_completed_successfully` 全都不启动，错误显式可见） |
| 迁移回滚 | `alembic downgrade -1`（单步；多步逐级回退，勿跳级），随后重跑 `migrate` 使 schema 与代码一致 |
| PG 数据异常 | 命名卷 `aideanbot_pgdata` 未破坏时 `down`（不带 `-v`）→ 修因 → `up -d`；**禁 `down -v` 除非用户书面授权** |
| 引擎挂死（npipe 不可达） | 三级处置：DD 重启 → DD 全退+wsl --shutdown → 冷启动（历史 10 次掉线档案见台账 §四.0） |
| LangBot 不可达 | 先查 NO_PROXY 是否被改动，再查 `aideanbot-langbot` 与 `aideanbot-langbot-plugin-rt` 两容器（box runtime 日志见 §3.3；`docker compose logs langbot` 取不到，属另一个项目——§3.5） |
| `container name already in use` | 旧栈容器未清理 → 按 §3.5 的 F-20 步骤清理；**不要**为绕过报错而删 `container_name`（同卷双 Postgres = WAL 损坏） |
